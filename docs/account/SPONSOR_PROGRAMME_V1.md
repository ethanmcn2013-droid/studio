# Internal Sponsor Programme reporting contract

Version: `sponsor-cohort.v1`. Internal venue implementation; not a production release, anonymity claim, new commercial offer or privacy/legal approval. The ten-unit rule is a conservative review candidate. Student and teacher configurations are present but disabled until their own eligibility, access scope and agreement are established. Teachers means staff, never pupils.

## Programme and entitlement boundary

The programme references the canonical sponsor and existing verified licence-code/issuance/redemption chain. It never grants access or creates workspace membership. Venue allowance remains unlimited eligible couples, and existing redeemed access survives venue cancellation under the existing commercial contract. A reporting member is not a recipient Project member. Education never inherits venue pricing, allowance or access duration.

One couple gift is one canonical claimed licence code and one sponsored Project. Within each sponsor report family, both code identity and Project scope are reserved by the disclosure ledger: a reissued code cannot make the same Project a second report unit. Multiple live grants on one Project are ambiguous and fail closed. A partner's permitted deliberate task creation counts toward the same unit. Other personal/B2C Projects, automated/import actions, invalid provenance and the wrong environment do not contribute.

## Fixed cohort and time windows

Each report follows gifts claimed in calendar month M in the programme timezone. Its activity period is calendar month M+1. Started planning means the first observed successful deliberate task creation from claim through the end of M+1. Return means another qualifying action on another local day within 35 days of that first observed action. Publication waits until M+1 end plus 35 full local days and the existing six-hour close grace. This gives every starter a complete follow-up opportunity. Day-level private contributions are kept for at most 100 elapsed days; raw event retention stays 35 days. A new publication is unavailable once the instant 100 elapsed days before publication reaches the cohort start in the programme timezone. This conservative fixed deadline prevents retention gaps even when the retention worker is delayed, including daylight-saving transitions. The resulting publication window is short (typically a few days); missed windows are unavailable and never reconstructed from expired history. Existing frozen reports keep their separate payload retention.

This is a cohort adoption/early-use report, not a dashboard of every currently funded recipient or a longitudinal trend. Within one sponsor report family, each gift and scope may appear in only one released report. Month order is monotonic; alternative dates, filters, epoch changes, overlapping cohorts, regenerated editions and cumulative totals are refused. A correction requires restriction, not changed published counts. The fixed reporting calendar can be reviewed later as a new version with explicit privacy review. Sequential sponsorship of the same Project by different sponsors can compose privacy loss: this version does not claim a global lifetime disclosure budget. Active overlapping grants are refused, but cross-sponsor historical composition remains an external-release blocker. Erasure removes private disclosure links rather than silently retaining them to imply a global guarantee.

The claim denominator comes from complete verified App grant enumeration checked against Studio's canonical issuance ledger, never from event senders or login activity. Incomplete pagination/outage refuses publication. Duplicate unit/scope or conflicting hash epochs yields unavailable data. Data-before-collection, missing quiet-day evidence, measurement opt-out or access expiry during the window makes the entire cohort's behavioural measures unavailable. Recent claims are not churn.

## Measurement and release

Only deliberate task creation is instrumented in v1. It is an activation/use proxy, not all planning, engagement, satisfaction or causal ROI. Repeated actions, multiple couple members and duplicate deliveries cannot increase distinct recipient units. Daily unique totals are never added into monthly unique recipients.

The publisher builds a 32-cell joint histogram over started/use/return/responded/useful flags. Every cell, including empty cells, receives independent discrete geometric noise with probability P(k) = 2^(-abs(k))/3, sampled as the difference of two geometric-half variates using cryptographically random fair bits. Signed cells are summed before final marginal clamping. Each eligible recipient's behavioral-vector substitution changes two histogram cells, so the candidate mechanism has epsilon ln(4) for this conditional behavior substitution model. This is not a whole-system membership, consent or eligibility privacy guarantee. The fixed cohort, canonical eligibility and coverage conditions are held constant in that model.

Only this noised vector drives behavioral suppression and rounded estimates: the estimated denominator must be at least ten, and each released marginal and complement must be at least ten. Released estimates are rounded to tens and labelled "About N"; they are not guaranteed ranges or exact counts. The raw cohort floor and incomplete-coverage states are explicit eligibility controls outside the conditional guarantee. A ten-unit threshold alone is not a privacy guarantee. No exact behavioral counts, rates, cells, identifiers, private content, workspace labels, person-level activity dates or invitation-to-activity joins appear in JSON, HTML or CSV.

Randomness is sampled only after the existing-publication lookup, inside the same writer transaction as the immutable report and disclosure reservation. Retries, HTML, JSON and CSV return one frozen result; no seed or private histogram is retained in the public projection. Failed transactions reveal no draw. Optional usefulness is disabled by programme configuration; `not_collected` does not depend on whether anyone submitted a response. The engine accepts structured feedback when explicitly configured, but v1 does not provide a recipient feedback collection UI or endpoint. No causal claims follow from it.

Coverage is an independently attested closed-day record including quiet days. An event proves an action, not complete daily observation. The private operator must supply a real evidence reference for each complete day; ingestion never automatically asserts complete coverage. The synthetic receiving rehearsal uses explicit isolated coverage fixtures. Missing telemetry is unavailable/partial, never zero. Precision and completeness are separate.

## Roles, lifecycle and retention

The App authenticates the actor and forwards a short-lived, purpose-specific signed assertion. Studio independently checks current per-programme `report_read`, `report_export` or `invitation_admin` capability and expiry on every request. Invitation administration reads only operational rows; generation, issuance and evidenced delivery are distinct. Delivery requires an authorized operator attestation with an evidence reference and timestamp; the response identifies that source and does not imply a transport-provider receipt. Claim facts come from complete verified App provenance, not the potentially stale Studio minted-code status; an unavailable claim census is explicit. Neither report-read nor billing identity implies invitation permission.

All responses use `private, no-store`; there is no CDN report cache. JSON/HTML reads and CSV exports share the same frozen aggregate. Invalid, cross-sponsor, removed and expired roles are denied. Reporting is feature gated to `internal_test`; no production enablement is delivered by this contract.

Recipient deletion/measurement withdrawal uses the existing signed erasure queue plus Project custody for partner activity. Inside the erasure transaction the programme is restricted, all report payloads for that sponsor are cleared, and contributions/feedback/coverage/disclosure links are removed. Further generation and all serving/export paths refuse the family. Reports are not recomputed after removal, preventing a subtraction disclosure. Previously downloaded files cannot be remotely recalled; internal recipients must delete withdrawn files. External distribution requires a separately reviewed retention/withdrawal policy.

Contributions expire after 100 days, feedback after its stored expiry, published payloads after one year. Expired contributions invalidate their coverage; expiry is not quiet use. Hash-epoch tombstones and existing identity custody follow the existing erasure retention. Operational invitation/entitlement retention is separate. The disclosure ledger is internal pseudonymous custody, never a sponsor field. Programme restriction prevents erased identities being readmitted to a regenerated report.

## API and handoff

- `GET /api/sponsor-programmes/:programmeId/reports/:claimMonth`: released JSON.
- Same route with `format=html`: minimal functional receiving view.
- Same route with `format=csv`: exactly the released metrics; export capability required.
- `GET /api/sponsor-programmes/:programmeId/invitations`: permitted operational references and statuses only.
- `POST` to invitations records issuance and optional evidenced delivery against an existing canonical code; immutable idempotent facts, no access minting.

States: privacy_estimate (rounded, randomized), withheld (no values), unavailable (measurement incomplete/not collected), not yet observable (open follow-up). API refusals: 403 capability/authentication; 404 absent report; 409 invalid cut/conflict; 410 withdrawn/expired family; 503 disabled or unavailable dependency. Errors expose no database or recipient details.

Receiving must bind exact App/Studio commits, real verified issuance/claim/action inputs, isolated database paths, actual API read/export/refusal proof, independent challenge, and owning repository checks. Passing a fixture, committing source or opening a PR alone does not establish acceptance.

## Local replay and configuration

Install each repository with its frozen lockfile. Run Studio `pnpm typecheck`, `pnpm test`, `pnpm build`, and the separate cross-repository `pnpm test:sponsor-receiving` with the matching App checkout beside Studio. The receiving command uses only disposable file databases and synthetic credentials. `node scripts/sponsor-report-rehearsal.cjs --serve` exposes the actual report HTML handler over loopback for three minutes; it does not use shared Preview. The generated JSON/HTML/CSV contain only synthetic approved aggregates. The evidence receipt identifies what was simulated: identities, eligibility, timestamps and closed-day coverage.

The production modules are wired but gates remain off. In an explicitly isolated internal environment, the App proxy requires `SPONSOR_REPORT_STUDIO_ORIGIN`, `SPONSOR_REPORT_ASSERTION_SECRET`, `SPONSOR_REPORTS_ENABLED=1` and `SPONSOR_USAGE_ENVIRONMENT=internal_test`. Studio uses the same purpose-specific assertion secret, existing entitlement binding, verified usage provenance configuration and one accepted hash epoch for operational claim reconciliation. The report secret must differ from issuance and usage secrets. Never commit values.

Apply additive local migrations in receipt order 0001–0004 using their individual guarded runners; no automatic DDL runs during ingestion or reads. Operator-owned programme/member/coverage rows must be explicitly provisioned for the intended environment. `publishCanonicalReport` is a private service entry point, not a sponsor-callable publication endpoint. v1 deliberately provides no public cohort-generation controls. Role expiry is mandatory. Collection remains behind the existing default-off usage flag; recipient withdrawal never changes access.
