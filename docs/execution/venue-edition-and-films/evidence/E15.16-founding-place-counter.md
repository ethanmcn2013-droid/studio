**Task:** E15.16 · **Written:** 2026-08-04 by Claude Code (WP-22)

## 1. The one failure with no correction path

Two venues told they hold the same founding number. D-009 point 6 assigns the
number on cleared payment, explicitly not on signature, precisely because the
cleared payment is the only event that cannot be walked back. D-027 point 2 gave
the number a real column with a unique constraint for the same reason: *"Point 2
costs little and removes the one failure that cannot be walked back: two founding
venues both told they hold the same number."*

## 2. What only a human can do

Notice that money landed. **Nothing detects a cleared payment automatically.**
The operator todo `apply-venue-edition-terms-migration` records it in its own
words: *"nothing detects a cleared payment automatically, so the first founding
numbers need an operator action that does not exist until E08. The field is
ready; the trigger is not."*

## 3. The script

### Step 1 — The schema is in production

- **Check:** `studio/content/hq/operator-todos/apply-venue-edition-terms-migration.md`
- **Result 2026-08-04:** **PASS.** `status: done`. Both passes applied
  2026-08-03. On the production entitlements database:
  `sponsors.founding_number`, `sponsors.founding_number_assigned_at`, **plus a
  unique index**. The todo also records the deliberate starting state: *"No
  existing venue was changed by either pass. No venue is on unlimited, and no
  number is assigned."*

### Step 2 — The uniqueness is enforced by the database, not by code

- **Run:**
  ```bash
  grep -n "founding_number" _wt-wp22/src/lib/entitlements-db/founding-numbers.test.ts
  ```
- **Expect:** a unique partial index on `(founding_number) WHERE founding_number
  IS NOT NULL`.
- **Result 2026-08-04:** **PASS.** The test fixture creates exactly that:

  ```sql
  CREATE UNIQUE INDEX sponsors_founding_number_idx
    ON sponsors (founding_number) WHERE founding_number IS NOT NULL
  ```

  Partial, so many venues can hold null and no two can hold the same number.

### Step 3 — The integrity checker already catches the ways this goes wrong

- **Run:** studio `pnpm test` (the entitlements integrity suite).
- **Result 2026-08-04:** **PASS.** All 21 checks green, including:

  ```
  ✔ catches two venues holding the same founding place
  ✔ catches a founding number outside 1 to 25
  ✔ catches a founding number assigned before payment cleared
  ✔ a correctly-recorded founding venue violates nothing
  ```

  And the assigner's own suite covers the cases that matter operationally: a
  lapsed venue holding a number, a venue that already holds seven asked to take
  seven again, a reversal, and retryability classification.

### Step 4 — Assignment happens inside the payment path, not beside it

- **Check:** `recordAnnualPrepayment` in `src/lib/entitlements-db/venue-billing.ts`.
- **Result 2026-08-04:** **PASS**, and the ordering is deliberate. Its own
  documentation:

  > Payment is recorded first so a failure between the two leaves a paid venue
  > without a number (recoverable, and the assigner is idempotent) rather than a
  > numbered venue without a payment (which is the thing D-009 point 6 forbids).

  The prior defect is recorded in `scripts/mark-venue-paid.ts`: the old script
  *"never assigned the founding number"*, so a founding venue could be marked
  paid and hold no number at all.

### Step 5 — The counter is the database

- **Rule:** the number of founding places taken is
  `SELECT COUNT(*) FROM sponsors WHERE founding_number IS NOT NULL`. Every other
  display is derived and labelled as derived.
- **Fail:** a spreadsheet, a note, or a hand-maintained figure on a page. Two
  sources of truth for this number is the same failure as two venues holding one
  number, one step earlier.

### Step 6 — After every assignment

- **Run:**
  ```bash
  cd studio && pnpm entitlements:integrity
  ```
- **Expect:** exit 0.
- **Fail:** any founding-number violation is a stop and a conversation, not a
  rollback. The venue has been told a number by then.

### Step 7 — The certificate must agree with the database

- **Do:** render `/hq/founding-certificate` for the venue and compare the number
  to `sponsors.founding_number`.
- **Result 2026-08-04:** the route exists (`src/app/hq/founding-certificate/page.tsx`
  parses a `foundingNumber`). Not exercised against a real assignment.
- **Fail:** any mismatch. The certificate is what the venue keeps.

### Step 8 — Publishing places remaining

- **Rule:** any public statement of places taken or remaining is a **static true
  statement with a date**, never a live countdown. Manufactured urgency and
  anything that can go stale are banned programme-wide.
- **Rule:** a venue name is published only where the permission register
  (E15.14) carries a row for that exact use.

## 5. What I would tell the founder

This is the best-defended thing in the programme. The number is unique at the
database level, it cannot be assigned before payment clears, the assigner is
idempotent, it runs inside the payment path rather than beside it, and there is a
checker that catches every way I could think of to get it wrong.

The one soft spot is human and it is named in the operator todo: **nothing tells
anyone that money landed.** The whole chain starts with a person noticing a bank
credit. Put a recurring reminder against it during the cohort windows, because a
founding number assigned three days late is fine and one assigned to the wrong
venue is not.
