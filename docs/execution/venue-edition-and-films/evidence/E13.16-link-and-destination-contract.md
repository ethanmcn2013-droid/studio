## 0. The determinations, made once

Six things a later session should not have to re-argue.

1. **The link layer lives beside the render, never inside it.** signal-motion's
   render manifests are `.strict()` and secret-free by design
   (`src/render/manifest-schema.ts`), and AGENTS.md is explicit: never serialize
   tokens, credentials or signed URLs. A tracked URL is a credential, because it
   is the only thing between a cold email and somebody else's private page.
   **No tracked URL is added to a manifest, to render props, or to any fixture.**
   The two halves are joined by `pinId`, which is already opaque and already
   public.
2. **The mapping token to account is private data.** A token will be sent to one
   named business, so anyone holding the mapping can turn a URL back into a
   venue. It is written under `private/`, which is gitignored with exceptions
   only for `README.md` and `venues.template.csv`, and the tool refuses to write
   anywhere else.
3. **The token encodes nothing.** Not the venue name, not the account id, not the
   cohort, not the pin, not the clock. It is 24 characters from the OS CSPRNG.
   E11.05-07 section 7.1 requires exactly this: a derived token can be computed
   for every other venue in the cohort by anyone who receives one email.
4. **A token is minted once and never re-minted.** Re-running the generator is
   additive. This is the whole safety property: D-013 point 4 runs four touches
   over weeks against one URL per venue, so a rotation would 404 a link already
   sitting in an inbox, and the only remedy after that is an apology.
   **One deliberate exception, and it is not a rotation** (section 12, D-032 R16):
   a leaked token is *replaced*, which keeps the old row resolving rather than
   404ing it. Replacement is an explicit single-account command with a confirm
   flag. It is never something an ordinary run does.
5. **The click is the only event.** D-013 point 3, and **D-032 R15**: page view
   only for Cohort 1. No open pixel, no read receipt, no play event, no
   watch-through event, no scroll depth, no session recording.
6. **A click is not a stage.** E11.01 section 0 point 4 and E09.04 section 0
   point 4, restated because this is the document that could most easily break
   it. A click informs who to follow up first. It never moves a venue forward, it
   never appears in a funnel, and no counter in `PROJECT_STATE.json` is
   incremented by it.

## 1. The URL shape

```
https://signalstudio.ie/v/<token>
```

| Property | Value | Why |
|---|---|---|
| Origin | `signalstudio.ie`, the sending domain | No shortener, no redirect hop, no third-party tracking domain. Shorteners hide the destination and are a known spam signal (E11.05-07 section 7.1) |
| Path | `/v/` and one segment | One page, one link, for the life of the relationship |
| Query string | **None** | A private page for a named business does not need its identifiers in something that gets forwarded, pasted into chat threads and logged by every proxy on the way |
| Token | 24 characters, `[A-Za-z][A-Za-z0-9]{23}` | About 143 bits. E11.05-07 sets the floor at 16 |
| Venue name | **Never** | Section 1.1 |
| Expiry | None during the programme | A venue returning in four months must not hit a 404 (E11.05-07 section 7.2) |

**The leading character is always a letter, and that is load-bearing.** The
export guard in `tools/venue-export.mjs` scans rendered output for Irish landline
patterns beginning `\b0(8[3-9]|6[1-9]|21|1)`. A token that opened with a zero and
happened to continue in the shape of an Irish mobile number sits immediately after
a `/` in its URL and after a quote in its JSON, both word boundaries, so a
perfectly good export would be refused with a message about personal data that
nobody could act on. Forcing a letter first removes every
position where that can happen. Same reasoning as the `pin_` prefix in
`venue-map-export.mjs`.

### 1.1 The URL shape is settled: bare token, never a slug

**Ratified by D-032 R13**, 2026-08-03: *"Private film URLs carry a bare token,
never a venue slug."* This is a decision, not a recommendation, and it is not
reopened.

| Source | Shape | Status |
|---|---|---|
| This contract, and `tools/venue-map-links.mjs` | `/v/<token>` | **Ratified, D-032 R13** |
| `E11.05-07-outreach-email.md` section 7.1 | `/v/<venue-slug>-<token>` | **Superseded by D-032 R13.** Boundary request: that document is outside this package's file column and still carries the slug form |

The case that lost: a slug makes the personalisation visible before the click and
reads legitimate in a way a bare token does not. The case that won:
`consent_public_naming` and `consent_map_publication` are `unknown` for all 219
researched accounts, and a slug in a path puts a venue's name into browser
history, proxy logs, CDN logs, referrer headers and every thread the link is
pasted into. The deciding argument was reversibility. A slug can be added to a
scheme that never had one. A name that has already been sent cannot be recalled.

**The generator already enforces the ratified shape**: a venue name inside any URL
is a fatal finding and nothing is written (`assertNoVenueNameInUrls`). No code
change follows from R13. What follows is that the conflict is closed and the
E11.05-07 line has to be corrected before it is built from.

## 2. The token file

`private/film-links-cohort-<n>.json`, one row per account, eight fields and no
ninth.

| Field | Value | Note |
|---|---|---|
| `accountId` | `VEN-nnnn` | The join key everywhere in this programme. Never a venue name |
| `pinId` | `pin_` + 12 hex | Identical to the map payload's, so the film and the link are the same venue |
| `token` | 24 characters | Minted once |
| `landingUrl` | `<origin>/v/<token>` | The only URL that ever goes in an email |
| `filmUrl` | The media file, or `null` | Keyed to the token. **Never sent to a venue** |
| `thumbnailPath` | The poster frame on disk, or `null` | Keyed to the pin id, never to the token |
| `generatedOn` | Date | When the link came into existence, not when the file was last touched |
| `sentOn` | Date or `null` | Set by the operator when a touch goes out |

**`filmUrl` is `null` today and that is the honest state, not a gap.** E11.05-07
section 7.3 records object storage as assumption A-3: Vercel Blob is recommended,
it is not currently a dependency of `studio`, and the plan's allowance has not
been checked against roughly 300MB plus a few hundred views. A plausible CDN
hostname nobody has provisioned would be a dead URL in the file whose job is to be
correct about where things are.

**`sentOn` is the barrier that protects a delivered link.** Once it is set, a
change to the origin or the path shape is a fatal finding rather than a quiet
rewrite. Before it is set, the same change is a warning: the token survives either
way, and only the assembled URL moves.

### 2.1 Replacement and revocation are row states, and section 12 specifies them in full

E11.05-07 section 8 plans for a leaked token: rotate it, redirect the old one.
That needed three things, and only the first existed.

1. **The route treats unknown and revoked identically.** Section 6. Built into
   this contract.
2. **A revoked-token list the route can read.** Was owned by WP-13 and unbuilt.
   **Section 12 removes the need for a second store**: revocation becomes a
   `status` value on the row that already exists, so there is one mapping rather
   than a mapping plus a list that can disagree with it.
3. **A way to mint a replacement for an account that already has a token.** The
   generator refuses to re-mint by design, which is correct for every ordinary
   run and wrong for this one deliberate act.

**All three are now specified.** **D-032 R16**, 2026-08-03: *"The leaked-token
replacement path is specified now and built before the first send."* The
specification is **section 12** and it is buildable as written: the schema change,
the generator behaviour, the route behaviour, the replacement page's words, what
is recorded on a hit, and the operator procedure. Section 12 also states the
deadline in dates.

**The schema in section 2 above is `signal-film-links/v1` and stays the record of
what exists today.** Section 12 defines `signal-film-links/v2`, which is what must
exist before the first send. Nothing in `v1` is deleted by it.

## 3. The destination

One page, two states on one URL (E11.05-07 section 7.2): invitation first,
proposal after a conversation. The venue never gets a second link.

### 3.1 What the page must carry

| Must | Why |
|---|---|
| The film, poster frame, click to play, no autoplay | Autoplay on a cold click reads as an ad and burns mobile data before consent |
| Captions as a `.vtt` track | Most first views are muted |
| The offer complete in text and stills **below** the film | The page must work with video blocked by a corporate policy. The film is not the destination |
| The venue's name, never the recipient's name | It gets forwarded to an owner or a partner and has to make sense to somebody who never saw the email |
| One action | Reply, or take a time |
| **The launch-scope sentence, verbatim** | **D-032 R4.** The page describes what a venue sees, so it carries `E09.11-copy-system.md` §5.1a's sentence pair without paraphrase: *"At launch you see your invitations and who opened them. Adoption figures follow later in the year."* A venue that reads the offer here and finds no adoption figures on 1 September reads it as concealment |
| One disclosure line about the click record, and a route to object | Section 4.4 |
| `noindex, nofollow`, excluded from the sitemap, `/v/` disallowed in `robots.ts` | A private invitation must not become a search result naming a venue that has not agreed to anything (E10.14) |

### 3.2 What the page must not carry

| Must not | Why |
|---|---|
| Any third-party script, including GA4 | Section 7. This is the blocker |
| Any open pixel or read receipt | D-013 point 3 |
| Any cookie that requires a banner | Nothing to consent to means no consent banner between a venue and the film |
| Session recording, heatmap, scroll depth | A player watching a reader, on a page whose subject is that nobody is being watched |
| Any IP-derived location | Section 4 |
| Any other venue's name, or any hint of one | The film's other pins are anonymous and stay anonymous (E13.04) |
| A login | A password on a cold-email click is where the funnel ends. The token is the access |
| The 45-minute figure, or the map as a promise of eligibility | `01-GEOGRAPHY.md` section 5. It is an internal market definition, and a published boundary turns a founder judgement into a refusal |
| The words "seats", "allotment", "codes remaining", "licences allotted", "X of your 60" | D-020, E09.02 section 8. The commercial gate requires a string sweep returning zero |
| "For life", "forever" | D-009 point 3, D-001 point 16, R-008. The founding rate holds for as long as the agreement renews without lapse |

## 4. The click, and exactly what is recorded

### 4.1 The click is the page render

There is no redirector. E11.05-07 section 7.1 refuses one, and E09.04 section 3.1
states the consequence plainly: the page render **is** the click, and that is the
whole reason the link points at a page rather than at a file. A redirector would
add a hop that hides the destination, is a spam signal, and would give a second
place for a token to be logged.

The event is E09.04's `venue_page_viewed`, in the `venue-outreach.v1` stream.
This document adds no new kind.

### 4.2 The recorded fields

Recorded server-side, after the token resolves and before the response returns.

| Field | Value |
|---|---|
| `accountId` | Resolved from the token server-side. **The token itself is not stored on the event** |
| `occurredAt` | Timestamp, ms since epoch, UTC |
| `cohort`, `touch` | From the account record |
| `state` | `invitation` or `proposal` |
| `firstView` | Boolean |
| `repeatViewCount` | The running count on the account |

**Never recorded, at any nesting depth:** an IP address, a referrer, a person's
name, an email address, a phone number, a device or browser fingerprint, a
location derived from any of those, a venue name in a query string, or any
couple, guest, wedding or planning data.

**One event per account per day.** E09.04's idempotency key is
`sha256(kind, accountId, dedupeKey, day)` over the Europe/Dublin calendar date, so
a page refreshed eleven times in one afternoon is one row and the repeat-view
counter carries the strength of interest instead.

**The token is resolved and then discarded.** Storing it on the event would put a
live credential in an analytics table, which is the first place a debugging export
comes from.

### 4.3 No user-agent class is recorded on a click. Settled.

**Ratified by D-032 R14**, 2026-08-03: *"No user-agent class is recorded on a
click."* This is a decision, not a recommendation, and it is not reopened.

The WP-12 brief for this task named three recorded values: token, timestamp, and
a **coarse user-agent class**. The third is now forbidden, which is what three
existing specifications already required.

- `E09.04-outreach-measurement.md` section 3.1: *"No user agent. No referrer."*
- `E09.04-outreach-measurement.md` section 7, what the stream never holds: *"An
  IP address. A user agent."*
- E09.01 section 6.1 already carries `userAgent` on its forbidden list.

The reasoning D-032 adopted: it is the position both documents already permit, it
is the reversible one, and a coarse class buys a follow-up decision very little
that `repeatViewCount` does not already carry.

**What this binds.** The route records exactly the fields in section 4.2 and no
others. A user-agent class added later is a change to this contract and needs a
change request, not a commit. The schema-level test required by acceptance
criterion 8 rejects rather than trims, so an added field fails the build rather
than arriving quietly in an analytics table.

### 4.4 The disclosure line

One quiet line on the page, and a route to object. Bound by the copy freeze
(2026-08-21) and owned by E12.

> Signal Studio records that this page was opened, and the date. Nothing else.
> Ask us to stop and the record is deleted.

## 5. Retention

Taken from `E09.04-outreach-measurement.md` section 6 unchanged. Outreach records
are commercial records about a business relationship. They do not inherit the
35-day couple-side sweep, and they do not live forever.

| Data | Retention | End action |
|---|---|---|
| Click records, converted account | Life of the agreement plus 24 months | Delete rows, keep the aggregate counts |
| Click records, non-converted account | 12 months from the last touch, or immediately on an explicit objection | Hard delete |
| Click records, suppressed account | **Delete on suppression**, except the suppression record itself | The suppression list is permanent. The observation of them is not |
| Repeat-view counter | Same as the events it summarises | Delete with them |
| The token to account mapping | Life of the relationship, then delete with the account's records | It is the only thing that turns a URL back into a business |
| Aggregate cohort counts | 24 months | Fold into programme totals |

**One rule under the table.** A venue that says stop has its address suppressed
permanently and its outreach observation deleted. Keeping a record of how many
times somebody who told you to go away looked at your page is the wrong side of
the line, and no reporting need justifies it.

## 6. Unknown, revoked and expired tokens

**Unknown and revoked must be indistinguishable.** A route that answers "no such
link" differently from "that link was withdrawn" is an oracle: it confirms which
tokens once existed, which is the enumeration the token exists to prevent.

| Case | Response | Recorded |
|---|---|---|
| Token not in the mapping | `404`, a plain page that names no venue and reveals no token space | **Nothing** |
| Token revoked (`status: "revoked"`) | Identical `404`, byte for byte | **Nothing** |
| Token malformed, wrong length, wrong alphabet | Identical `404` | **Nothing** |
| Token replaced (`status: "replaced"`) | `200`, the replacement page. Section 12.4 | One log line, no analytics event. Section 12.6 |
| Token valid, programme still running | The page | One `venue_page_viewed`, per section 4 |
| Token valid, programme closed | Redirect to `/venues` (E11.05-07 section 7.2) | **Nothing** |

**Replaced is deliberately distinguishable, and revoked is deliberately not.**
They are different acts with different obligations. A replaced token belongs to a
venue that is still in the programme and still needs to reach the film, so
somebody has to be told what happened. A revoked token belongs to a link that must
stop existing. Section 12.3 states the oracle cost of that choice and why it is
accepted.

**No event is recorded for a failed resolve.** A count of bad tokens is a count of
somebody probing, and it is not worth a table. **The response time must not
differ** between a hit and a miss in a way that reveals which is which: resolve
against a constant-time lookup, or make the miss path do the same work.

**The 404 page names nothing.** No venue, no cohort, no "this invitation has
expired", no count of anything. It says the link is not valid and offers the
public `/venues` page.

## 7. The GA4 carve-out, and it is the blocker

**Verified on 2026-08-03.** `studio/src/components/analytics/google-tag.tsx`
renders gtag.js from the root layout at `studio/src/app/layout.tsx:144`, on every
page in production, with `gtag('config', ...)` fired immediately, no Consent Mode
default and no cookie banner. The component's own comment records the gap.

`/v/[token]` will live under that same root layout. **On the day it ships it will
load an unconsented third-party tag**, which directly contradicts section 3.2 of
this document, section 7.2 of E11.05-07 and acceptance criterion 6 of E09.04. The
page whose entire subject is that the venue's couples are not being watched cannot
ship with an ungated third-party tag on it.

**The click contract is violated on arrival unless the route carries an explicit
carve-out.** Three requirements, in order, all owned by WP-13:

1. **Exclude `/v/*` from `GoogleTag` before the route ships.** Whatever mechanism
   is chosen, **the predicate must be imported from one place**. The `app` repo
   already carries that exact defect twice over — `app/src/lib/bare-artifact-path.ts:2`
   and `app/src/instrumentation-client.ts:10` maintain the same predicate by hand
   — and E09.04 section 5.1 recorded it so studio would not copy it.
2. **Add `/v/` to the robots disallow list and exclude it from the sitemap.**
   `studio/src/app/robots.ts` currently disallows `/api/`, `/hq/`, `/redeem/` and
   `/review`. `/v/` is not there.
3. **Decide the public-surface consent position** (E09.04 section 8.2) before any
   new tag, first-party or third-party, lands on a public Venue Edition page.

**A request-log assertion on a real page load is the proof.** Not a code read: the
tag is injected by a layout two levels up from the route, and the only honest test
is what the browser actually requested.

## 8. The poster frame, and the join to the render

### 8.1 What is built, and what it deliberately does not duplicate

`scripts/limerick-first-render.mts` (E13.15) is the batch pipeline. It already
renders stills at `LIMERICK_MAP_REST_FRAME` and already writes them with the pin
id in the name, so E13.16 adds **no second naming scheme and no second still**.

| Item | Decision |
|---|---|
| Frame | `LIMERICK_MAP_REST_FRAME`, currently 360, read from `mapSpec.ts` |
| Why that frame | The first frame on which the map is final, including the recipient's name plate. The spec module already names it as the review still and the sound design contract |
| Declared where | `POSTER_FRAMES` in `src/render/poster.ts`, per composition, from the spec module. A composition with no entry has not decided where its poster is, and that is refused rather than defaulted |
| Name | `makeRenderFilename` with its `frame` segment set: the video's own name plus `__f0360`, in the same directory |
| Format | The render profile's own `imageFormat`, so the poster is a true sample of the same image pipeline. `jpeg` for the review and invitation profiles, `png` for the masters. The delivered JPEG under 200KB (E11.05-07 section 7.3) is a finishing step |
| Derivation | `posterPathForRender(videoPath)` reads the composition and the profile back out of the video's name rather than taking them again from the caller, so a poster cannot be written beside a film it does not belong to |
| Refusals | A path that is not a render output, an unknown profile, an extension that is not that profile's, a frame outside the composition's duration, and **a path containing the recipient's venue name** |

**The gap E13.16 closes.** The pipeline's `--stills` and `--video` modes are
mutually exclusive, so one pass produces a film **or** its poster, never both.
`scripts/venue-film-poster.mts` writes the poster that belongs beside a video that
already exists, and exports `renderVenueFilmPoster` so the pipeline can call it
in-process instead of growing a second copy. **Wiring it into the video path is a
one-line change in a file this package does not own** — recorded as a boundary
request, not made here.

Proven by rendering one:
`signal-motion/out/limerick-first/1/signal-motion__limerick-map-v1__pin-78864023a9a4__limerickfirstmap-16x9__review-16x9-v1__r001__f0360.jpeg`,
frame 360, from the committed fictional fixture. The map is complete, the
recipient dot carries the single earned indigo, and the name plate is fully open.

### 8.2 The join to the link file, and a trap that was live

**Every personalised render filename must contain that venue's `pinId`.** The
pipeline already satisfies this: `makeRenderFilename`'s `subject` segment is the
pin digest. The generator resolves each account's poster by finding the one image
in the render directory whose name contains it. Zero matches means "not rendered
yet". More than one is a fault and stops the run, so `--renders` must point at one
profile's output rather than at a directory holding several.

**The pin id and not the token.** A token is a credential, and a filename ends up
in build logs, terminal scrollback and review screenshots. The generator refuses a
`thumbnailPath` that contains the token, compared case-insensitively because a
filename segment is lowercased on the way to disk.

**The trap, found by rendering rather than by reading.** `safeSegment` lowercases
every filename segment and collapses everything outside `[a-z0-9-]` to a hyphen,
so `pin_78864023a9a4` is written to disk as `pin-78864023a9a4`. A resolver
searching for the underscored form finds nothing, **for every venue in the cohort,
with no error anywhere** — twenty-five null thumbnails and a green run. Both sides
now carry the translation and both have a test that fails if it is removed:
`pinSegment` in `tools/venue-map-links.mjs` and `posterCarriesPin` in
`src/render/poster.ts`.

## 10. Acceptance criteria

Written so an auditor who was not in the room can answer each yes or no.

1. Every account in a cohort has exactly one link, and the link file's declared
   size matches its body.
2. Re-running the generator mints nothing for an account that already has a
   token, and the resulting file is byte-identical when no input changed.
   *Verified: 25 reused, 0 minted, byte-identical.*
3. A token is 24 characters from a URL-safe alphabet, starts with a letter, and is
   not derived from the account id, the venue name, the cohort or the clock.
4. No venue name appears in any URL, path or filename the generator writes,
   proven by a check against the real names in the operational file.
5. No token appears in a render manifest, in render props, in a fixture, or in any
   file inside `signal-motion`.
6. The link file is written only inside `private/`, and `private/` is gitignored.
   *Verified: `git check-ignore` resolves it to `.gitignore:64`.*
7. Every `pinId` in the link file is present in that cohort's map payload, and
   every payload pin has a link.
8. The destination route records exactly the fields in section 4.2 and no others,
   proven by a schema-level test that rejects rather than trims.
9. No open pixel, read receipt, session recording, heatmap, scroll-depth or
   IP-location mechanism exists on the destination, proven by a string sweep over
   `studio/src`.
10. The destination loads no third-party script and sets no cookie that requires
    consent, proven by a request-log assertion on a real page load.
11. `/v/` is disallowed in `robots.ts` and absent from the sitemap.
12. An unknown token and a revoked token produce byte-identical responses, and
    neither records an event.
13. Every personalised render filename contains that venue's pin id, and the link
    tool resolves each account's poster by it in the form the filename actually
    carries. *Verified: 25 of 25 resolved against a directory named the way the
    pipeline names one.*
14. The poster frame number is read from the composition's spec module, proven by
    a test that fails if a script carries a literal instead.
15. Every delivered film has a poster frame beside it, produced in the same run.
    **Not met.** The mechanism exists and is proven; the batch pipeline's still
    and video modes are still mutually exclusive. Boundary request in section 9.

**The replacement path, added by D-032 R16. Every one of these is unbuilt today
and every one must be met before the first send (section 12.8).**

16. Every row in the link file carries an explicit `status` of `active`,
    `replaced` or `revoked`. A row with no `status` is a fatal finding, never a
    row defaulted to `active`.
17. Exactly one row per `accountId` has `status: "active"`. Zero is fatal, because
    the account is unreachable. Two is fatal, because two live links for one venue
    is the condition the whole file exists to prevent.
18. An ordinary run mints nothing for an account that already has an active row,
    and is byte-identical when no input changed. The v1 stability property
    survives the schema change unweakened.
19. A replacement run touches exactly one account, keeps the old row with its
    `token`, `landingUrl`, `generatedOn` and `sentOn` unchanged, and appends one
    new row. `assertTokensPreserved` passes across the change.
20. No row anywhere carries a forward pointer from a replaced token to the live
    one. Proven by a test that fails if the field is added.
21. A replaced token returns `200` and the replacement page, emits no
    `venue_page_viewed`, and the page names no venue, carries no film, carries no
    offer detail and links to no other token. A revoked token returns the same
    `404` as an unknown one, byte for byte.

Criteria 8 to 11 are WP-13's to satisfy. Criterion 15 is E13.15's. Criteria 16 to
20 are E13.16's. Criterion 21 is shared: the generator side is E13.16's, the route
and the page are WP-13's. Criteria 1 to 7, 13 and 14 are E13.16's and are met or,
where marked, verified.

## 12. The replacement path for a leaked token

**Ratified by D-032 R16**, 2026-08-03: *"The leaked-token replacement path is
specified now and built before the first send."*

**The problem this closes, stated plainly.** Today a leaked film link cannot be
replaced. The generator refuses to re-mint by design (section 0, determination 4),
there is no revoked-token list, and there is no route. So if a token is posted in
a public forum, pasted into a shared inbox, or forwarded outside the venue it was
sent to, the only remedy available is an apology. That is not an acceptable state
to send twenty-five cold emails from.

**What follows is a buildable specification**, not a plan to write one. Every
field, refusal, response code, sentence and operator step is fixed here. The one
thing it cannot fix is section 12.9, and that is named rather than hidden.

### 12.1 The schema change

**`signal-film-links/v2`.** The version string is a literal the destination route
parses against (`LINKS_SCHEMA_VERSION` in `tools/venue-map-links.mjs`), so it
changes and both sides move together. Nothing in `v1` is deleted. Three fields are
added to each row, making eleven, and there is no twelfth.

| Field | Value | New in v2 | Note |
|---|---|---|---|
| `accountId` | `VEN-nnnn` | | The join key. Never a venue name. **No longer unique across rows** |
| `pinId` | `pin_` + 12 hex | | Unchanged on a replacement: the venue is the same venue and the film is the same film |
| `token` | 24 characters | | **Unique across every row, live or not** |
| `landingUrl` | `<origin>/v/<token>` | | |
| `filmUrl` | The media file, or `null` | | Keyed to the token, so a replacement re-keys it |
| `thumbnailPath` | The poster on disk, or `null` | | Keyed to the pin, so a replacement carries it across unchanged |
| `generatedOn` | Date | | When *this row's* token came into existence |
| `sentOn` | Date or `null` | | Never cleared by a replacement. It is the record that this URL reached a human |
| `status` | `"active"` · `"replaced"` · `"revoked"` | **yes** | **Required. No default.** A row without it is a fatal finding |
| `withdrawnOn` | Date or `null` | **yes** | The date this row stopped being the live one. Non-null if and only if `status` is `"replaced"` or `"revoked"`. Named for both states rather than for one, because a field called `replacedOn` sitting on a revoked row is the kind of small lie that later gets read as data |
| `replacementFor` | A token, or `null` | **yes** | **Points backwards only.** Set on the new row, naming the token it replaces. Never set on the old row |

**Why `status` has no default, and this is the most important line in the
section.** A row that arrives without a status and is treated as `active` silently
resurrects a token somebody deliberately withdrew. Defaulting is how a withdrawal
becomes a leak a second time. A missing status stops the run.

**Why `replacementFor` points backwards.** The obvious design puts a forward
pointer on the old row, and it is wrong. A route resolving a leaked token would
then be holding the live token in memory one field away from the response, and the
first debugging log, error report or serialisation mistake puts it in front of
whoever has the leaked link. Pointing backwards means the replaced row carries
nothing that could leak the replacement, and the audit trail is still complete
because the new row says what it replaced. **Acceptance criterion 20 is a test
that fails if a forward pointer is ever added.**

**Uniqueness, restated because it is what the guard has to enforce.**

- `token` is unique across every row in the file, whatever its status.
- `accountId` is **not** unique. That is the change.
- **Exactly one row per `accountId` has `status: "active"`.** Zero is fatal: the
  account has no reachable link. Two is fatal: a venue with two live links is the
  condition the file exists to prevent.
- `pinId` still equals `pinIdFor(accountId)` on every row, replaced ones included.
- `generatedFor.size` still equals `links.length`, now counting replaced and
  revoked rows. A file that under-declares its own length is how a truncated read
  passes.

**What the schema deliberately does not carry.** No reason string, no free-text
note, no operator name, no leak description. The file is a private JSON that gets
copied to make backups. A sentence describing how a token leaked is a sentence
about a person, and it belongs in the session record, not in the mapping.

### 12.2 The generator behaviour

**An ordinary run does not change at all, and that is a requirement rather than a
convenience.** `node tools/venue-map-links.mjs --cohort=1` still mints only for an
account with no row, still reuses every existing token, and is still byte-identical
when no input changed. Acceptance criterion 18 pins it. The v1 stability property
is the one thing that must not weaken when the file learns to hold a second row per
account.

Three internals move to make that true:

| Today | In v2 |
|---|---|
| `previous` is a `Map` keyed by `accountId` | Keyed by `token`, with a separate index from `accountId` to its one active row |
| `assertTokensPreserved` compares tokens per account | Compares per token: every token that existed still exists, with the same `accountId`, the same `landingUrl`, and a status that has only moved forwards |
| `guardLinkFile` rejects a duplicate `accountId` | Rejects a duplicate `token`, and rejects any `accountId` whose active-row count is not exactly one |

**Status is a one-way ratchet.** `active` may become `replaced` or `revoked`.
Nothing ever becomes `active`. A run that would move a status backwards is a fatal
finding and writes nothing. Un-revoking is not a repair, it is a second leak.

**The replacement act, and it is explicit, single and confirmed.**

```
node tools/venue-map-links.mjs --cohort=<n> --replace=<accountId> --confirm-replace
```

| Rule | Behaviour |
|---|---|
| One account per run | A second `--replace` is a fatal finding. There is no `--all`, no comma list and no glob. Replacing twenty-five tokens in one command is not an operation anybody should be one typo away from |
| `--confirm-replace` is required | Without it the run prints what it would do and writes nothing |
| The account must have an active row | If it does not, the run refuses and says so. There is nothing to replace |
| The old row | `status` becomes `"replaced"`, `withdrawnOn` becomes today. `token`, `landingUrl`, `generatedOn` and `sentOn` are untouched |
| The new row | A fresh mint through the same `mintToken`, `status: "active"`, `replacementFor` set to the old token, `generatedOn` today, `sentOn` `null` |
| `filmUrl` | Re-keyed to the new token when `--media-base` is set, `null` otherwise. The old row keeps its old `filmUrl` so the operator can find the object to delete |
| `thumbnailPath` | Carried to the new row unchanged. It is keyed to the pin, and the pin has not moved |
| Every existing guard | Runs unchanged. A replacement run that trips the venue-name check, the forbidden-column check or the phone-pattern check writes nothing, exactly like an ordinary run |
| The `sentOn` barrier | Still fatal on the replaced row. Replacing a token is not permission to rewrite the URL that was already delivered |

**Revocation uses the same act with a different flag**, `--revoke=<accountId>
--confirm-revoke`, and mints nothing. The account is left with no active row,
which is a fatal finding on the next ordinary run unless it has also been removed
from the cohort. That is deliberate: a venue whose only link is revoked has to be
consciously taken out of the cohort rather than left half-present.

**The printed counts on a replacement run**, because an operator needs to read
success rather than infer it: `1 replaced, 1 minted, 0 re-minted, N reused,
M carried`. A `re-minted` count above zero is a bug, not a result.

### 12.3 What the route does, and the oracle cost of it

The route reads the mapping and branches on `status`.

| Status | Response | Why |
|---|---|---|
| `active` | The page, per section 3 | |
| `replaced` | `200` and the replacement page, per section 12.4 | Somebody is holding a link we withdrew and they need to be told something true |
| `revoked` | The same `404` as an unknown token, byte for byte | Section 6. The link must stop existing |

**The oracle, stated and accepted.** Section 6 requires unknown and revoked to be
indistinguishable, because a route that answers differently confirms which tokens
once existed. A replaced token is distinguishable, so it is an oracle, and that is
a deliberate exception rather than an oversight.

What it costs: somebody probing the token space who happens to land on a replaced
token learns that this one existed. What it does not cost: which venue it belonged
to, whether that venue is in the programme, what the offer is, or what the live
token is. The page names nothing and carries nothing.

What it buys: the one person who actually matters, the recipient of a link that
stopped working, gets a sentence instead of a `404`. Twenty-four characters of
base62 is about 143 bits, so the enumeration this trades against is not a real
attack. The venue reading a dead link is real.

**The route reads three fields and no others**: `token`, `accountId`, `status`. It
does not read `replacementFor`, which exists for the operator's audit trail. Not
reading it is enforceable: `replacementFor` is null on every replaced row by
construction, so a route that read it would get nothing.

**No redirect, ever.** A replaced token must not redirect to the live one. That
would hand the working link to whoever holds the leaked one, which is the exact
failure the replacement exists to prevent. The replacement page carries no link to
any other token.

### 12.4 The replacement page, in final words

Bound by the copy freeze, **2026-08-21**, which is the earliest of this section's
three deadlines. Applies `E09.10-copy-hierarchy.md` and `BRAND.md` section 3.

> ### This link is no longer in use
>
> The address you opened has been replaced. If it was sent to you, write to
> hello@signalstudio.ie and we will send you the current one.
>
> Signal Studio records that this page was opened, and the date. Nothing else.
> Ask us to stop and the record is deleted.
>
> signalstudio.ie

**What each line is doing.** The heading states the fact without accusing anybody
of anything: whoever is reading may be the venue, may be a colleague it was
forwarded to, and may be a stranger. The second sentence gives the one action, and
it is a reply to a person rather than a form. The disclosure line is section 4.4's
sentence reused verbatim rather than a second version of it. The last line is a
name, not a call to action.

**What the page must not carry.**

| Never | Why |
|---|---|
| The venue's name, or any hint of it | Whoever is reading may not be the venue |
| The film, a poster frame, or any still | The withdrawn link's content is exactly what is being withdrawn |
| The offer, the price, the term, or the founding programme | This is not a commercial surface |
| A link to the replacement token, or any other token | Section 12.3 |
| "Expired", "revoked", "invalid", "unauthorised", "security" | Each either states something untrue or invites a question the page cannot answer. The link was not invalid and nothing expired |
| A date, a countdown, or "as of" anything | It tells an enumerator when the token changed |
| Any third-party script, cookie or pixel | Section 3.2 applies to this page unchanged |
| A form, a field, or anything to type into | The action is an email to a person |

`noindex, nofollow`, excluded from the sitemap, and covered by the same `/v/`
robots disallow as every other state of this route.

### 12.5 Replace or revoke, and how the operator tells them apart

They are not two names for one act.

| Situation | Act |
|---|---|
| The link was posted publicly, forwarded outside the venue, or landed in a shared inbox that is not the recipient's, **and the venue is still in the programme** | **Replace.** They still need to reach the film |
| The venue has said stop | **Revoke**, and delete its outreach rows. Section 5's rule under the table: a venue that says stop has its address suppressed permanently and its outreach observation deleted |
| The link was sent to the wrong venue | **Revoke** the wrong one, and mint a fresh row for the right account through an ordinary run. A replacement page shown to a venue that was never meant to be contacted explains nothing to them |
| The film itself is wrong: mispronounced name, wrong county, wrong pin | **Neither.** E11.05-07 section 8 already answers this: fix the render, re-upload against the same token, and tell them plainly. The URL does not change, which is the whole reason the link points at a page rather than at a file |

### 12.6 What is recorded on a hit to a replaced token

**No `venue_page_viewed`.** A page nobody meant to open is not a film view, and
counting it inflates the one metric D-032 R15 leaves standing. The event stream
records nothing.

**One structured server log line**, and nothing else:

| Field | Value |
|---|---|
| `accountId` | Resolved from the token server-side |
| `occurredAt` | Timestamp, ms since epoch, UTC |
| `outcome` | The literal string `replaced` |

**Never on that line, at any nesting depth:** the token, an IP address, a
referrer, a user agent, a person's name, an email address, or a location derived
from any of those. The same never-list as section 4.2, for the same reasons.

**Retention: 30 days, then gone.** It is an operational log, not measurement. It
never reaches a figure, a rate, a funnel, a CRM stage or a counter in
`PROJECT_STATE.json`, and it is never venue-visible.

**Why it exists at all, since section 6 records nothing for a failed resolve.** It
answers exactly one operator question: is the withdrawn link still circulating.
That is the only input to the decision to escalate from replace to revoke. A
leaked link that nobody opens again needs nothing further; one that is still being
opened three weeks later is a different situation. Without the line the operator
is guessing.

**The alternative that was refused**, recorded so it is not reinvented: emitting
`venue_page_viewed` on a replaced hit. It needs no new plumbing, which is its only
merit. It would put opens of a withdrawn page inside the one figure Cohort 1 is
measured on, and the first person to notice would be whoever tried to explain the
number.

### 12.7 The operator procedure

Nine steps. Every one is checkable by somebody who was not in the room.

1. **Confirm it is a leak.** A leak is: the URL posted publicly, quoted in a
   screenshot outside the venue, forwarded to an address outside the venue, or
   sitting in a shared inbox that is not the recipient's. A colleague at the same
   venue opening it is not a leak. Neither is a second view from the recipient.
2. **Decide replace or revoke** against the table in section 12.5. Write the
   decision down before running anything.
3. **Run the replacement**, one account, with the confirm flag:
   `node tools/venue-map-links.mjs --cohort=<n> --replace=<accountId>
   --confirm-replace`. Read the printed counts. Expect `1 replaced, 1 minted,
   0 re-minted`. Anything else means stop.
4. **Re-key the film object and delete the old one.** A leaked landing page is
   recoverable. A leaked media URL that still serves is not, because the file
   itself is the thing that was private. The old row keeps its `filmUrl` so the
   object is findable.
5. **Publish the updated mapping** to wherever the route reads it. Section 12.9
   is honest that this step is not yet specifiable.
6. **Verify, on the real deployment, not by reading code.** The old token returns
   `200` and the replacement page. The new token returns the venue page. An
   unknown token returns the same `404` it did yesterday. No `venue_page_viewed`
   appears against the old token.
7. **Tell the venue, in the ordinary reply thread**, one line, no apology theatre
   and no explanation of the mechanism. Never a fresh cold email: a second cold
   email about a link problem is a worse impression than the link problem.
8. **Set `sentOn` on the new row** when that message goes out. Until then the row
   is correctly recorded as never sent.
9. **Return it for recording.** One line in the session record naming the account,
   the date and which act was taken. If the leak was ours rather than the venue's,
   it is also a `RAID.md` entry. Neither file is written by a work-package
   session (WORKFLOWS section 7); both are returned to the orchestrating session.

### 12.8 The deadline, in dates

**"Before the first send" resolves to a date, and it is not the date it looks
like.**

The first send is Cohort 1's first touch, which is Phase 6 work and lands with the
Cohort 1 release at **milestone M5, 2026-09-01**. It cannot happen earlier,
because it depends on the film-lock at **2026-08-28** (D-008 point 3, and E13.17's
own target) and on the release candidate at **2026-08-30**. It also cannot happen
without DKIM, SPF and DMARC live plus a two-week domain warm-up (R-010, E11.05-07
section 9), which means the warm-up starts no later than **2026-08-18** for a
1 September send.

| What | By when | Why that date |
|---|---|---|
| **The replacement page's words** | **2026-08-21** | The copy freeze, D-008 point 3. They are front-facing strings. This is the earliest deadline and it is eighteen days from 2026-08-03 |
| The schema, the generator, the route and the tests | **2026-08-30** | The release candidate. A path built after the candidate is a path that has never been exercised in the build that ships |
| Everything, working, verified on the real deployment | **2026-09-01** | M5. The first tokens go into inboxes on this date and the window closes behind them |

**Why the window closes rather than narrows.** Before the first send there are
zero live links and building this costs nothing but time. After it there are
twenty-five, each one in a named business's inbox, and the first leak arrives
whenever it arrives. There is no version of this that is cheaper to build later.

### 12.9 The one part this document cannot finish

**The route needs a store it can read at request time, and there is not one.**
Today the mapping is `private/film-links-cohort-1.json`, which is gitignored, sits
on one machine, and is read by a tool rather than by a server. The route does not
exist yet either (section 11).

Choosing that store is WP-13's, and this document does not choose it. What this
document fixes is the contract it has to satisfy:

1. It carries the eleven fields of section 12.1, with `status` required and no
   default.
2. It enforces the uniqueness rules of section 12.1, ideally in the store rather
   than in application code. One active row per account is an invariant a database
   can hold and a JSON file cannot.
3. **No venue name is in it**, in any column, at any nesting depth. The same rule
   as the file it replaces.
4. Token resolution never leaves the server, and the token is never returned to
   the client in any response, header or error.
5. A miss costs the same as a hit, or the miss path is made to do the same work.
   Section 6's timing rule applies to the store, not only to the handler.

**Until that store exists, step 5 of the operator procedure has no command**, and
this is the honest state rather than a gap somebody forgot. It is recorded as a
boundary request to WP-13 rather than resolved here, because writing a store into
a surface another package owns is how two packages ship two incompatible halves of
one thing, which is the reason section 0 gives for this document containing no
route code at all.
