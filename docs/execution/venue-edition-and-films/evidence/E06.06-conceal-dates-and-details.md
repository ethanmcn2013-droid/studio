# E06.06 — concealing dates and other sensitive details

Written 2026-08-03 in worktree `_wt-wp14` (app, branch `claude/wp14-timeline`).
Acceptance criteria were written before the assessment.

Nothing in this document states or implies legal approval or GDPR compliance
(D-016). Capabilities that do not exist are named as not built.

---

## The headline in one paragraph

Per-milestone date concealment already worked and is recorded here rather than
rebuilt. The wedding day itself did not: `primaryDate` was written once at
creation and there was no way to take it off a live page short of unpublishing
the whole artifact. That is now a control the couple can use, and concealing
removes the field from the payload rather than hiding it in the render. Location
is a different matter and the honest answer is a refusal, written down.

---

## Criterion-by-criterion

### 1. Milestone date concealment, on the serialised DTO — **MET, existing**

Two layers, both already shipped.

**Curation.** `node_overlays.date_override` carries an explicit three-way
intent, `inherit | date | undated`, persisted through the sentinel
`__signal_timeline_undated__`
(`src/modules/timeline/server/db/timeline-queries.ts:77-99`). A null column no
longer doubles as both "inherit" and "intentionally undated", which is what
makes concealment expressible.

**Published copy.** `updateAudiencePublicationItem`
(`src/modules/timeline/server/audience-timeline.ts:599`) accepts a null
`calendarDate` on an already published item, and the owner control submits it
through `optionalCalendarDate`, so clearing the date field in the manager and
saving takes the date off the live page.

**The payload.** `lib/audience-timeline.ts:221`:

```ts
if (item.date !== undefined) mapped.date = calendarDate(item.date, `${path}.date`);
```

```
✔ E06.02 · title-and-date · an undated milestone carries no date key
```

In one resolved payload, "Find the dress" has keys exactly
`publicId, state, title` and `"date" in item` is false, while "The ceremony" in
the same payload has `date, publicId, state, title`. The key is absent, not
blank.

### 2. The wedding day has its own control — **MET, built here**

**The gap.** `primaryDate` and `primaryDateLabel` were set inside
`createAudiencePublication` (`audience-timeline.ts:219-220`) and no code path
updated them afterwards. `getOwnerAudiencePublications` read them; nothing
wrote them.

**What was added.**

- `setAudiencePrimaryDate` — `src/modules/timeline/server/audience-timeline.ts:650`.
  Re-checks `ownsPublication`, then writes both columns. Returns `"set"` or
  `"concealed"`.
- `updateAudiencePrimaryDateAction` —
  `src/modules/timeline/server/actions/audience-timeline.ts:363`. Owner-gated
  through `ownerWorkspace`, demo-read-only guarded, revalidates
  `/app/timeline/audience`.
- The owner control — `src/modules/timeline/app/audience/audience-manager.tsx`,
  in each publication card: a label field, a date field, a **Save** button, and
  a separate **Hide the date** button that appears only when a date is set.

The copy, on voice:

> **The main date**
> Shown at the top of the shared timeline and used for the countdown. Hide it
> and the date is removed from the page itself, not just from view. Your own
> plan keeps it.

and on success:

> The main date is hidden. The shared page no longer carries it.

When there is no main date the card reads "No main date on the shared page",
so the absence is stated rather than silent.

**Proven.**

```
✔ E06.06 · hiding the main date removes the key from the published payload
```

The fixture publishes with `primaryDate = 2027-08-14`, a date carried by no
milestone in the publication, so "the string is gone" means the main date and
nothing else. Before concealment the DTO carries
`{ label: "The day", date: "2027-08-14" }`. After `setAudiencePrimaryDate(null,
null)` and a link rotation — a fresh token, so the per-request cache around
`resolveAudienceTimeline` cannot return the pre-concealment DTO — the assertions
are that `"primaryDate" in dto` is false, that the serialised payload does not
contain `2027-08-14`, and that it does not contain `"The day"`.

### 3. A half-set pair never publishes a partial date — **MET**

`setAudiencePrimaryDate` treats a missing label or a missing date as
concealment:

```ts
const conceal = !input.primaryDate || !input.primaryDateLabel;
```

This matters because the DTO only emits `primaryDate` when both columns are
present (`audience-timeline.ts:819-826`). Writing one without the other would
look like a change in the form and do nothing on the page.

```
✔ E06.06 · a half-set pair conceals rather than publishing a partial date
```

Submitting `primaryDateLabel: "The day"` with `primaryDate: null` returns
`"concealed"` and the resolved DTO carries no `primaryDate` key.

### 4. Owner-scoped — **MET**

```
✔ E06.06 · concealment is owner-scoped: another workspace cannot touch it
```

`Publication not found`, the same message and the same `ownsPublication` guard
that publish, rotate, revoke and unpublish use. The action layer additionally
resolves the workspace from the signed-in owner before the id is trusted.

### 5. Location, stated plainly — **MET as a refusal**

**There is no location field anywhere in the published model.** Verified by
reading `src/server/db/schema.ts` (the `workspaces` and `tasks` tables) and
`src/modules/timeline/server/db/timeline-schema.ts`: no location column on
`workspaces`, on `tasks`, on `node_overlays`, on `timeline_publications` or on
`timeline_publication_items`.

So a location on a couple's page is text the couple typed — into a milestone
title, into the publication label, or into their own workspace name.

**The refusal, and why it is the right answer for 1 September.** A "hide the
location" toggle would be a control whose label promises something the data
cannot deliver: it would have nothing to hide, because there is no location to
hide, while the venue name in a milestone title would stay published. Shipping
that toggle would be worse than shipping nothing, because the couple would
believe it worked.

**What the couple actually has**, and what E12.07 should say in their words:
every published title is theirs to edit after publishing without touching their
private plan, and the main date is theirs to remove. Anything they do not want
on the page, they take out of the words. That is true today.

**Not built, named as not built:** a structured location field, a venue-address
field, a "hide venue" toggle, and any automatic detection of a place name in
free text. If a structured field is wanted later it is a Timeline schema change
and inherits E06.02's migration blocker.

### 6. Concealed values never reach the social preview — **MET**

`/s/[token]` builds its title, description and OpenGraph card from
`dto.label` and `dto.audienceKind` only (`src/app/s/[token]/page.tsx:23-36`).
Not from `primaryDate`. Not from `ownerDisplayLabel`.

```
✔ E06.06 · the shared page's social preview carries no concealable value
```

A source contract test asserting the file references neither `primaryDate` nor
`ownerDisplayLabel`, plus a positive assertion that
`robots: { index: false, follow: false, noarchive: true, nosnippet: true }` is
still there, so a widening is loud. This is a source-text assertion and is
recorded as one: it proves the metadata builder cannot reference the fields, not
that a rendered unfurl was inspected.

**Scope note, so this is not over-read.** This criterion is proven for `/s`.
The `/p` OpenGraph card (`src/app/p/[slug]/page.tsx:21-59`) builds from the
workspace name and its domain label, which is a different surface with a
different owner: E06.05 for the indexing posture, E06.12 for the social-preview
QA. R-024's rule — venue branding is the venue name only, including in
OpenGraph descriptions — is satisfied on `/s` trivially, because no venue value
appears in its metadata at all.

### 7. EXIF GPS, cross-referenced — **MET as a statement of position**

No photograph reaches any public surface today. `attachments` is in
`FORBIDDEN_KEYS` (`lib/audience-timeline.ts:69`), `ITEM_KEYS` has no image key,
and the only attachment read path in the app,
`src/app/api/attachments/[id]/route.ts`, re-checks authentication before
streaming a byte. Bytes are written with `access: "private"`
(`src/server/storage.ts`).

So there is no metadata channel to leak a concealed location through, and **this
document makes no claim that EXIF is handled, because nothing strips it.** When
E06.03 opens a public byte path, EXIF stripping — GPS and capture time included
— becomes a precondition of this criterion rather than a nicety, and the
concealment promise here becomes dependent on it.

## What is not done

- A structured location field. Deliberately refused, with the reasoning above.
- EXIF stripping. Belongs to E06.03 and blocks nothing today because no
  photograph is public.
- An equivalent main-date control on `/p`, if the founder decides the couple's
  keepsake lives there. Recorded, not assumed.
- No end-to-end browser assertion of the new owner control. The server function,
  the action and the payload are proven; the button was not clicked in
  Playwright. Stated rather than implied.
