# E06.03 — the photograph boundary, and what is not wired to it

Evidence for E06.03. Written 2026-08-03 in worktree `_wt-wp14` (app, branch
`claude/wp14-timeline`, stacked on `claude/wp08-couple`). Acceptance criteria
were written before the audit. Every claim carries a path and a line as it
stands in that worktree, or a command and its real output.

---

## The headline in one paragraph

The privacy-critical half of E06.03 is built and tested: a photograph's GPS,
capture time, orientation and free-text comments are read and then removed,
and a photograph that still carries any of them is refused publication. The
product half is not wired, and it cannot be wired from this branch: the secure
upload path E08.07 delivered lives on `claude/wp07-engineering`, the DTO has no
`image` key, and the Timeline database has no receipt-backed migration runner
to add the columns that would hold orientation, alt text and dimensions. What
is built is the piece the audit said to build first, and the pieces that are
missing are named below rather than implied.

## 1. Criterion by criterion

### C1 — GPS, capture time and orientation are read, then removed — **MET**

`src/lib/image/metadata.ts`. `inspectImage` parses JPEG segments and PNG chunks
and reads the TIFF stream that carries EXIF, following the IFD0 chain into the
Exif SubIFD, looking for orientation (`0x0112`), the GPS IFD pointer (`0x8825`)
and the three date tags (`0x0132`, `0x9003`, `0x9004`).

Proven on a round trip, not by reading. The test builds a JPEG byte by byte
carrying an EXIF APP1 with orientation 6, a `DateTime` of `2026:08:03 12:00:00`
and a GPS IFD, plus a `COM` comment reading "Taken at home".

```
✔ a phone photograph's GPS, capture time and orientation are all read before anything is removed
✔ a GPS-bearing JPEG comes out clean: no EXIF, no GPS, no capture time, no comment
```

The second test asserts the negative twice over: `inspectImage` on the output
reports `hasExif: false`, `hasGps: false`, `hasCaptureTime: false` and an empty
`metadataSegments`; and the raw byte stream, read as latin1, no longer contains
the literal strings `Exif`, `Taken at home` or `2026:08:03`. Parsing something
as absent and it actually being gone are different claims, so both are made.

The same is proven for PNG, where EXIF arrives in an `eXIf` chunk and captions
arrive in `tEXt`:

```
✔ a PNG's eXIf and tEXt chunks are removed and the image chunks are left alone
```

That test also asserts `sRGB`, `IDAT` and `IEND` survive, so the file still
renders after the strip.

### C2 — orientation survives the segment that carried it — **MET**

```
✔ orientation survives as a value after the segment that carried it is gone
```

`stripImageMetadata` returns `orientation: 6`, `orientationSwapsAxes` returns
true and `orientationTransform` returns `rotate(90deg)`, while `inspectImage`
on the stripped bytes returns `orientation: null`. That pair is the whole
mechanism: the file no longer describes itself, and the caller still knows
which way up it goes.

**This caught a defect in my own API and it is worth recording.** The first
version of `decidePhotograph` read orientation out of the bytes it was given.
Since it is only ever given *stripped* bytes, it always read null, and every
portrait photograph would have reserved a landscape box on the public page.
The test failed, the signature changed to take orientation as a parameter, and
a regression assertion now pins the failure mode:

```ts
// And the regression this API shape exists to prevent: forget to pass the
// orientation on and a portrait photograph silently reserves a landscape box.
const forgotten = decidePhotograph(strip.bytes);
assert.equal(forgotten.displayWidth, 1600);
```

### C3 — format support is an allowlist, and refusal is the point — **MET**

JPEG and PNG only, because those are the two formats this module can prove it
has cleaned. WebP carries its own `EXIF` and `XMP ` chunks that it does not
handle, so a WebP is refused rather than passed through unexamined. Same for
HEIC, an empty buffer, and a truncated JPEG.

```
✔ a format whose metadata cannot be proven removed is refused, not passed through
✔ a truncated JPEG is refused rather than half-parsed
```

This is the same rule E08.07 applied to MIME types: a format nobody thought of
is refused too.

### C4 — stripping never touches a pixel — **MET**

```
✔ stripping removes description and never a pixel
```

Intrinsic dimensions are identical before and after, the trailing entropy-coded
bytes are asserted byte-identical, and the output is strictly smaller. The
implementation copies everything from the SOS marker onward verbatim and drops
whole PNG chunks, so every surviving chunk keeps its own CRC. That is why this
needs no image library and cannot lose quality.

Segments deliberately **kept**: JPEG `APP0` (JFIF density) and `APP2` (ICC
colour profile), and PNG `sRGB`, `gAMA`, `iCCP`. None describes a person or a
place, and dropping ICC visibly shifts colour.

### C5 — the numbers exist as numbers — **MET**

`src/lib/image/policy.ts`:

| Constant | Value |
|---|---|
| `PUBLISHED_MAX_LONG_EDGE_PX` | 2000 |
| `PUBLISHED_MIN_LONG_EDGE_PX` | 800 |
| `PUBLISHED_TARGET_BYTES` | 512,000 (500 KB) |
| `PUBLISHED_MAX_BYTES` | 2,097,152 (2 MB) |
| `ALT_TEXT_MAX_LENGTH` | 200 |
| `PUBLISHED_IMAGE_MIME_TYPES` | `image/jpeg`, `image/png` |

```
✔ the stated dimension bounds are the ones enforced
```

The test drives the bounds from the exported constants rather than restating
them, so changing a number changes the test's meaning rather than breaking it
silently.

### C6 — alt text, three outcomes, no filename — **MET**

```
✔ alt text never falls back to a filename
✔ a photograph with no description is decorative, and decorative means an empty alt attribute
✔ a description the couple wrote is kept, and an overlong one is refused
```

`IMG_4183.JPG`, `DSC00214.jpeg` and `photo 3.png` are all refused as filenames.
`altAttribute` returns `""` and never `undefined`, because an `<img>` with no
alt attribute is announced by its `src`, which is the outcome the rule exists
to prevent. A filename read aloud also leaks the couple's camera-roll
numbering onto a public page.

### C7 — a caller that forgets to strip is refused — **MET**

```
✔ bytes that still carry metadata are refused publication outright
```

`decidePhotograph` on un-stripped bytes returns `{ publishable: false, reason:
"metadata-present" }`. The check is in the policy rather than trusted to the
caller because a photograph reaching a public page with its GPS intact is the
failure the module exists to prevent, and "the caller will remember" is not a
control.

### C8 — no face detection, no auto-tagging, no face grouping — **MET**

```
$ grep -rniE "face|detect|recognit|smart.?crop|autotag|auto-tag" src/lib/image/
src/lib/image/metadata.ts:11: * reaches a public surface until its description has been removed from it.
src/lib/image/metadata.ts:76:// ── format detection ──────────────────────────────────────────────────
src/lib/image/metadata.ts:80:function detect(bytes: Uint8Array): SupportedImageFormat | null {
src/lib/image/metadata.ts:479:  const format = detect(bytes);
```

Four matches, verbatim. One is "face" inside "surface"; three are **format**
detection, which reads the first three bytes of a file to tell a JPEG from a
PNG. No face detection, no recognition, no tagging and no smart crop exists.
D-033's standing no is honoured by absence, which is the only way to honour it.
The grep is reported in full rather than filtered, because a filtered grep is
the shape of a claim nobody can re-run.

### C10 — what is not built, stated — **MET, and this is the important section**

**Not built, and why:**

1. **Wiring into the upload action.** This tree still has the old denylist path
   at `src/server/actions/attachments.ts:36`. E08.07's `upload-validation.ts`
   is on `claude/wp07-engineering` and is not here. Adding the strip to the old
   path would either be discarded on merge or conflict with it. The seam is
   left clean and the wiring is one call, at the point where E08.07's
   `validateUpload` returns and before `.insert(attachments)`.
2. **A public image path.** No attachment is publicly readable today, by
   design. Making one readable is the exposure decision in the spec, and it is
   not reversible once couples have shared links.
3. **Crop.** Nothing exists. A crop that runs in the browser and re-encodes
   through a canvas would also strip metadata as a side effect, which makes it
   attractive, but it moves the privacy control client-side where it can be
   bypassed. The server-side strip has to stay regardless.
4. **Server-side re-compression.** There is no image library. Adding one is a
   dependency decision on a serverless platform, not a line of code. Until
   then the byte and dimension ceilings are enforced by **refusal**, not by
   correction: a couple uploading a 12-megapixel photograph is told no rather
   than being helped. That is a worse experience and it is recorded as a
   deliberate trade, not hidden.
5. **Columns for orientation, alt text and display dimensions.** The Timeline
   database ledger `drizzle-timeline/` holds one file,
   `0000_timeline_baseline.sql`, and `scripts/db/migrate.mjs:465` reads
   `TASKS_DATABASE_URL` only, so the receipt-backed runner does not reach it.
   No column can be added safely until that path exists or another is agreed.

**Also not claimed:**

- No statement is made that any file has been scanned for malware. E08.07
  deferred that deliberately and nothing here changes it.
- No statement about legal or regulatory compliance (D-016).

## 3. One honest failure, reported

The first run of this test file was **12 pass, 1 fail**. The failing test was
"a portrait photograph reports swapped display dimensions", and the fault was
in the code, not the test: `decidePhotograph` read orientation from bytes that
by definition no longer carried it. The API signature changed and a regression
assertion was added. It is recorded because a first-run-green test file is
usually a test file that asserts what the code already does.
