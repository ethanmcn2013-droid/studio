## 0. The audit, before any design

E08.07's title names four things. Three of them existed in some form and one
does not exist at all. Reported in that shape rather than as a checklist.

| Title element | What was actually there on 2026-08-03 |
|---|---|
| file validation | A **denylist of eight MIME types**, checked against the client-supplied `file.type` string. Nothing read the file. |
| malware controls | **Nothing.** No scanner, no service, no quarantine. |
| size limits | Real and correct. Tier-driven quota plus a 50 MB server-action ceiling, with claim-then-verify so the usage SUM is atomic. Kept unchanged. |
| private storage | Written `access: "private"`, then **served by 302-redirecting the browser to the private URL** — which cannot work. And the store is not provisioned, so nothing is stored at all. |

### The production storage backend, reported honestly

`src/server/storage.ts` `chooseBackend()`:

1. `BLOB_READ_WRITE_TOKEN` set → Vercel Blob;
2. not on Vercel → local disk;
3. **on Vercel with no token → `putBytes` throws.**

`studio/content/hq/operator-todos/premium-blob-storage.md` reads
`status: open`, `priority: P1`, `blocking: true`. The token has not been
provisioned.

**Therefore: attachment upload is broken in production right now.** Every
upload on `app.signalstudio.ie` hits branch 3 and throws "Storage not
configured". This is not caused by this task and is not fixed by it — it is a
founder action. It is recorded here because E08.07 cannot honestly report on
"private storage" without saying that there is currently no storage.

## 1. Criterion-by-criterion

### C1 — allowlist, with refusal by absence

`src/lib/upload-validation.ts`. Thirteen accepted types. Ten types are proven
refused — `image/svg+xml`, `text/html`, `application/xhtml+xml`,
`application/xml`, `text/xml`, `application/x-msdownload`,
`text/x-shellscript`, `application/octet-stream`, `application/javascript`,
`application/x-httpd-php` — and the test asserts each is refused **because it is
not on the list**, not because it is on a block list. That distinction is the
whole point: a type nobody thought of is refused too.

Proof: `src/server/attachment-upload-security.test.ts` → "refuses SVG, HTML and
XML by ABSENCE, which is what an allowlist means".

### C2 — the bytes decide, not the label

The exact bypass the old denylist had, tested directly: HTML content declared as
`image/png`. Under the old rule it passed, because `image/png` was not on the
block list and nothing opened the file. It is now `content-mismatch`.

Also tested: an SVG claiming `image/png`; a Windows `MZ` executable claiming
`application/pdf`; a JPEG claiming `image/png`; and a RIFF/AVI container
claiming `image/webp`, which checks that the four wildcard bytes in the WebP
signature have not turned every RIFF file into a WebP.

### C3 — the stored type is the validated type

`const mimeType = verdict.mimeType;` in `uploadAttachmentAction`. This matters
because `GET /api/attachments/[id]` serves `att.mimeType` as `Content-Type`. If
the raw client string reached the database, the uploader would be choosing how
every future viewer's browser treats their file.

### C4 — refused before the row is claimed

A source-contract test compares the offset of `validateUpload(` against
`.insert(attachments)` and fails if validation moves after the claim.

### C5 — no invented signatures

`text/plain`, `text/csv` and `text/markdown` have no dependable magic number.
They return `sniffed: "no-signature"` rather than `"matched"`. HTML source
uploaded as `text/plain` is **accepted**, and that is correct rather than a
hole: it is stored as `text/plain` and served as `text/plain` with `nosniff` and
`default-src 'none'; sandbox`, so the browser renders it as text.

### C6 — private blobs are streamed, not redirected

This was a latent production defect and it is the substantive fix in E08.07.

`putBytes` writes with `access: "private"`. Verified from the installed
package's own type declarations, `@vercel/blob@2.6.1`:

> `'private': The blob requires authentication to access.`

and `get()` documents that "The authorization header is automatically set" from
`BLOB_READ_WRITE_TOKEN`. A browser has no such token. The route's
`Response.redirect(url, 302)` therefore sent the user to a URL they could not
open.

It had never fired **because the store is not provisioned** — so it would have
fired on the day the founder provisioned it, which is the worst possible day to
discover it. `ServeResult.kind` is now `"blob"` rather than `"redirect"`, and
`openBlobStream()` streams through the route after the workspace check.

A test asserts `Response.redirect` is absent, `openBlobStream(` is present, and
that `put` and `get` **agree** on `access: "private"` — a mismatch would either
make every attachment world-readable or make every download 404.

### C7 — security headers on every backend

`nosniff`, `default-src 'none'; sandbox; frame-ancestors 'none'`, and
`Cache-Control: private, no-store`. The redirect branch used to discard all
three for blob-backed files. There is now **exactly one** `Response` and one
header block, and the test counts the header occurrences so a future branch
cannot route around them.

### C8 — 404, never 403

Unchanged and re-asserted: `att.workspaceId !== ws` returns `notFound()`, and
`status: 403` appears nowhere.

### C9 — what is not built, stated

See §0 and §2.

## 2. Malware controls: priced, not pretended

There is no scanning in this stack and the budget is zero (D-015 Q5). Rather
than tick the box, here is what it would take.

| Option | Cost | Fit |
|---|---|---|
| ClamAV in a container alongside the app | no licence fee; needs a long-running host with ~1 GB RAM for signatures. **Vercel serverless functions cannot host it.** So it means a second piece of infrastructure to run and patch. | Poor for a sole founder 29 days from release. |
| A scanning API (VirusTotal, Cloudmersive and similar) | per-scan pricing, and **the file is sent to a third party**. For a couple's wedding paperwork that is a new processor, a new DPA and a new disclosure. | Poor: it converts an engineering gap into a privacy one. |
| Scan on download rather than on upload | same services, same problems, later. | No better. |

**Recommendation: defer, with the exposure recorded and a named trigger.** The
compensating controls that do exist are real and are now tested: an allowlist
checked against bytes, a stored type that cannot be chosen by the uploader,
`nosniff` plus a sandbox CSP on every response, and no execution surface — the
files are downloaded, never run by Signal Studio.

Trigger to revisit: the first venue that asks about it in writing, or the first
upload of a file type outside the current allowlist.

**Nothing in the product says or implies a file has been scanned.**

## 4. What this evidence does not claim

- **It does not claim uploads work in production.** They do not; the blob store
  is unprovisioned and `putBytes` throws.
- **The private-blob streaming fix is verified statically only** — source
  contract plus the SDK's own type declarations. No blob store exists to
  exercise it against. It should be smoke-tested the day the token is
  provisioned, before Cohort 1.
- **It does not claim any file has been scanned for malware.**
- **`.docx`, `.xlsx`, `.pptx` and `.zip` are indistinguishable by leading
  bytes** — all four are ZIP containers. The allowlist accepts a ZIP archive
  under any of those four declared types. Deeper inspection would mean parsing
  the archive's central directory, which is a larger change than this task.
- No statement is made about legal or regulatory compliance (D-016).
