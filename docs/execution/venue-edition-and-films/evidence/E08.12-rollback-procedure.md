# E08.12 — rollback procedure

**Task:** E08.12 · **Written:** 2026-08-03
**Operator:** Ethan McNamara, alone, probably at night.

Read this before a release, not during one.

---

## The one thing to understand first

**Code rolls back in a minute. Data does not roll back at all.**

Three things ship in a release and they have three different rollback stories:

| Layer | Reversible? | Time |
|---|---|---|
| Code (a Vercel deployment) | Yes, cleanly | ~2 minutes |
| Configuration (environment variables) | Yes, but needs a redeploy to take effect | ~5 minutes |
| Schema and data (a migration) | **No.** Forward-only. | see §3 |

So the decision order is always: **configuration first, code second, schema
never** — unless you have exhausted the first two and the alternative is worse.

---

## §1 · Decide, in under two minutes

Answer these in order and stop at the first yes.

1. **Is couple data being disclosed to someone who should not see it?**
   → This is not a rollback. Go to `E08.12-incident-response-runbook.md` §2.
   Contain first, roll back second.

2. **Is the site down, or is a core path broken for everyone?**
   → §2, promote the previous deployment. Do it now, diagnose after.

3. **Is one feature broken, with everything else working?**
   → §4, configuration or a forward fix. Rolling the whole deploy back to fix
   one surface trades a small failure for a large one.

4. **Is the schema wrong?**
   → §3. Slow down. This is the only step that can make things permanently
   worse.

---

## §2 · Roll back the code

Vercel keeps every deployment. Promoting a previous one is the fastest safe
action available and it does not touch the database.

```bash
vercel ls                                   # find the last known-good deployment
vercel inspect <deployment-url>             # confirm the commit sha is what you think
vercel promote <deployment-url> --scope=<team>
```

Then, immediately:

- [ ] Reload the production URL in incognito. Confirm the failure is gone.
- [ ] Confirm you promoted the **right** repository. `app` and `studio` are two
      projects and a broken `/venues` page is studio, not app.
- [ ] If the release included a migration, **the old code is now running against
      the new schema.** That is usually fine because every migration in this
      repository is additive by policy — but confirm it against §3 before you
      walk away.

**Time budget: 2 minutes.** If it takes longer than five, you are debugging, not
rolling back. Promote and debug afterwards.

## §3 · The schema, which does not roll back

**There is no down migration in this repository and that is deliberate.** The
migration runner is forward-only and receipt-backed. `drizzle-kit migrate` and
`drizzle-kit push` must never touch production; the historical `0000`–`0013`
chain is non-idempotent and running it again damages the database.

### What that means in practice

Every migration in this project is written to be **additive**: new nullable
columns, new tables, new indexes. Migration `0027` is the model — it adds
`token_hash` and `token_scheme` and a unique index, modifies no existing row,
and leaves every existing share link resolving through a fenced legacy branch.
Old code runs against the new schema without noticing.

So the rollback for a bad migration is almost never "undo the migration". It is:

1. **Promote the previous deployment** (§2). Additive schema means the old code
   still works.
2. **Write a forward migration** that corrects the problem, with its own
   receipt, tested against an isolated copy.
3. Ship that.

### When the data itself is wrong

If a migration or a backfill wrote wrong values — not wrong structure — restore
is the tool, and it costs everything written since the backup.

```bash
# 1. Confirm the backup you intend to use actually restores. Never skip this.
node scripts/db/restore-verify.mjs --backup=<path>

# 2. Understand exactly what you are about to lose: everything between the
#    backup timestamp and now. Write that window down before you proceed.

# 3. Restore. This is the point of no return.
node scripts/db/backup.mjs --restore=<path> --environment=production \
  --confirm-production=tasks

# 4. Prove the restored database is intact, not merely present.
node scripts/db/integrity-check.mjs --environment=production
```

**A restore that loses a couple's afternoon of wedding planning is a serious
event, not a technical step.** If any sponsored couple wrote to the product
inside the loss window, that is a communication obligation, not just an
operations one. Go to the incident runbook §4.

**Time budget: 30 minutes, and never under pressure.** If the choice is between
a wrong number in a report and losing a couple's work, live with the wrong
number until morning.

### The drill that proves this works

```bash
cd studio && pnpm recovery:drill
```

Last run 2026-08-03: PASSED in 1,665 ms. 5 rows across 15 tables restored and
re-verified **from the restored database**, 43 indexes and 2 triggers recreated,
append-only enforcement proven on the restored ledger rather than assumed. Run
it before you trust any of the above.

## §4 · Configuration rollback

Faster than a code rollback and often the right answer. Every one of these is a
single variable, and every one requires a **redeploy** to take effect — changing
it in the Vercel dashboard alone changes nothing already built.

| Symptom | Variable | Set it to |
|---|---|---|
| The site opened before you meant it to | `NEXT_PUBLIC_SIGNAL_LAUNCH_STATE` | `pre` — holds the site closed past `LAUNCH_AT` with no code change |
| The CSP is blocking a real surface | `SIGNAL_ENFORCE_CSP` | unset — drops back to Report-Only |
| Rate limiting is blocking legitimate use | `UPSTASH_REDIS_REST_URL` | unset — the limiter becomes a no-op that allows. **Understand what you are turning off.** |
| Venue metrics roll-up is 401ing | `PARTNER_STATS_SECRET` | must be byte-identical in both projects |

- [ ] Change the variable
- [ ] **Redeploy.** Nothing takes effect without it.
- [ ] Verify in incognito.

## §5 · Rolling back a wrongly issued entitlement

Not a deploy problem, and the reason it is here is that it is the one that will
actually happen: a code issued to the wrong couple, or a founding number
assigned before payment cleared.

- A founding number is **withdrawn**, not deleted:
  `withdrawFoundingNumber` records the date and the reason in the audit ledger
  and returns the place to the pool. There is no path that silently reassigns a
  number, and there must never be — two venues told they hold 07/25 is the one
  failure that cannot be walked back.
- The audit ledger is **append-only at the database level**, enforced by
  triggers. You cannot quietly edit history, and you should not want to.
- A couple's access is **never shortened** to correct an administrative error.
  D-020 point 2 and D-022 are both one-directional: access can move later, never
  earlier. If a code was issued in error, the correction is a conversation, not
  a revocation.

## §6 · The rehearsal this document has not had

**The `data` release gate requires the rollback to have been executed once
against a staging deploy. It has not been.**

Nothing in this document has been run against a real deployment. The recovery
drill has (§3), and the migration contract gate has (19/19), but promoting a
deployment and confirming the site returns has not been rehearsed by anyone.

The rehearsal is short and it is the founder's to run:

1. Deploy any commit to a preview or staging target.
2. Deploy a second one.
3. `vercel promote` the first.
4. Confirm in incognito that the site serves the first again.
5. Write down what took longer than expected. It always is step 3.

Until that is done, this is a procedure and not a proven one, and this document
says so rather than implying otherwise.
