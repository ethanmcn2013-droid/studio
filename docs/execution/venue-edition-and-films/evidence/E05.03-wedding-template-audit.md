## 1. Where the template lives, and the trap

**`src/lib/templates.generated.ts` is a build artifact.** Its own banner says
so at `:1-4`.

| | Path |
|---|---|
| Canonical source | `studio/src/lib/templates/wedding-planning-workspace/` (`meta.ts`, `tasks.ts`, `notes.ts`, `roadmap.ts`, `analytics.ts`, `index.ts`) |
| Generator | `scripts/sync-templates.ts`, npm script `pnpm sync:templates` |
| Output | `src/lib/templates.generated.ts`, committed so Vercel does not need the studio repo |

`scripts/sync-templates.ts:20` resolves the source as
`resolve(__dirname, "../../studio/src/lib/templates")`. From
`_wt-wp08/scripts` that is `C:/Users/ethan/signal-studio-workspace/studio/src/lib/templates`,
**the live studio working tree**, which the shared brief forbids this package
from editing and which carries another lane's uncommitted work.

**Four traps a later build agent must know.**

1. **WP-08 has no studio worktree.** Any change to template CONTENT belongs in
   `studio/src/lib/templates/wedding-planning-workspace/tasks.ts` and cannot be
   made from here. Hand-editing the generated file would be reverted by the
   next `pnpm sync:templates`.
2. **The generator reads the live studio tree**, so running `pnpm sync:templates`
   in this worktree would pull in whatever is dirty over there.
3. **The committed artifact has already been hand-edited and no longer matches
   its own generator.** `src/lib/templates.generated.ts:1` reads
   `// AUTO-GENERATED, do not edit by hand.` while `scripts/sync-templates.ts:62`
   emits `// AUTO-GENERATED — do not edit by hand.` (em dash). Proof that hand
   edits happen and that re-running the generator reverts them.
4. **`src/modules/timeline/lib/templates.generated.ts` wears the same banner and
   has no generator.** `sync-templates.ts:79` writes only
   `src/lib/templates.generated.ts`. No script in the repo writes the Timeline
   one. It is hand-maintained under a generated file's banner.

**Consequence for this task, stated plainly.** E05.03 splits in two. The
*mechanism* (can a template express a milestone and a real date at all) is
entirely app-side and was built here. The *content* (which tasks, in whose
voice, and what happens to the dietary task) is canonical-source work plus a
founder decision, and was deliberately not done here.

### 2a. Is it restrained? No.

The criterion I used: **a template is restrained when everything it puts in
front of the couple on day one is something they can act on this month, and
nothing on the board is a claim about work the couple did not do.**

Against that, six findings.

1. **Two tasks arrive already `done`.** "Venue contract and deposit schedule
   recorded" and "Ceremony room layout agreed with venue"
   (`templates.generated.ts:17,26`). A couple who redeems on the day they book
   opens a board where two things they have not done are ticked off. One of
   them, the ceremony room layout, is usually months away.
2. **Zero milestones**, so the Timeline renders empty. Section 3.
3. **Zero real dates.** Only 4 of 18 tasks carry a `due`, and the values are
   `"Today"`, `"Tomorrow"`, `"Fri"`, `"Fri"`. `apply-template.ts` wrote
   `due: t.due` verbatim and never `dueAt`. The board is frozen at whatever day
   the copy was written.
4. **The voice is a coordinator's, not a couple's.** "Review seating chart with
   venue", "Build supplier contact sheet", "Write one-page update for couple and
   suppliers". `studio/.../meta.ts:15` states the audience outright:
   `audience: "wedding-planner"`. The sponsored couple is not the planner.
   `billing.tsx:98` repeats the error on the pricing card ("12 months of editing
   for the planner").
5. **Eighteen tasks is not the problem on its own; the mix is.** Eleven of the
   18 sit in `todo` with no date and no priority above p1, which is a list, not
   a next action. The brief's own bar, "the eight that actually matter first",
   is a real improvement over this.
6. **One task is an open Article 9 question.** Section 4.

**Verdict: the shipped wedding template is not restrained, and it is not
addressed to the couple.** It is a competent planner's checklist that was
repurposed as a couple's starting point.

## 3. The gap that was built

Two facts made the mechanism the right thing to build rather than new copy.

- Timeline's milestone source requires `t.is_milestone = 1` and orders by
  `t.due_at` (`src/modules/timeline/server/sync/tasks-milestone-source.ts:120-141`).
- Signal's briefing reads `t.due_at`
  (`src/modules/signal/lib/briefing/tasks-db-source.ts:114`).

A template could not set either. So "restrained milestones", the words in
E05.03's own title, were not expressible.

### 3a. Files changed, all inside `_wt-wp08`

| File | Change |
|---|---|
| `src/lib/template-anchor.ts` | **New, pure.** `parseAnchorDate`, `resolveTemplateDueAt`, `templateMilestoneCount`. |
| `src/lib/templates.ts` | `TemplateTaskInput` gains optional `milestone?: boolean` and `dueOffsetDays?: number`. |
| `src/server/db/apply-template.ts` | Reads the workspace's `primary_date` as the anchor, writes `tasks.is_milestone` and a real `tasks.due_at`. Third argument `options.anchorDate` lets a caller supply the date directly. |
| `src/server/actions/templates.ts` | The remix path carries `isMilestone` for parity. A remix has no anchor, so `due_at` stays null. |
| `scripts/sync-templates.ts` | Type documents the two new pass-through fields. The generator already copies the whole task object, so a studio-side declaration reaches the app with no further change here. |
| `src/lib/template-anchor.test.ts` | **New.** 9 tests. |
| `src/lib/wedding-template-contract.test.ts` | **New.** 6 tests: the R-017 forward guard, the restraint bar, and four audit pins. |
| `package.json` | Both suites added to the `test` chain. |

### 3b. The load-bearing refusal

With **no anchor date there is no due date**. `resolveTemplateDueAt` does not
fall back to "days from now". A wedding template's dates are relative to the
wedding, not to the day the couple happened to redeem. Signal builds the
couple's briefing from `due_at` and Timeline orders milestones by it, so a
now-relative date would surface as a deadline nobody set. This is asserted by
the test named "NO ANCHOR MEANS NO DUE DATE. It never falls back to
days-from-now".

The anchor column already exists: `workspaces.primary_date`
(`src/server/db/schema.ts:308`), which the contextual onboarding flow already
populates from a field labelled "Wedding date"
(`src/components/welcome/contextual-onboarding.tsx:383`). **No migration was
needed and none was written.**

### 3c. Behaviour is unchanged until content declares the new fields

No shipped template sets `milestone` or `dueOffsetDays`. So today every seeded
task gets `is_milestone = false` (the column default,
`src/server/db/schema.ts:140`) and `due_at = null`, which is byte-for-byte
what the code did before. The capability is inert until the founder approves
content, which is the correct posture for a task whose content is undecided.

## 4. R-017, handled exactly as instructed

**Not designed away. Not silently deleted. Guarded and put to the founder.**

**Inventory, run today.** `grep -rn "Collect final dietary notes"` across the
whole app repo returns **two** lines: `src/lib/templates.generated.ts:108`
(production) and `src/lib/wedding-template-contract.test.ts:54` (the ledger I
added). The canonical source is
`studio/src/lib/templates/wedding-planning-workspace/tasks.ts:69`.

**The prior audit's cost estimate is wrong, and this matters.** It states
"Nine touchpoints, and `suite-navigation-contract.test.mjs:428,459` asserts the
exact string, so removing it fails the suite". The contract test asserts a
**different** sentence at `:464` and `:495`, "Confirm the final dietary list
before the venue team locks the service notes", which is Notes and Tasks demo
fixture copy (`src/modules/notes/server/demo/notes-demo.ts:57`,
`src/server/demo/tasks-demo.ts:76`, `experience/cross-suite-journey.json:30`).
Two different strings were conflated. Verified by running the suite: 41 pass,
0 fail, with the template string present.

**So removing the template task is a one-line change in the canonical source
plus a re-sync, and it breaks no test.** The reason it has not been made is
that it is a product decision, not that it is expensive.

**What was built instead: a forward guard.**
`src/lib/wedding-template-contract.test.ts` fails when a task whose title
matches a special-category pattern (dietary, allergy, accessibility, medical,
medication, wheelchair, pregnancy, religion) is added to the wedding template
and is not on a reviewed ledger. The ledger currently holds one entry, marked
open, with a comment stating that adding a title to clear the test is not the
fix.

**Fail-before proof.** With `"Collect final dietary notes"` temporarily
replaced by `"Ask guests about allergies and accessibility needs"` plus
`milestone: true, dueOffsetDays: -30`:

```

  AssertionError: Unreviewed special-category task(s) in the wedding template:
  Ask guests about allergies and accessibility needs. This is R-017.

✖ audit pin (E05.03): no task carries a wedding-relative due offset
```

The file was restored (`git diff --stat src/lib/templates.generated.ts` empty)
and the suite is 6/6 green. The run also proved the two new fields survive the
whole path from the generated file into `getTemplate`.

**The founder decision is in the packet.** Three options with trade-offs, plus
the questions. E05.03 does not pre-empt E03.01's role map.

## 8. A process hazard found during this session, recorded because it will recur

`_wt-wp08` is **not a single-agent worktree.** During this session, files
appeared in it from at least four other packages: `src/lib/tasks/anchor-due.ts`
(E05.06 shape), `src/modules/notes/lib/notes-copy.ts` (E05.04 shape),
`src/modules/timeline/server/unpublished-timeline-boundary.test.ts` (E05.08
shape), `src/server/venue-never-a-collaborator.test.ts` (E05.10 shape), plus
tracked edits to `src/lib/domain-context.tsx`, `src/app/invite/[token]/page.tsx`,
`src/components/app/tasks-runtime-shell.tsx` and two Notes files.

**Disclosure.** Before that was apparent, this session ran `git stash push -u`
once, to take a clean-tree typecheck baseline, and popped it about two minutes
later. The pop reported no conflict and every sibling file was present
afterwards. It was still an unsafe thing to do in a shared worktree and it was
not repeated. If a sibling package reports a lost edit around that window, this
is the first place to look.

**Recommendation to the orchestrator:** give each package its own worktree, or
state in the brief that the worktree is shared so agents do not run
tree-wide operations. Green gates are not obtainable from a shared worktree
while siblings are mid-flight, which means gate colour stops being evidence.
