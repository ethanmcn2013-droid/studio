### F-01 · `/p` publishes a couple's workspace to search engines · CRITICAL · OPEN

**Verified.** `app/src/app/robots.ts:14` disallows
`["/app", "/s", "/share", "/redeem", "/welcome", "/api"]`. `/p` is not in that
list. `app/src/app/p/[slug]/page.tsx` sets no `noindex` and its own comment
states the intent: server-rendered for indexing, a public page hit by crawlers
and social unfurls.

**Failure scenario.** A sponsored couple publishes their workspace. The
published payload carries task titles and tags, which for a wedding routinely
name suppliers, family members and guests. Those names become searchable, under
the couple's slug, next to the venue's name in the attribution footer. Nobody
in that list agreed to anything, and the couple was not told that publishing
means indexing.

**Why it is still open.** `/p` being indexable is a deliberate product choice
for the general product. Whether a *sponsored wedding* workspace should default
to it has never been decided. This is R-031, and it is a decision, not a bug.
The privacy documentation and the E03.01 role map both model every published
surface as token-bound and revocable, which is true of `/share/[token]` and `/s`
and is the opposite of true for `/p`.

**Recommendation.** Sponsored wedding workspaces publish to `/s` and
`/share/[token]` only. That removes the question rather than managing it, and
costs the couple nothing they asked for. If `/p` stays, it needs a `robots.ts`
entry, a `noindex`, and a sentence in the publish confirmation that says the
word "search".

**Deadline that matters.** Copy-freeze is 2026-08-21. If the decision lands
after it, the publish confirmation cannot be reworded.

### F-02 · Google Analytics runs on public pages with no consent gate · HIGH · OPEN

**Verified.** `app/src/app/layout.tsx:81` renders
`<GoogleTag enabled={process.env.VERCEL_ENV === "production"} />` on every route
except bare artifact paths. `app/src/components/analytics/google-tag.tsx:18`
carries its own admission: "No consent gate yet".

**Failure scenario.** A wedding guest follows a link to a couple's published
page and is measured by a third-party US analytics provider before being asked.
Under ePrivacy as transposed by SI 336/2011, consent is required for
non-strictly-necessary storage and access on a device. Analytics is not strictly
necessary. The exposure is not the couple's — it is every guest, supplier and
family member who clicks the link.

**This is R-032.** Recommendation: exclude `/p`, `/s`, `/share` and `/embed`
from third-party analytics regardless of what is decided about the marketing
site, because those pages carry other people's names. That is a one-line change
to the `enabled` condition and it does not require a consent banner.

### F-03 · `/embed` renders a couple's workspace inside any third-party page · MEDIUM · OPEN

**Verified in the headers, not only the route.**
`app/next.config.ts:136-149`: `/embed/:path*` is excluded from the global
`X-Frame-Options: DENY` by negative lookahead and receives the full security
header set **minus** XFO, with its CSP rewritten from `frame-ancestors 'none'`
to `frame-ancestors *`. The route resolves through the same
`getPublishedWorkspaceBySlug` path as `/p`, with no token. It is correctly
`noindex`.

**Failure scenario.** Anyone holding a slug renders a couple's published
workspace inside a page the couple has never seen. The couple gets no signal
that it happened and no way to stop it short of unpublishing entirely. For a
sponsored wedding artifact carrying guests' and suppliers' names, that is a
different proposition from a link the couple chose to share.

**This is R-033's redistribution half.** The framing decision is deliberate and
documented (AD-012: partner and venue pages iframe a live board). Whether
*sponsored wedding* workspaces are embeddable has not been decided.
Recommendation: no, by default, with a per-workspace opt-in if it is ever
wanted.

### F-04 · Share-link secrets are stored in plaintext in production · HIGH · REDUCED (fix built, not deployed)

**Verified.** Migration `drizzle/0027_share_link_token_hash.sql` adds
`token_hash` and `token_scheme` and a UNIQUE index over the hash.
`src/server/db/share-link-resolver.ts` hashes the guest secret before it touches
the database, matches on the unique index, and re-compares in constant time,
with a fenced legacy branch for rows the backfill has not moved.

**Two things were verified rather than assumed:**

1. **The `--> statement-breakpoint` trap did not recur.** The workspace has lost
   two cycles to a comment-only first segment silently running one statement.
   `0027` puts its comment block in the same segment as the first `ALTER`, and
   applying it as the runner does produces all three objects:

   ```
   segments: 3
     [0] "-- 0027 · share_links.token_hash + share…"
     [1] "ALTER TABLE share_links ADD COLUMN token…"
     [2] "CREATE UNIQUE INDEX uq_share_links_token…"
   columns: token,workspace_id,view,token_hash,token_scheme
   indexes: [{"name":"uq_share_links_token_hash","u":1}, …]
   ```

2. **The migration release gate accepts it.** `pnpm db:contract` → 19 tests,
   0 fail.

**Why it is reduced and not closed.** The migration has **not been applied to
production**, and `scripts/db/backfill-share-link-token-hashes.mjs` has never
run. Until both happen, every live share link is still a plaintext credential
sitting in a column, and a database read still discloses live access. Production
is what a couple touches. A branch is not.

### F-05 · One shared password opens every Signal HQ room · HIGH · REDUCED

**Verified, and the register is now out of date in a good way.**
`studio/src/lib/hq/auth.ts` was rewritten during this session. The v1 cookie was
`sha256("signal-hq-session:v1:" + password)` — derivable offline by anyone
holding the password, and an unsalted single-hash oracle *for* the password if
the cookie ever leaked. v2 is `v2.<issuedAtMs>.<hmac>` with a PBKDF2-SHA256
signing key and the issue time inside the signed token, so expiry is a server
fact.

**What is unchanged, and it is the part that matters.** It is still one shared
password. There is no per-person identity, no revocation of one holder without
rotating for everyone, and no audit trail that attributes an action to a named
person. The same password opens Today, Money, Company, Vault, Atlas, Decks,
Founders Circle and the Data Room.

**Failure scenario.** A venue is given "their" login and holds the founder's
entire operating surface. This is R-043 and the mitigation is a product
decision: E07.16 Option C — Signal HQ administers, the venue receives evidence
rather than a login. **No venue may be given this password.** No surface may
describe it as venue authentication.

### F-06 · Rate limiting fails open and may not be provisioned · MEDIUM · OPEN (operational)

**Verified.** `app/src/lib/ratelimit.ts:14-21` states its own design: when
`UPSTASH_REDIS_REST_URL` / `_TOKEN` are unset the limiter is a **no-op that
allows**, and when Redis errors at request time it **allows rather than 500s**.
Redemption is limited on two axes (`redeem-user`, `redeem-ip`) at
`src/server/actions/comp.ts:213,233`.

**Failure scenario.** If Upstash is not provisioned on the production Tasks
project, there is no rate limit on redemption, on share resolution, or on the AI
endpoints — silently, with no error and no log line saying so.

**The arithmetic that stops this being critical.** An invitation code body is 10
characters over a 31-symbol alphabet: 10 × log₂(31) = **49.5 bits**, and
`src/lib/comp-code.ts` asserts a 48-bit floor that fails the build if the length
or alphabet is reduced. 7.9 × 10¹⁴ combinations is not guessable online even
with no limiter at all. The limiter matters for cost and for the AI endpoints,
not for code guessing.

**Action:** confirm `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are
set on the production Tasks project before 1 September. It is on the HQ operator
ledger and needs no code change.

### F-07 · The Content-Security-Policy ships in Report-Only mode by default · MEDIUM · OPEN (configuration)

**Verified.** `app/next.config.ts:20` —
`const enforceCsp = process.env.SIGNAL_ENFORCE_CSP === "true"`. Every header
block picks `Content-Security-Policy` or `Content-Security-Policy-Report-Only`
off that flag. Unless the variable is set to the exact string `true` in
production, the CSP reports and blocks nothing.

This session cannot read production environment variables, so this is stated as
a question rather than a defect. It matters twice: an unenforced CSP is not a
control, and `/embed`'s comment notes that a browser only lets an **enforced**
`frame-ancestors` override `X-Frame-Options` — so the framing posture differs
depending on this flag.

**Action:** confirm `SIGNAL_ENFORCE_CSP=true` in production, or record
deliberately that the CSP is in report mode at launch.

### F-08 · The venue metrics roll-up applies no small-cell floor · MEDIUM · REDUCED

`reachedBoard` — a behavioural count of how many sponsored couples opened their
board — with no D-011 floor.

**Why it is reduced, not open.** The route is not venue-facing. Its only

couples would be told exactly how many of them opened the product. That is R-027
reproduced on a surface the R-027 fix never reached.

### F-09 · The shipped wedding template instructs couples to collect Article 9 data · CRITICAL · OPEN

**Verified.** `app/src/lib/templates.generated.ts:108` ships a "Collect final
dietary notes" task in the wedding template.

**Verified as NOT true:** there is no structured dietary field anywhere in the
schema, and `app/src/app/the-wedding/page.tsx:26` is marketing copy describing

health data to a venue. The original R-017 entry overstated this and was

**The real shape.** The private workspace is an unstructured store that will

**Not in this task's scope to fix**, and R-017 explicitly says not to design an
in-product venue flow for it. Recorded here because a production-readiness
review that omits it would be a reassurance document.

## 2. What holds up

Verified, and worth stating because a review that lists only problems is as
misleading as one that lists none.

| Control | Evidence |
|---|---|
| **Tenant isolation** | There is no database row-level security and the code says so in the first paragraph of `app/src/server/db/tenant.ts`: libSQL/SQLite has none, and the only thing separating workspace A from workspace B is a `WHERE workspace_id = ?` predicate. That is compensated by `byWorkspace()` throwing on an empty id, a static CI gate (`tenant-scope.test.mjs`) that fails when a scoped table is read without a predicate, and a cross-tenant negative suite. All green. |
| **Invitation-code entropy** | 49.5 bits, with a 48-bit floor asserted in a test that fails the build. The alphabet excludes `0/O` and `1/I/L` because a code gets dictated over a phone. Both repositories restate the numbers and both assert them. |
| **Share-token design** | 256-bit secret, sha256 at rest, UNIQUE index, constant-time compare, public id separated from the secret so visit counting never touches it. Tested against the real migration and the real resolver, not a hand-written approximation. |
| **Migration release gate** | `pnpm db:contract` → 19/19. Receipt-backed, ledger-hashed, fails closed on drift, on a wrong target, and on a rolled-back postcondition. |
| **Backup and restore** | `pnpm recovery:drill` → PASSED in 1,665 ms; 5 rows across 15 tables restored and re-verified from the restored database, 43 indexes and 2 triggers recreated, append-only enforcement proven **on the restored ledger** rather than assumed. |
| **Data integrity** | 27 integrity checks in app and 21 in studio, each proven to catch a specific corruption by creating it. |
| **Venue metrics privacy floor** | R-027's two-sided small-cell rule and R-028's branded rate type both landed in studio and are held by tests proven to fail on the old behaviour. |
