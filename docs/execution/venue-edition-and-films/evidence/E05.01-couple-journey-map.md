## 2. Step 4 loses the code, and this is provable from source

`src/app/sign-up/[[...sign-up]]/page.tsx` reads `redirect_url` at `:24-31`, but
only to resolve a sponsor name for a card. The value it hands Clerk is computed
independently:

```
:33  const preselected = segmentFromParam(sp.use);
:34  const welcomeUrl = buildWelcomeUrl(preselected);
:72  fallbackRedirectUrl={welcomeUrl}
:73  forceRedirectUrl={welcomeUrl}
```

`buildWelcomeUrl` never reads `sp.redirect_url`. So `/redeem/{code}` is never
passed to Clerk in any prop, and `forceRedirectUrl` is documented to take
precedence over the `redirect_url` query parameter. The couple lands on
`/welcome`.

**And `/welcome` does not redeem.** `src/app/welcome/page.tsx:58` calls
`detectVenueWelcome(me)`, which at `src/server/db/venue-welcome.ts:39-55`
queries the `entitlements` table for a row that the redemption would have
created. With no redemption there is no row, `venueWelcome` is null, the branch
at `:69-86` does not run, and the couple sees the generic segment picker with
no venue anywhere on it.

**Consequence.** On the source reading, a sponsored couple who follows the
venue's link never redeems the code, never gets the wedding template, and never
sees the venue's name after sign-up. The prior audit called this "needs a live
Clerk check; not provable read-only". The Clerk behaviour still needs one live
run, but the app-side half is now settled: the redeem path is not in any prop
Clerk receives, and `/welcome` has no fallback that redeems.

**Unverified, and stated as such:** whether Clerk honours the query parameter
over `forceRedirectUrl` in this version. One live sign-up against a real code
settles it. Nobody should plan on the answer being favourable.

## 3. The access term. This is the most serious finding in this document.

**D-022 is implemented, tested, and not connected to a couple.**

The ratified rule `max(redemption + 548 days, wedding date + 90 days)` is
implemented at `studio/src/lib/venue-edition.ts:100-121` (`coupleAccessExpiryMs`),
applied at `studio/src/lib/entitlements-db/codes.ts:252-267`
(`expiryForRedemption`) inside `redeemLicenseCode` at `:285`, with postponement
handled by `extendedCoupleAccessExpiryMs` at `codes.ts:635`.

**None of it runs.** `grep -rn "redeemLicenseCode|setCoupleWeddingDate" studio/src studio/scripts`
returns only `codes.test.ts` and one re-export at
`studio/src/lib/entitlements-db/index.ts:101`. `studio/src/lib/venue-lifecycle.ts`,
the whole lifecycle state machine, has exactly one importer:
`studio/src/lib/venue-lifecycle.test.ts`.

`codes.ts:29-34` says so in its own header: *"The public redeem WRITE lives in
the Tasks repo today; moving it here is gated on the
licensing-policy-ratification redemption ownership decision."*

**What actually runs** is `src/server/actions/comp.ts:215-217`:

```
const expiresAt = new Date(
  Date.now() + row.durationDays * 24 * 60 * 60 * 1000,
);
```

Flat. `row.durationDays` is 548, because `studio/scripts/issue-codes.ts:121-129`
still refuses any other value, which is the guard D-022 point 4 said to relax.

`grep -rniE "weddingdate|wedding_date|coupleAccessExpiry|venue-lifecycle|venue-edition" src/ scripts/ drizzle/`
across the entire app repo returns five hits, all of them the string
"venue-edition" inside comments. **The app has no concept of a wedding date on
an entitlement.**

**So the failure R-015 exists to prevent is live.** A couple who books in March
2027 for a September 2028 wedding and redeems on the day they sign loses the
product in September 2028, before the wedding, at the venue that gifted it.

**The seam is cheaper than it looks, and it already half-exists.**

1. `workspaces.primary_date` is a real column (`src/server/db/schema.ts:308`),
   described as "Calendar date, never an instant".
2. The contextual onboarding flow already asks for it, labelled **"Wedding
   date"** and required for the wedding context
   (`src/components/welcome/contextual-onboarding.tsx:383`), and writes it to
   that column via `src/server/actions/planning.ts:902` and `insertWorkspaces`.
3. That flow is gated on `contextualOnboarding`, which defaults to
   `env.NODE_ENV !== "production"` (`src/lib/planning/flags.ts:33`), so **it is
   off in production and on locally.**
4. That flow applies **no wedding template** and does not touch the entitlement
   expiry.

So the wedding date the ratified term needs is already asked for, in the
couple's own words, on a path that is off in production and wired to nothing.
D-022 point 1 says "capture the wedding date at redemption". The capture exists
and is in the wrong place.

**What has to change for D-022 to be true for a real couple, smallest form:**

- a wedding-date field on the redemption path, or the contextual onboarding
  path turned on and given the template apply;
- an expiry computation in `comp.ts` that calls the studio rule rather than
  multiplying `durationDays`, or the same rule reimplemented app-side;
- `issue-codes.ts:121-129` relaxed from "must equal 548" to "must be at least 548";
- a recompute when the date changes, which `extendedCoupleAccessExpiryMs`
  already provides.

None of that is E05.01's build. E05.01's job was to find out whether the map
could describe the term honestly. It cannot, and this section is why.

## 4. Step 10: the gate bounces the couple. Re-confirmed.

`src/app/app/layout.tsx:11,16` imports and calls `requireAppAccess`.
`src/server/require-app-access.ts:21-34` is allowlist-only and redirects to
`/waitlist` when `isEmailAllowed(email)` is false. Redemption touches no
allowlist.

The membership-aware version exists. `src/server/app-access.ts:29-62`
(`requireAppAccessTasks`) passes any user with at least one `workspace_members`
row, and its own header at `:20-22` names the failure the shipped gate now
permits. It is called at `src/components/app/tasks-runtime-shell.tsx:67`, which
is **inside** the layout the outer gate wraps. The outer gate fires first.

**Worth stating because it makes the fix small:** a redeemed couple already
qualifies under the inner gate. `ensureUserProvisioned` writes a
`workspace_members` row with role `owner` before the entitlement is inserted
(`comp.ts:206-207`). So swapping the call in `app/layout.tsx:16` from
`requireAppAccess()` to `requireAppAccessTasks()` admits every redeemed couple
and every accepted invitee, and admits nobody else.

## 7. What the venue can see. Traced exhaustively.

**Answer: no private planning content, at any stage.** Not a task, not a note,
not an unpublished Timeline, not a briefing.

Every venue-facing read path out of the app:

1. **`src/app/api/internal/partner-stats/route.ts`** is the only production
   venue-facing egress. Bearer `PARTNER_STATS_SECRET`, `timingSafeEqual`. It
   reads `comp_codes` filtered by `json_extract(notes,'$.sponsor_slug')` and
   `entitlements` by `notes IN (…)`, and returns four scalars: `codesRedeemed`,
   `redeemed30d`, `reachedBoard`, `mostRecentRedemptionAt`. No title, tag, name,
   date or workspace identifier. Consumed by
   `studio/src/lib/partners/stats.ts:104`.
   **Gap, and it is real:** there is no small-cell floor on this endpoint.
   `codesRedeemed: 1` against a venue that issued forty is a statement about one
   identifiable couple. That is the R-027 shape on a second endpoint the R-027
   entry does not name. Owner: WP-07 / WP-05, not this task.

2. **`listSponsorActivationDTOs`** (`src/server/planning/queries.ts:225-245`) is
   sponsor-scoped and has **zero callers** anywhere in `src`, `scripts` or `e2e`.
   Its allowlist carries no workspace name, task, note, member, invitation or
   public-link field, and `projectSponsorActivation`
   (`src/lib/planning/sponsorship.ts:11-36`) additionally nulls the activation
   label and primary date unless consent is recorded. The only writer,
   `src/server/actions/planning.ts:906-917`, copies only `activationLabel` and
   `primaryDate`. Dormant, correct, and the thing a future venue portal will
   reach for.

3. **Studio `/hq/account-review`** reads the entitlements DB and a daily-metrics
   rollup through `assertSnapshotPrivacy`. Aggregate only. And no venue can
   reach it at all: R-043, the only guard is one shared HQ password.

4. **Public surfaces** `/p/[slug]`, `/s/[token]`, `/share/[token]`,
   `/embed/[slug]` are the couple's own publishing choice and are not
   venue-scoped. A venue holding a link sees what any stranger sees. Two live
   exposures already on the register apply here and are not this task's to
   close: `/p` is deliberately indexable and absent from `src/app/robots.ts:14`
   (R-031), and `/embed` is tokenless and frameable (R-033).

**Confidence.** `grep -rn "sponsorId\|sponsor_id\|sponsorSlug" src/server src/app/api`
returns **23 lines**, and filtering those 23 for `tasks|notes|comments|attachments`
returns **zero**. Not one sponsor-scoped read touches a content table. The
boundary holds by deliberate allowlist DTO and one narrow endpoint, not by
accident.

**The one thing missing is a test.** `src/server/planning-security-contract.test.mjs`
tests membership scoping and asserts that `sponsorship` appears in the actions
file. It does not assert the DTO allowlist. The programme's central promise has
no regression test at the app boundary. Recommended to E05.10.
