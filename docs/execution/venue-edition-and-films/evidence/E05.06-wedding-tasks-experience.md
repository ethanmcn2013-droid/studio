## AC1 — the assign menu offers real workspace members

**FAILED on audit. Built.**

The defect, as it stood: `src/components/app/detail-panel/field-rows.tsx:26`

```ts
const ALL_USERS: UserId[] = ["chloe", "david", "alex", "ada", "marcus"];
```

rendered at `:291` as the entire contents of the "add someone" menu. Those five
are seed personas from `src/lib/data.ts`. A couple opening any task in their own
wedding workspace was offered five people who do not exist and could assign
their wedding work to them.

This contradicted two source files that both state the rule in prose and neither
of which enforced it:

- `src/lib/members.ts:1-6` — *"Minimal member identity for client surfaces: the
  assign menu, avatar stacks … Resolved server-side from workspace_members ⋈
  users by `getWorkspaceMemberMeta`"*
- `src/lib/domain-context.tsx` (`members` field) — *"The assign menu and avatar
  stacks hydrate from this — never from design-lab fixtures."*

The board already did it correctly. `src/components/hybrid/options/a/board-view.tsx:241`
calls `listPeople()`, which reads the runtime registry that
`src/components/hybrid/hybrid-workspace.tsx:88-100` fills from
`useWorkspaceMembers()`. Only the task detail was missed. This is why the fix is
a wiring change and not a new system.

**Built:** `field-rows.tsx` `AssigneesRow` now reads `useWorkspaceMembers()`.
Avatars receive the member's real name so a Clerk id resolves to correct
initials through `resolveUser` rather than to "?" through the `USERS` proxy
fallback.

**Confirmed live path.** `TaskDetailPanel` mounts inside
`src/components/app/tasks-runtime-shell.tsx:182`, so this panel is present on
every `/app` page. `MetadataRail` renders `AssigneesRow` at
`src/components/app/task-detail/metadata-rail.tsx:96`. The roster is real:
`tasks-runtime-shell.tsx:120` calls `getWorkspaceMemberMeta(workspaceId)`
(`src/server/db/members.ts`), which joins `workspace_members ⋈ users`, owner
first.

**One thing the prior audit did not reach, and a correction to a natural
assumption.** `src/components/hybrid/shared/task-inspector.tsx:108` contains the
same class of defect — it imports `LAB_PEOPLE` from `src/components/hybrid/fixtures.ts`
directly, bypassing `listPeople()`. **It is not a live defect.** A repo-wide
grep for `task-inspector` returns exactly one hit outside the file itself:
`src/server/suite-navigation-contract.test.mjs:35`. The component has no
importer. It is dead code wearing a live bug. Recorded rather than fixed,
because deleting another package's file mid-wave is not this task's call.

## AC3 — the wedding date as a first-class field, and what a redeemed couple actually has

**PASSES as a schema question. FAILS as a product question. This is the most
important finding in the task.**

The field exists and is first class:

- `src/server/db/schema.ts:308-309` — `primaryDate: text("primary_date")` and
  `primaryDateLabel: text("primary_date_label")`, commented *"Calendar date,
  never an instant."*
- `src/components/welcome/contextual-onboarding.tsx:383` labels it **"Wedding
  date"** when the context is a wedding, and makes it `required`.
- `src/server/actions/planning.ts:875` refuses to complete a `wedding_season`
  planning period without one.

**And a redeemed couple never gets one.** Traced end to end:

| Step | File | What happens to the wedding date |
|---|---|---|
| Redemption | `src/server/actions/comp.ts` | Applies the wedding template, sets `template_id` and `active_domain='wedding'`. Never writes `primary_date`. |
| `/welcome`, contextual branch | `src/app/welcome/page.tsx:59-67` | Redirects to `/welcome/plan?context=wedding_season`, which does capture the date. **Gated on a flag that is off in production:** `src/lib/planning/flags.ts:33` sets `defaultEnabled = env.NODE_ENV !== "production"`. |
| `/welcome`, production branch | `src/app/welcome/page.tsx:69-85` | Applies the template, sets `template_id`, `active_domain`, `primary_use_case`, `onboarding_completed_at`. **Never writes `primary_date`.** |
| Afterwards | `src/components/app/settings/sections/workspace.tsx` | Zero matches for `primaryDate`, `primary_date`, `Wedding date` or `anchor`. **No field anywhere in the app sets or changes it.** |

Independently corroborated: the E05.03 work running concurrently in this same
worktree reached the same anchor field from the write side
(`src/lib/template-anchor.ts`, `src/server/db/apply-template.ts`), and made the
same refusal — no anchor means no due date, never a fallback to days-from-now.
Two packages arriving at `workspaces.primary_date` independently is the
strongest evidence available that it is the right field.

**Consequence, stated plainly:** in production today a sponsored couple's
workspace has `primary_date = NULL`, and there is no way for them to set it.
Every wedding-relative feature on both sides of this wave is inert until that
changes. It also bears on D-022: the ratified term is
`max(redemption + 548 days, wedding date + 90 days)`, and the app holds no
wedding date to compute the second half from. That is R-015, still open, and
this is a second independent path to it.

## AC4 — a due date is legible against the wedding date, in exact days

**FAILED on audit. Built.**

Nothing related a due date to the anchor. `src/components/app/detail-panel/due-calendar.tsx`
contained one mention of a wedding, in a comment about a wedding planner
guessing date wording. `DomainCtx` carried no anchor date at all.

Built, in three parts:

1. **`src/lib/tasks/anchor-due.ts`** — pure, no I/O. `relateDueToAnchor` returns
   `{ state, days, label }` using `calendarDaysBetween` from
   `src/lib/planning/dates.ts`, so the count is calendar days and never elapsed
   milliseconds. Counts are **exact days, never rounded to weeks or months** —
   "about six weeks" is a different claim from the one the dates support.
2. **`useWorkspaceAnchor()`** on `src/lib/domain-context.tsx`, fed from
   `workspaces.primary_date` / `primary_date_label` selected at
   `src/components/app/tasks-runtime-shell.tsx` and passed to `DomainProvider`.
   Both props are optional and default to null, so the single existing caller is
   the only one that had to change.
3. **Render.** `DueRow` in `field-rows.tsx` shows the relation under the due
   chip (`42 days before the wedding`), carrying
   `data-due-anchor-relation="before|on|after"` for later capture. `DueCalendar`
   takes `anchorDate` and `anchorNote`, heads the picker with
   *"The wedding is in 313 days"* and marks the anchor day in the grid with a
   ring and `data-anchor-day`.

The noun comes from `primary_date_label`, not from a hard-coded "wedding": a
label of "Examinations" produces "42 days before the examinations". A label that
already carries an article is not doubled.

**Demo mode is deliberately excluded.** `tasks-runtime-shell.tsx` passes null for
both anchor fields in demo mode, so no existing review capture or visual
baseline changes shape. That is also why this feature renders in no current
Playwright evidence — consistent with the audit's finding that all 128 passing
tests run in demo mode.
