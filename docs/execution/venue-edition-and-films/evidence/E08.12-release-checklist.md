## Release day · Step 1, the database

**Never** paste a `drizzle/*.sql` file into production. **Never** run
`drizzle-kit migrate` or `drizzle-kit push` against production. The historical
`0000`–`0013` chain is non-idempotent and will damage the database.

```bash
# 1. Where is production now?
pnpm db:status -- --environment=production --confirm-production=tasks

# 2. Take a verified backup FIRST. Record the path and the hash.
node scripts/db/backup.mjs --environment=production

# 3. Restore that backup into an isolated copy and verify it, before touching
#    production. If this fails, stop: you have no rollback.
node scripts/db/restore-verify.mjs --backup=<path-from-step-2>

# 4. Build the execution receipt (target identity, environment, current ledger
#    hash, pending migration hashes, backup hashes), then:
pnpm db:migrate -- \
  --environment=production \
  --confirm-production=tasks \
  --receipt=<execution-receipt.json>

# 5. Confirm the ledger moved and nothing else did.
pnpm db:status -- --environment=production --confirm-production=tasks
```

- [ ] Backup taken and its restore **verified** (step 3 passed)
- [ ] `db:migrate` reported the expected migrations applied and no others
- [ ] `db:status` after the run shows the ledger at the expected hash

### If migration `0027` is in this release

- [ ] After the migration, run the share-link backfill:
