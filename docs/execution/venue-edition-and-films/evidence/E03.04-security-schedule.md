## 0. The rule this schedule was written under

**Every control described here was read in the repository on 2026-08-04 and is
named by file.** A control that could not be pointed at was not written down.
Everything the task title implies but the product does not do appears in §6,
"What is not built", in the same words it would have used if it did.

This is the opposite of how a security schedule is usually written, and it is
deliberate. A venue's adviser can check every line of §1 to §5. A schedule that
cannot be checked is marketing.

**Two framing statements before the detail.**

> **Signal Studio does not implement encryption itself.** Transport security and
> encryption at rest are properties of the providers in Schedule 2, offered under
> their own terms. Signal Studio configures HTTPS-only transport and relies on the
> providers for the rest. Neither has been verified by Signal Studio in this
> programme, and no claim about either is made here.

> **There is no row-level security.** Turso and libSQL do not offer it. Tenant
> isolation is enforced in the application and verified by tests. That is
> materially weaker than database-level isolation, which fails closed beneath the
> application (D-033, CR-005 / E08.04).

## 1. Tenant isolation

The control that keeps one couple's workspace out of another's, and every
couple's workspace away from every venue.

| Control | Where it lives | What proves it |
|---|---|---|
| Every workspace-scoped read carries a tenant predicate | four data surfaces: tasks, signal, notes, timeline | `app/src/server/tenant-scope.test.mjs`, wired into `pnpm test`. 247 governed reads scanned, 8 waived in writing, 0 unscoped |
| The detector is proven to detect | `app/src/server/tenant-scope-rules.mjs` | `app/src/server/tenant-scope-rules.test.mjs`, 22 synthetic statements with known answers, including a pinned regression for a real false negative found on 2026-08-03 |
| A runtime guard that throws rather than degrading to an unscoped query | `byWorkspace()` in `app/src/server/db/tenant.ts` | asserted in `app/src/server/cross-tenant-negative.test.ts` |
| A real cross-tenant negative test, per object | `app/src/server/cross-tenant-negative.test.ts` | an in-memory libSQL database, two workspaces, nine sensitive objects, each asserting a scoped read returns nothing when handed the other tenant's key, with a control case proving the assertions are not vacuous |
| No venue-scoped read reaches a couple's product data | studio | `studio/src/lib/hq/hq-authorization.test.mjs`: no venue-facing module may reach the tasks database, and the projector may not fetch |
| The governed table list cannot drift from the schema | both directions | drift guard in `tenant-scope.test.mjs`, its own detection proven in `tenant-scope-rules.test.mjs` |

### 1.1 The limits of this control, recorded rather than hidden

Taken from `evidence/E08.04-E08.05-tenancy-and-access-control.md`, which records
them against its own criteria.

1. **It is a detector, not a boundary.** A read scoped to the wrong workspace id
   passes it. Only the runtime guard and the authentication choke points constrain
   which id is used.
2. **Tokens are matched as substrings**, so a local variable named `taskId` counts
   as evidence of scoping even though it is not a column reference. Accepted, and
   pinned as an explicit test so it is a recorded property rather than a surprise.
3. **Eight waivers are honoured on trust.** The gate checks that a human wrote a
   reason, not that the reason is good.
4. **404-versus-403 is proven at the data layer only.** Two routes were confirmed
   to return 404 rather than 403. A route-level sweep has not been done.

## 2. Authentication and access

### 2.1 Couples and account holders

Authentication is provided by Clerk. Signal Studio never sees or stores a
password.

**Not asserted here.** The live page at `studio/src/app/security/page.tsx` says
"Multi-factor authentication is available on every account." That is a property of
the Clerk configuration, not of Signal Studio's code, and it has not been checked
in the Clerk dashboard in this programme. It is recorded as a claim already made
on a live page and not repeated as a control.

### 2.2 Signal Studio's own operator access, stated plainly

**This is the weakest control in the system and a venue's adviser will find it, so
it is stated here rather than found.**

Every Signal HQ surface is guarded by **one shared password** held by the founder.
The session token is `v2.<issuedAt>.<HMAC>` over a key derived with PBKDF2, which
is a real improvement on the derivable v1 cookie it replaced, and its tests in
`studio/src/lib/hq/auth.test.ts` are written to fail against v1 and do.

What it does not do:

- **There is no per-person identity.** No account, no name, no login record that
  attributes an action to a human.
- **There is no way to revoke one holder** without rotating the password for
  everyone.
- **The same password opens every Signal HQ room**, including the ones that have
  nothing to do with venues.

Verified at `studio/src/lib/hq/auth.ts` and recorded as R-043.

**Consequence for the venue agreement.** The data protection agreement does not
promise a venue a login, because handing a venue this password would put the
founder's entire operating surface behind a credential shared with a customer.
See Decision point B in the agreement.

### 2.3 Venue roles

`studio/src/lib/account/roles.ts` implements three roles and six capabilities,
cross-checked in both directions against `role-matrix.test.ts`.

**It is a specification, not a running control.** No venue holds any of these
roles, because no venue-authenticated route exists (R-043). The matrix governs
four founder-facing review panels. It must not be cited as evidence that venue
authorisation is implemented, and it is not cited that way here.

One documented control does hold and is worth naming: the capability list is a
runtime value with the type derived from it, and the test that asserts "no venue
role may hold a capability reaching couple content" reads the production list
rather than a hand-written copy. That was proven by mutation: adding a capability
named for couple content turns the test red where it previously passed green.

### 3.1 A live page contradicts this schedule, and it is being reported rather than reconciled

`studio/src/app/security/page.tsx`, updated 2026-07-12, states: "X-Frame-Options
is set to DENY across the suite, so Signal Studio surfaces cannot be embedded in
third-party frames."

**That sentence is false of `/embed/*`**, which exists in order to be framed and
whose own route file says so. The same page also states that errors are reported
to Sentry, that backups age out inside ninety days, that the database is encrypted
at rest and sits primarily in Frankfurt, and that new share links are stored as
hashes. Each of those is either unverified in this programme or contradicted by
§6 below.

This schedule does not restate any of them. Correcting the live page is outside
E03.04 and is raised in the recommendation packet, because rewriting a live public
security page inside a document task would be exactly the kind of quiet change
this programme forbids.

## 4. Transport, headers and content security

Verified in `app/next.config.ts` and `studio/next.config.ts` on 2026-08-04.

| Header | Value | Scope |
|---|---|---|
| `Strict-Transport-Security` | `max-age=63072000; includeSubDomains; preload` | both apps |
| `X-Content-Type-Options` | `nosniff` | both apps |
| `Referrer-Policy` | `strict-origin-when-cross-origin` | both apps |
| `X-Frame-Options` | `DENY`, with named exceptions | both apps. Studio relaxes to `SAMEORIGIN` on four specific document routes. The app strips it entirely on `/embed/*` |
| `Permissions-Policy` | `camera=(), microphone=(), geolocation=(), interest-cohort=()` | both apps |
| `Content-Security-Policy` | **Report-Only** on the baseline of both apps | app promotes to enforcing only when `SIGNAL_ENFORCE_CSP=true`; studio has no promotion path in the config at all |

**Two honest qualifications.**

1. **A Report-Only CSP reports and does not block.** Whether
   `SIGNAL_ENFORCE_CSP` is set in production has not been verified in this
   programme, and this schedule does not assert that it is.
2. **The couple-facing public surfaces are an exception, on the integration
   branch.** `/p`, `/s`, `/share` and `/embed` receive an **enforcing**
   Content-Security-Policy that blocks third-party analytics hosts, independent of
   the environment variable, because a privacy control that only reports is not a
   control. Verified on `claude/integrate-app`; not on `app` `main`.

| Control | State | Evidence |

## 6. What is not built. This section is the point of the document.

Each line is verified. None is softened.

### 6.1 Monitoring, alerting and detection

- **Error monitoring is integrated and not provisioned.**
  `app/src/instrumentation.ts` returns early when `SENTRY_DSN` is unset, and
  `studio/docs/INFRASTRUCTURE.md` lists Sentry, PostHog, Upstash and production
  Anthropic under "Provisioned deliberately later ... integrated in app code, none
  provisioned". An unhandled error in production is currently observed by nobody.
- **Studio has no error reporting at all**, not even an unprovisioned integration.
- **There is no alerting of any kind.** No pager, no threshold, no notification,
  no escalation. No such mechanism exists in either repository.
- Consequence: detection of a disclosure, a corrupted row, or a share link
  resolving after revocation is manual. This is stated in the agreement at §7.3
  as well, because a venue must not have to find it here.

### 6.2 Audit logging

- **The application's audit log covers two event kinds**, `inviteSent` and
  `inviteAccepted`. Removing a member, changing a role, creating or revoking a
  share link, publishing a workspace and deleting an account are **unaudited**.
- A venue or a couple asking "who removed this person from our workspace" cannot
  be answered today.
- **The entitlements audit ledger is genuinely strong** and is credited: it is
  hash-chained, written inside the same transaction as the state change, called
  from fifteen sites, and enforced append-only by database triggers. It covers
  entitlements, codes, founding numbers, erasure and billing. It does not cover
  workspace activity.

### 6.3 Backups and recovery

- **Nothing takes a backup on a schedule.**
- The Turso account is on the **Free tier**, so point-in-time recovery is
  unavailable, and the budget is zero (D-015 Q5).
- The only backup of production is a manual dump at `db-archive/2026-07-31/`:
  a single copy, on one laptop, covering the **previous generation** of databases,
  never restored.
- A restore **has** been rehearsed with recorded numbers, against a local file
  with the production schema: 462 rows, 25 tables, 6459 ms, hashes recomputed.
  That is a real rehearsal and it is credited. It is not a network restore with a
  production cutover.
- The data-loss window today is "time since someone last ran a dump by hand".

Source: `evidence/E08.08-E08.09-observability-and-continuity.md`, `studio/docs/RECOVERY.md`.

### 6.4 Published surfaces

- **No data-protection footer exists on any published surface.** No controller
  name, no contact address, no Article 14 sentence, no removal route. Role map §5
  Consequence 5 and founder decision 1 record this as the cheapest and
  highest-value item in the whole map.
- **Publication is workspace-level.** One settings toggle publishes every task in
  the workspace. There is no per-item publish opt-in.
- The published data transfer object allowlists `id, title, lane, priority, due,
  tags`. Excluding descriptions is a real control and is credited. Titles and tags
  are where a person's name gets typed.

### 6.5 Vulnerability reporting, stated accurately

- **There is a route, and it is published.** `studio/src/app/security/page.tsx`
  asks reporters to write to `hello@signalstudio.ie` with the subject line
  "security", commits to acknowledging inside two working days, and asks for
  thirty days before public disclosure.
- **There is no `security.txt`.** No `public/.well-known` directory exists in
  either repository.
- **There is no `security@` address.** The route is the general mailbox with a
  subject-line convention. The repository's own launch-readiness list records this
  as open: `app/src/server/roadmap/launch-readiness-seed.ts:399`, item
  `AI-vuln-disclosure`, priority P1, "Publish security@<domain> + scope +
  safe-harbor language."
- There is no bug bounty, and the page says so.

### 6.6 Standards and assurance

- No SOC 2 report, no ISO certification, no external penetration test, no audit.
- No uptime commitment.
- The live security page already says these things in its own words, under the
  heading "What we will not pretend", and that framing is kept.

### 6.7 Rate limiting

`app/src/lib/ratelimit.ts` is gated on Upstash and **fails open**: it is a no-op
until `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN` are provisioned.
`studio/docs/INFRASTRUCTURE.md` records Upstash as not provisioned. So the
per-user burst caps documented in `app/src/server/ai.ts` are not enforced today.

## 7. Changes to this schedule

Signal Studio will update this schedule when a control changes, and will tell the
Venue in writing before adding a new recipient of personal data. A control being
removed is a change the Venue is told about, not one it discovers.

## 8. Points a solicitor must settle

1. Is a security schedule that states this many unbuilt controls safer for Signal
   Studio than one that describes a target state, or does listing them create an
   admission that damages the position it is meant to protect?
2. Does application-level tenant isolation without row-level security meet Article
   32's "appropriate technical and organisational measures" for a product holding
   special-category data about third parties, and if not, what is the minimum that
   would?
3. Does the absence of scheduled backups and any alerting breach Article 32(1)(b)
   or 32(1)(c), and is the sole-responder position defensible for a controller of
   this size?
4. Is the absence of malware scanning on an upload path open to a consumer a
   material Article 32 gap, given that attachments are private and never rendered
   on a published surface?
5. Does publishing a security schedule that a venue can check line by line create
   any contractual warranty Signal Studio does not intend to give, and should it
   carry an express "this is a description, not a warranty" clause?
