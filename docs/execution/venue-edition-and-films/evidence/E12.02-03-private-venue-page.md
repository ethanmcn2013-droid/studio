## 0. The one structural decision, and why it is not two pages

E12.02 asks for a private invitation page. E12.03 asks for a parameterised
private proposal page. **They are the same URL**, and that is ratified rather
than convenient: `E13.16` section 3 says "One page, two states on one URL:
invitation first, proposal after a conversation. **The venue never gets a second
link.**"

The task titles are not rewritten, because imported titles never are. What is
built is one route whose state is a property of the venue's row rather than of
the address. E12.02 owns the invitation state and the shell; E12.03 owns the
proposal state and the parameterisation.

**The consequence that must not be missed.** D-032 R13 settled the URL as a bare
token. So this page cannot use the `venue` tracking parameter that every other
commercial link in the programme uses (`src/lib/tracking.ts`), and it cannot be
addressed by slug. A venue is resolved server-side from an opaque 24-character
token, and that is the whole access-control model: there is no login, because a
password on a cold-email click is where the funnel ends.

## 2. E13.16's acceptance criteria, the four that are WP-13's

### Criterion 8 — exactly the fields in section 4.2, proven by a test that rejects rather than trims

**Met.** `event.ts` exports `VENUE_PAGE_VIEWED_FIELDS` as the seven names, and
`buildVenuePageViewedEvent` throws on an eighth rather than dropping it.
`event.test.ts` proves it three ways: an arbitrary extra key, a `userAgentClass`
key by name (D-032 R14), and every entry on the never-list including `token`.

Real emitted line, from a live request:

```json
{"stream":"venue-outreach.v1","kind":"venue_page_viewed",
 "idempotencyKey":"ce0e0d2696ef0808e14cfed17bf34decc3645c6739b7e63a641996c47868c499",
 "event":{"accountId":"VEN-0042","occurredAt":1785741473884,"cohort":1,
          "touch":"email_1","state":"invitation","firstView":true,"repeatViewCount":0}}
```

No token, no IP, no referrer, no user agent, no venue name. The route reads no
request header, so there is no path by which any of them could arrive by
accident.

**Not met, and stated rather than implied: there is no durable store.**
`venue-outreach.v1` is defined by E09.04 and implemented by nothing in this
repository. What ships is a structured server log line. Two consequences follow
and neither is engineered around:

1. `firstView` and `repeatViewCount` come from a per-process counter. The
   verification run shows it plainly: the second visit to the same token
   reported `firstView: true` again, because the module had been reloaded. On a
   serverless deployment every cold start does the same.
2. Deduplication is at ingest, not at emit. The idempotency key is computed and
   emitted, and the two visits above carry the same key, which is the property
   E09.04's `sha256(kind, accountId, dedupeKey, day)` exists for. Nothing
   consumes it yet.

### Criterion 9 — no open pixel, read receipt, session recording, heatmap, scroll depth or IP location

**Met.** None is present. The route has no client component, no `useEffect`, no
script tag of its own and no third-party import. The rendered page's only
scripts are Next.js's own framework chunks.

### Criterion 10 — no third-party script and no consent-requiring cookie, proven by a request log on a real page load

**Met, and proven differentially rather than by a code read**, because the tag is
injected by a layout two levels above the route.

A dev server was run with `VERCEL_ENV=production` set, which is the only
condition under which `GoogleTag` renders at all. Occurrences of
`googletagmanager` in the served HTML:

|---|---|---|---|
| `/` | 1 | 5 | present |
| `/venues` | **0** | 0 | present |
| `/v/<invitation token>` | **0** | 0 | **absent** |
| `/v/<proposal token>` | **0** | 0 | **absent** |
| `/v/<replaced token>` | **0** | 0 | **absent** |
| `/v/<unknown token>` | **0** | 0 | **absent** |

That is D-032 R8 satisfied for `/v/*` and for `/venues`, with the rest of the
site unchanged. **R-032 is not decided by this.** The site-wide consent position
for every other public page remains open and nothing here touches it.

### Criterion 11 — `/v/` disallowed in robots, absent from the sitemap

**Met.** Served `robots.txt`:

```
User-Agent: *
Allow: /
Disallow: /api/
Disallow: /hq/
Disallow: /redeem/
Disallow: /review
Disallow: /v/
```

`sitemap.ts` filters the private prefix rather than relying on its absence, and
`paths.test.ts` walks every rendered sitemap entry and fails if any is a private
path. The page also sets `robots: { index: false, follow: false, nocache: true }`,
verified in the served head: `<meta name="robots" content="noindex, nofollow, nocache"/>`.

### Criterion 12 — an unknown token and a revoked token produce byte-identical responses, and neither records an event

**Met.** A revoked token and an unknown token of the same length were requested.
Both returned `404`. Both bodies are **54,290 bytes**. After substituting the
requested token string in each body, the two files differ in exactly one place:
Next.js's own per-request random identifier (`self.__next_r`), which is generated
fresh on every request to any route and is not a function of registry state.

No `venue_page_viewed` was emitted for either. The dev log carries four event
lines across the whole run, all from the two resolvable tokens.

**The one thing an observer can distinguish, and it is not a leak.** The response
echoes the token the requester itself sent, in the Flight payload. That is the
requester's own input, and it says nothing about whether the token was ever in
the mapping.

### Criterion 21 — a replaced token returns 200 and the replacement page

**Met.** `/v/<replaced token>` returned `200`. The rendered page is 298
characters of text:

> This link is no longer in use. The address you opened has been replaced. If it
> was sent to you, write to hello@signalstudio.ie and we will send you the
> current one. Signal Studio records that this page was opened, and the date.
> Nothing else. Ask us to stop and the record is deleted. signalstudio.ie

Section 12.4 verbatim. It names no venue, carries no film, carries no offer
detail, links to no other token and links to nothing at all. It emitted no
`venue_page_viewed` and one operations line carrying exactly `accountId`,
`occurredAt` and `outcome: "replaced"`.

## 4. Venue branding, and one decision the founder should look at

**What is rendered:** the venue's trading name, as text, three times on the
invitation state and three times on the proposal state. No logo, no colour, no
venue-written content, no other venue asset. That is D-027 point 3 and R-024.

**What is not rendered, and this is the decision.** The venue's name does not
appear in the page's `<title>`, its meta description or any OpenGraph field.
Verified on the served head of the invitation state: the title is `Signal Studio`
and the description is the root layout's generic one. `Glenmara` appears nowhere
in the 4,662-character head.

**Why it was built that way.** E13.16 section 1.1 settled the URL as a bare token
on one argument: a slug puts a venue's name into browser history, proxy logs, CDN
logs, referrer headers and every thread the link is pasted into, and a name that
has already been sent cannot be recalled. An OpenGraph description is fetched and
cached by every unfurling service a private link touches, which is the same
exposure through a different door. `consent_public_naming` is `unknown` for all
219 researched accounts.

**The judgement, stated plainly so it can be reversed in one word.** R-024 says
venue branding is the venue's name only. It does not say the name must appear.
Rendering nothing is trivially within "name only". If the founder wants the name
in the link preview, it is one line, and this document is where the reasoning
against it is recorded.

## 6. Forbidden wording

`grep -rnaiE` over `src/lib/venue-invitation/` and `src/app/v/`, case-insensitive:

**Zero hits** for: `for life` · `lifetime` · `forever` · `in perpetuity` ·
`founding fifteen` · `first fifteen` · `2,500` · `guaranteed` · `partner` ·
`exclusive` · `seamless` · `no seats` · `allotment` · `dietary` · `co-branded` ·
`welcome message` · `GDPR` · `solicitor`. **Zero** em dashes.

`node scripts/check-venue-edition-contract.mjs` returns `[venue-edition-contract] ok`
with the four new sources in `currentCommercialSources`.

**Scarcity is static and true.** "Twenty-five" and "01/25 through 25/25" cannot
go stale. The proposal's paid count is operator data verified against the
register at the moment of sending (mechanics §1), and it is the one number on the
page that a stale runtime document could make wrong. That is named in the task
spec as an operator risk rather than engineered around, because the register is
the truth and a private page with no login should not open a database connection
on a cold click.

**"No seats" is deliberately absent.** P6 blocks it pending OQ-6, which is still
open. The page uses D-020's ratified sentence instead, which says the same thing
and does not use the phrase.

## 8. Honest state

- **`filmUrl` is null on all twenty-five links** (E13.16 §11), so no film was
  rendered in verification. The page is built to stand without one, which is what
  §3.1 requires: "The page must work with video blocked by a corporate policy.
  The film is not the destination." When a film does arrive, the registry refuses
  it unless a poster frame **and** a `.vtt` captions track arrive with it.
- **There is no durable event store.** §2 criterion 8.
- **The runtime link document is an environment variable**, `VENUE_INVITATION_LINKS`.
  No venue name and no token is committed to this repository. Absent or malformed,
  every token 404s, which is the correct state for a preview build.
- **Nothing was deployed and nothing was pushed.** R-025 stands.
- **No venue has been contacted.**

## 10. What a founder needs to decide

1. **The venue's name in the page metadata.** Built as absent, on E13.16 §1.1's
   reasoning. §4 above.
2. **Where the runtime link document lives.** Built as one environment variable.
   A table in the entitlements database is the alternative, and it costs a
   migration.
3. **Registering `studio.page.v-by-token` and `studio.state.v-by-token-not-found`.**
   The gate is two worse until somebody does, and this is the third time in two
   days a new surface has hit the same structural gap. The real fix is expanding
   the capture plan.
4. **The durable store for `venue-outreach.v1`.** Until it exists, "we can see
   that you opened it" is true of a log line rather than of a record anybody can
   read. That is the one sentence in the venue copy pack that the product does
   not yet fully support.
