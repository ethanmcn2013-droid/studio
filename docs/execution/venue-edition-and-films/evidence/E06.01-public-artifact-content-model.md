## 0. There are two published products, and conflating them is how the privacy
documentation got `/p` wrong

| | `/p/[slug]` | `/s/[token]` |
|---|---|---|
| What it renders | A published **Tasks** workspace, through `PublishedWorkspace` / `WeddingTheme` | A published **Timeline** artifact, through `TimelineArtifact` |
| Database | Tasks (`TASKS_DATABASE_URL`) | Timeline (`TIMELINE_DATABASE_URL`) |
| Projection | `PublicTask` via `toPublicTask` (`src/lib/public-task.ts`) | `AudienceTimelineDto` via `validateAudienceTimelineDto` (`src/modules/timeline/lib/audience-timeline.ts:148`) |
| Access | No token. Slug only. | 256-bit bearer token, SHA-256 hashed, unique index, timing-safe compare |
| Publish act | `publishWorkspaceAction` (`src/server/actions/settings.ts:260`) sets `publishedAt` | `createAudiencePublication` then `publishAudiencePublication`, which mints a token |
| Search engines today | **Indexable.** Not in `src/app/robots.ts:14`, sets no `noindex`. | **Excluded.** `robots: { index: false, follow: false, noarchive: true, nosnippet: true }` at `src/app/s/[token]/page.tsx:29`, plus layout metadata and an `X-Robots-Tag` header, and `/s` is in the robots disallow list. |

They are two databases, two publish actions and two DTOs. This document
describes both separately and does not write a single "published surface"
abstraction over them.

**D-033 (R-031 Option B) governs `/p`.** Wedding workspaces ship `noindex` by
default, `/p` goes into the `robots.ts` disallow list, search visibility becomes
an explicit couple opt-in, and the publish confirmation states plainly what
publishing does. **None of that is implemented yet.** It is E06.05's build. As
of 2026-08-03 a published wedding workspace on `/p` is still crawlable, and this
document says so rather than describing the decision as if it were the state.

**Open founder question, recorded and not assumed.** D-033 says the couple's
artifact stays on `/p`. In code, `/p` renders a lane-grouped Tasks board reskin,
and the editorial vertical artifact that E06.09 and E06.10 refine renders only
on `/s`. Which one is the sponsored couple's keepsake is a genuine product
question. It changes nothing built here.

## 1. The Timeline audience DTO — field by field

`AudienceTimelineDto`, `src/modules/timeline/lib/audience-timeline.ts:29-39`.

### Top level

| Field | Type | Source | May it identify anyone |
|---|---|---|---|
| `version` | literal `1` | constant | no |
| `audienceKind` | `class \| module \| couple` | owner's choice at creation | no |
| `publicationId` | uuid | minted at creation | no. Not the workspace id, not the Tasks id. |
| `label` | string ≤ 120 | owner-authored | It is the couple's own title for their own page. This is the one field that also becomes the OpenGraph title. |
| `ownerDisplayLabel` | optional string ≤ 80 | owner-authored | **Yes, deliberately.** See §3. |
| `primaryDate` | optional `{ label ≤ 40, date }` | owner-set, now owner-removable (E06.06) | the wedding date, if the couple leaves it on |
| `lastUpdatedAt` | ISO instant | publication row | no |
| `today` | calendar date in the publication's named zone | derived | no |
| `sections` | array | derived | — |

### Section

`state`, `label`, `items`. Nothing else. `SECTION_KEYS`, line 55.

### Item

`ITEM_KEYS` is exactly `publicId`, `title`, `date`, `state` — line 56.

| Field | Notes |
|---|---|
| `publicId` | a uuid minted at copy time. Not the Tasks task id, not the node id. |
| `title` | ≤ 180. The owner's shared wording, which they can edit after publishing without touching the private source (`updateAudiencePublicationItem`, `server/audience-timeline.ts:599`). |
| `date` | optional and genuinely optional: `if (item.date !== undefined) mapped.date = ...` at line 221. An undated milestone emits **no `date` key at all**. |
| `state` | one of five, and it must match its section (line 218). |

There is no image key, no story key, no description, no attachment, no comment,
no assignee, no cost. Not because they are filtered — because they do not exist
at this layer.

### How the allowlist is enforced

`exactKeys(value, allowed, path)` at line 109 does two things on every object at
every level:

```
if (FORBIDDEN_KEYS.has(key)) throw new TypeError(`${path}.${key} is forbidden`);
if (!allowed.has(key)) throw new TypeError(`${path}.${key} is not allowlisted`);
```

The second line is the one that matters for "excluded by default": a new field
appearing anywhere in the candidate object throws, whether or not anyone
remembered to add it to a denylist. It runs at four levels — top (line 150),
`primaryDate` (line 193), section (line 203) and item (line 214).

`FORBIDDEN_KEYS` (lines 57-74) is the named denylist under it:
`workspaceId`, `workspaceSlug`, `userId`, `sourceId`, `sourceRef`,
`sourceRelation`, `sourceDigest`, `ownerEmail`, `sponsor`, `membership`,
`description`, `attachments`, `comments`, `notes`, `audit`, `privateMetadata`.
It exists so the error message says *forbidden* rather than *not allowlisted*,
which is a better signal to whoever is reading the stack trace.

**`validateAudienceTimelineDto` rebuilds the DTO; it never spreads the
candidate.** Lines 155-227 construct a fresh object and copy named fields onto
it. Even if `exactKeys` were removed, an unnamed field could not survive the
rebuild. That is two independent mechanisms, and it is why this boundary is the
best-built thing in the module.

The select that feeds it is equally explicit: `server/audience-timeline.ts:797-809`
names five columns with a comment stating the rule.

## 3. `ownerDisplayLabel` — the decision, and the rule

### The decision: owner identity stays in the published projection

`ownerDisplayLabel` is emitted at `server/audience-timeline.ts:816-818` and
rendered at `components/artifact/timeline-artifact.tsx:275` as
`timeline.ownerDisplayLabel ?? "Shared timeline"`.

**It stays.** Reasoning, recorded so it is not re-argued:

1. It is the couple's own name for their own page, typed by them. A keepsake
   headed "Shared timeline" is not a keepsake.
2. It is **optional**. A couple who wants no names publishes without it and the
   artifact reads correctly.
3. It is **not derived from account identity**. It is never the Clerk name,
   never the email, never the workspace owner record. Nothing reads an identity
   store to populate it.
4. Removing it would not remove names from the page anyway — `label` and every
   item `title` are also owner-authored free text. Taking out the one field
   labelled "identity" while leaving three that carry the same risk is theatre.

The honest counter-argument, recorded: it is the only field on the DTO whose
*purpose* is to name a person, so it is the one a reviewer will ask about. The
answer is the rule below.

### The rule

Added in this task, `src/modules/timeline/lib/audience-timeline.ts:95-103`:

```ts
const COUPLE_DISPLAY_LABEL_RE = /^[\p{L}\p{M}][\p{L}\p{M} '’\-&.,]*$/u;
```

On a **couple** publication the shared name must be name-shaped: letters,
combining marks, spaces, apostrophes, hyphens, ampersands, full stops and
commas. Digits are refused, and that is the point — a door number, an Eircode,
a phone number and a date all need digits and a couple's shared name does not.
`@`, `/` and `:` fall outside the class, so an email address and a URL are
refused with them.

Enforced twice:

- `src/modules/timeline/server/actions/audience-timeline.ts:193-199` — at the
  form, so the couple gets a plain sentence rather than a stack trace.
- `src/modules/timeline/lib/audience-timeline.ts:184-187` — inside
  `validateAudienceTimelineDto`, so a row written before this rule existed
  fails at the boundary rather than rendering.

`class` and `module` publications keep the older rule. "Year 3, 2027" is a
legitimate label for a class timeline and carries nobody's home in it.

**What the rule does not do, stated plainly.** It cannot stop a couple typing a
street or a townland in words. It catches the structured identifiers. The
control that matters for prose is that the field is theirs, optional, and shown
to them in the owner studio before anyone else sees it.

The refused message, on voice:

> A shared name can use letters, spaces, apostrophes and hyphens. Take out
> anything else, including numbers, an address, a phone number or an email.

## 4. R-017 — Article 9 data, answered by mechanism

Dietary notes, allergy notes and accessibility requirements reveal health, and
routinely reveal religious belief. They are entered by the couple about guests
who agreed to nothing. **They can never reach a public surface, and the reason
is structural on both products:**

- **Timeline.** There is no field to put them in. `ITEM_KEYS` is four keys and
  `description`, `notes`, `comments` and `attachments` are all in
  `FORBIDDEN_KEYS`. A dietary note lives in a task description or a comment in
  the private workspace, and neither has a representation at this layer. Adding
  one would require editing `ITEM_KEYS`, which is the right place for a review
  gate.
- **Tasks.** `toPublicTask` copies seven named fields and `description` is not
  one of them. A dietary note written into a description does not publish.

**The limit, stated rather than smoothed over.** A couple who writes "Aoife —
coeliac" into a *task title* publishes it, because titles publish by design on
both products. No field-shape rule can catch that, and this document does not
claim one does. R-017's own mitigation is architectural — move dietary capture
to a guest-facing step where the guest supplies their own data — and that is
E03.01 / E03.04 territory, not E06's.

**Not built, and named as not built:** there is no structured dietary field, no
Article 9 classifier, no retention rule tied to the wedding date, and no
under-16 rule. Do not design an in-product venue flow for dietary data (R-017).

## 5. The standing refusals

Ratified in D-033 and recorded here because this is the document E06.03 will
read:

- **No face detection. No auto-tagging. No face grouping.** A "smart crop" is a
  face detector and is covered by this refusal.
- **No third-party analytics on `/p`, `/s`, `/share` or `/embed`**, excluded
  entirely and unconditionally (D-033, R-032 Option A). Implementation is
  E06.07's; this model records it as a property of the surfaces.
- Venue attribution on a couple's page is **one line in the footer, the venue's
  name only**, no logo and no venue-written words (D-011 point 2, D-027 point 3).

## 6. The model for values not yet built

Pre-agreed here so E06.02 and E06.03 inherit a shape instead of inventing one.
**None of this exists. It is a specification, not a description.**

| Proposed field | Layer | Rule |
|---|---|---|
| `image` | new `ITEM_KEYS` entry, new column on `timeline_publication_items` | An object `{ src, alt, width, height }` and nothing else. `alt` is required and stored, never derived from a filename. `src` points at a byte with all EXIF stripped, GPS and capture time included, orientation applied then discarded. |
| `story` | new `ITEM_KEYS` entry, new column | A plain string with a stated maximum. No HTML, no markdown link syntax, no embedded URL. It is a sentence about a day, not a rich-text field. |

Both need a column on the **Timeline** database, which has one baseline
migration (`drizzle-timeline/0000_timeline_baseline.sql`) and no receipt-backed
runner: `scripts/db/migrate.mjs:465` reads `TASKS_DATABASE_URL` only. That is a
real blocker and it is E06.02's founder question.

Whatever is added, it is added to `ITEM_KEYS` **and** given its own validator
branch in the rebuild. A field that is allowlisted but not rebuilt is a field
that can carry anything.

## Test infrastructure note

`src/modules/timeline/server/couple-artifact-boundary.test.ts` uses a
**file-backed** temporary libSQL database, not `:memory:`. The libSQL sqlite3
client drops its connection when a transaction opens and reopens on next use,
and a reopened `:memory:` database is a different, empty one — so every publish,
which is transactional, silently lost the schema. Found by running it, not by
reading. The E05.08 suite is unaffected because it never opens a transaction.
