# E05.08 — the authenticated Timeline, and where it stops being private

Evidence for E05.08. Written 2026-08-03 by WP-08 in worktree
`_wt-wp08` (app, branch `claude/wp08-couple`). Criteria were written before the
assessment. Every claim below carries a path and a line as it stands in that
worktree, or a command and its output.

**Builds on `evidence/E05-E06-audit.md`.** Where this document extends or
corrects that audit, it says so in bold and gives the evidence.

---

## The headline in one paragraph

The private-to-published boundary in Timeline is the best-built thing WP-08
looked at. It is a hashed token, a unique index, a timing-safe compare, an
explicit published-state gate and a hand-written column allowlist, and it is now
covered by a test that fails when the gate is deleted. The problem is on the
other side: **no sponsored couple can reach the authenticated Timeline at all**,
so the boundary currently protects a room nobody can enter. That is one
decision and roughly a day of work, and it is the thing to fix.

generated token. `resolveAudienceTimeline(rawToken)` returns

### 2. Publish opens it, unpublish closes it — **MET**

Same test file, two assertions. `publishAudiencePublication`
(`audience-timeline.ts:447`) sets `state: "published"` and mints a new token;
`unpublishAudiencePublication` (`:565`) sets `unpublished` **and** revokes every
active share in the same transaction (`:587-595`). Both directions verified
against the same token.

### 3. A revoked share reads nothing — **MET**

`resolveShareAccessState` (`lib/audience-timeline.ts`) is consulted at
`audience-timeline.ts:737` before the publication is fetched at all. Test:
`a revoked share cannot re-open a published Timeline`.

### 4. The published projection carries presentation fields only — **MET**

The select at `audience-timeline.ts:759-769` names five columns and its comment
states the rule. The test asserts the negative on the serialised DTO for
`sourceWorkspaceId`, `source_workspace_id`, `sourceRelation`, `source_relation`,
`sourceDigest`, `workspaceSlug`, `workspace_slug`, `ownerUserId`, `ownerEmail`,
`sponsor`, and the literal fixture values `ws-tasks-1`, `mara-and-finn`,
`ms-ws-tasks-1-t1`, `digest-item-1`. It then asserts the item key set is exactly
`["date","publicId","state","title"]`.

**Extends the audit.** The audit recorded `ITEM_KEYS` as a constant. This is the
same invariant asserted on a real serialised response rather than on the
constant that is supposed to produce it.

### 5. The tasks-to-milestones relationship, stated exactly — **MET, and it is the finding**

The chain, in full:

| Step | Where | Condition |
|---|---|---|
| A Tasks task becomes a Timeline milestone | `src/modules/timeline/server/sync/tasks-milestone-source.ts:135` | `t.is_milestone = 1`, ordered by `t.due_at` |
| Sync is invoked | `server/actions/workspaces.ts:232` `syncMilestonesAction` | owner-only, requires a bound canonical Tasks workspace |
| Milestones are curated | `upsertNodeOverlayAction` (`:386`), `createManualMilestoneAction` (`:440`), `reorderNodesAction` (`:516`) | owner-only, project-scoped |
| Curation is published | `createAudiencePublication` → `publishAudiencePublication` | separate act, mints a token |
| `is_milestone` is written | `src/server/db/apply-template.ts:79` `isMilestone: t.milestone === true` | template must declare it |

**Correction to the recon map given to this package.** The recon stated that
`applyTemplateToWorkspace` "writes `due: t.due` and never sets `dueAt`". That is
no longer true in this worktree: `apply-template.ts:74-81` sets both `dueAt`
(via `resolveTemplateDueAt`) and `isMilestone`. The mechanism is built. What is
missing is that the shipped wedding template declares neither. Measured
2026-08-03T07:13:31Z:

```
tasks 18
dueOffsetDays declared 0
milestones declared 0
lanes {"done":2,"doing":4,"review":3,"todo":9}
```

**So a sponsored couple's Timeline would render empty even if they could reach
it**, and it would stay empty until E05.03 declares milestones and the wedding
date exists to anchor them. The audit reached the same conclusion by a different
and now-outdated route; the corrected route makes the fix much cheaper, because
it is template data rather than code.

### 6. Every venue-facing read path, and none of them touches Timeline — **MET**

Enumerated:

1. `src/app/api/internal/partner-stats/route.ts` — the only production
   venue-facing egress from this app. Bearer `PARTNER_STATS_SECRET`,
   `timingSafeEqual` at `:40`. Returns four scalars (`:100-105`). Asserted in
   the test: the file contains none of `timeline`, `Timeline`, `publication`,
   `audienceShares`, `workspaceSlug`, `tasks`, and does contain all four scalar
   names.
2. `listSponsorActivationDTOs` (`src/server/planning/queries.ts:225`) —
   sponsor-scoped, allowlisted, and has zero production callers. Asserted in the
   E05.10 test.
3. Studio `/hq/account-review` — reads the shared entitlements database only,
   and no venue can reach it (R-043).

`grep -rn "sponsorId|sponsor_id|sponsorSlug" src/server src/app/api` returns no
line that joins to any Timeline table.

**Gap recorded, not fixed here.** `partner-stats` has no small-cell floor. A
`codesRedeemed` of 1 against a venue that issued forty is a statement about one
identifiable couple. That is the R-027 shape on a second endpoint the R-027
entry does not mention. It carries no Timeline content, so it is not an E05.08
defect, but it belongs on the register and with WP-07/WP-05.

### The boundary that is not in scope, stated so it is not papered over

`/p/[slug]` is deliberately search-indexable and is absent from
`src/app/robots.ts:14`. That is **R-031, undecided**. It is a Tasks published
workspace, not a Timeline publication, and it does not resolve through
`resolveAudienceTimeline`. Nothing in this document describes the token-bound
model as covering it. `/s/[token]` and `/share/[token]` are token-bound and
`/s/[token]` sets `robots: { index: false, follow: false, noarchive: true,
nosnippet: true }` (`src/app/s/[token]/page.tsx:29`).

## Test infrastructure added

`src/test/register-server-only.mjs` and `src/test/server-only-stub.cjs`.
`server-only` is a transitive dependency of Next and is not hoisted, so no
module importing it could be tested under `node --test` before this. The hook
uses the synchronous `module.registerHooks` API because tsx transpiles to
CommonJS and the failing lookup is a `require`. It changes no runtime behaviour
and is only loaded by an explicit `--import`.
