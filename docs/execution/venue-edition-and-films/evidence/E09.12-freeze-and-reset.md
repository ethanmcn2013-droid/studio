## 2. The reset

`app/scripts/demo-reset.mjs` · `pnpm demo:reset`

### 2.1 What "reset" means here, because it is not one operation

`app/DEMO_MODE.md` lines 20 to 26 carry a load-bearing safety invariant: demo and
review modes never query the real database. `getCurrentUser()` resolves to a
synthetic id and every read short-circuits to an in-memory fixture module before
any `db` call. That invariant is why a mis-deployed flag leaks nothing, and it is
the reason the obvious shape for this command, "wipe and re-seed", would have
been the wrong one.

Three of the four products have no rows to restore. Their canonical state **is**
their source. So the command splits into three honest kinds of work.

| | What it does | Why |
|---|---|---|
| **Regenerate** | Re-runs `sync-templates.ts`, re-emitting all five template parts to their four generated destinations. | A file derived from a canonical source can drift. This is the only thing in the demonstration that can actually be restored. |
| **Verify** | Renders the whole demo state, hashes it per surface, compares against a pinned baseline. | In-memory fixtures drift in source, not at runtime. A hash mismatch is an edited fixture, and the command names which surface moved. |
| **Report** | Names every surface it cannot reach, with the reason, on every run. | A surface absent from the output is a surface nobody remembers is missing. |

disagree with it.

### 2.3 The determinism proof

The gate's wording is that the same command produces the same state every time.
So: the command, run twice, diffed. Verbatim in
`E09.12-reset-determinism-run.txt`.

- **Run A** ambient clock, `TZ=UTC`. Exit 0.
- **Run B** wall clock shifted **+400 days**, `TZ=Pacific/Kiritimati`. Exit 0.
- **`diff A B`** produced no output.

Both runs did real work: `sync-templates` regenerated four files on each pass, so
this is an end-to-end proof rather than a read-only comparison.

**The proof is only worth something if it can fail, so two negative controls.**

1. `--self-test` injects a change into the rendered state in memory and asserts
   that exactly one surface moves and that it is named. Pass.
2. A real on-disk edit: `name: "Glenmara House, events"` became
   `name: "Glenmara Hous3, events"` in `src/lib/review-suite-fixture.ts`. The
   reset exited 1 and named **four** surfaces: review-fixture, tasks-board,
   timeline and signal. The file was restored immediately and the reset re-run
   clean.

One edit moving four surfaces is the one-story consolidation working. Tasks,
Timeline and Signal derive the venue name from the review fixture rather than
restating it, so there is one place to change and the reset proves it.

### 2.4 The production gate is not wrapped

`seed-wedding.ts`'s header says `--i-understand-prod` must never appear in
automation. The reset **refuses** to forward it:

> demo-reset: refusing. seed-wedding.ts's production gate must be run directly
> and deliberately, never through a convenience command.

Database seeding is opt-in (`--seed-db`), and its arguments pass straight through
untouched. Wrapping a production gate inside a convenience command is how a gate
stops being one.

### 3.3 A change is detectable, proven

Negative control. `Compliments of {sponsorName}` in
`app/src/components/welcome/venue-welcome-card.tsx` was changed to
`With compliments from {sponsorName}`. The check exited 1:

```
[capture-copy-freeze] capture copy has moved since it was recorded
- ../app/src/components/welcome/venue-welcome-card.tsx:65 carries a capture string
  that is not in the manifest (16be9fad6586c6a2): "With compliments from {}"
- ../app/src/components/welcome/venue-welcome-card.tsx no longer carries the
  recorded capture string d963bed55c703e78: "Compliments of {}"
```

Both directions, named. The file was restored and the check re-run clean.

That line is not a string literal. It is JSX text, and the first version of the
extractor missed it, which would have frozen everything on the capture path
**except the one line D-027 point 3 is about**. JSX text extraction was added for
exactly that reason. Two similar near-misses are recorded in §3.4 because the
class of mistake matters more than the instances.

### 3.4 Three filter mistakes, recorded so they are not repeated

A copy extractor is a filter, and every filter is a decision about what does not
matter. All three of these were wrong in the same direction: they dropped the
thing that mattered most.

1. **The copy heuristic required sentence punctuation or a common stopword.** It
   dropped *"Collect final dietary notes"*, which is the single string in this
   manifest most needing to be pinned. The rule is now shaped around what is not
   copy, rather than around what looks like a sentence.
2. **A minimum length of 12 characters dropped `"18 months"`**, nine characters
   with one space, on screen four times in the portal mock a prospect reads. The
   rule now is: the copy filter may drop a string, it may never drop a defect.
   Anything breaking a prohibited claim is recorded whatever its shape.
3. **Only string literals were extracted**, so the couple-facing attribution line
   was invisible. §3.3.

The same class of mistake, in a different check, is recorded in
`E09.11-copy-system.md` §12.5: a citation heuristic that suppressed two real
defects on the live venues page.

### 3.5 What the freeze does not cover

**Rendered output.** A string can be correct in source and wrong on screen
through composition, truncation or a conditional. The runtime counterpart is
`demo-reset.mjs`, which hashes the rendered demonstration state itself, and
`demo-determinism.mjs`, which proves that state does not move with the wall
clock. Between them, source and render are both pinned. Neither is a screenshot
baseline, and a visual freeze is E05.12's, not this task's.

**Anything outside the 14 named surfaces.** The list is a judgement about what is
on screen during a capture. A surface added later is not frozen until it is
added, and the check fails loudly if a listed surface disappears.

## 6. Open questions for the founder

**OQ-9 — the portal has no demonstration path, and the data gate assumes one.**
The gate says "across all four products and the portal". There is no venue-facing
route in studio to demonstrate from, and the only account surface is HQ-gated
operator review which also lists every live venue by name in a picker
(`E11.09-10` finding F-2, critical). So demonstrating the portal today would
either show nothing or show other founding venues.
*Answerable with:* build a read-only venue-facing demo route in studio reading
`getVenueFixture()` behind `access-mode`, which is WP-05's column and probably
half a day; **or** narrow the gate to the four products and demonstrate the
portal from a recorded film frame instead.
**Recommendation: the first.** Beat 5 of the walkthrough is "what you see, and
what you never see", which is the beat that sells the privacy boundary, and it is
the one beat that has no live surface.

**OQ-10 — the second demonstration wedding.** `demo-data.ts` still carries an
older wedding (slug `wedding-planning`) reachable through
`getDemoSharedUpdateDataset`. It predates the one-story determination. Deleting
it is a product change; renaming it silently would recreate the several-venues
problem D-012.1 closed.
*Answerable with:* delete it, or fold it into the one story.

**OQ-11 — the reset's baseline is a pinned hash, and re-pinning is one flag.**
`--write-baseline` re-records the demonstration state. That is correct during
build and dangerous after the capture freeze, because it turns a drift failure
into a keystroke.
*Answerable with:* approve, or require that after 2026-08-22 the baseline may
only move alongside a recorded founder approval.
**Recommendation: the second, from the capture freeze date.**
