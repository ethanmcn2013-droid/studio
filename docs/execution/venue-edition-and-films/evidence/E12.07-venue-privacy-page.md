## 6. The two things this page deliberately does not say

**Both omissions are the point of the page, so they are recorded rather than
left to be noticed.**

### 6.1 Nothing is described as token-bound, private, secure or unlisted

R-031 is open and undecided: `app/src/app/p/[slug]/page.tsx` exists to be
crawled, `app/src/app/robots.ts` does not disallow `/p`, and the page sets no
`noindex` — while `privacy-permission-matrix.md` and the E03.01 role map model
every published surface as token-bound and revocable. **The privacy
documentation describes a different product from the one running.**

So the page says only what E09.11 §6.4 point 3 permits:

> A published page can be found by anyone with the address, including a search
> engine.

and then states the consequence plainly: "So a published plan is a public page.
We do not call it private, unlisted or secure, because it is none of those
things."

**Searched and confirmed absent:** `private link` (0), `secure link` (0),
`unlisted` (0), `only the people you send it to` (0), `encrypted` (0),
`token` (0), `revocable` (0), `expires` in a sharing context (0).

**The gap that remains, and it is not this page's to close.** Whether a
*sponsored wedding* workspace should default to the indexable surface at all has
never been decided. This page is truthful about today's behaviour and silent
about the decision, which is the correct posture for a commercial page and the
wrong posture to leave the programme in. It is raised as a founder question.

### 6.2 No artifact is described as existing when it does not

E03.04 (data processing agreement, security schedule) and E03.05 (couple terms
and privacy notice) are both **`backlog`** — confirmed in `BACKLOG.md` lines 69
and 70. E09.10 §6 Answer 1's conditions of use gate the full GDPR answer on
those existing as drafts a venue could be sent, and on R-017 being decided.
R-017 is open.

The page therefore says the documents "are being written now" and never that
they exist. It also carries P15 verbatim in substance: no region, no country and
no transfer claim, because E03.05 has not verified any.

**Searched and confirmed absent:** `GDPR compliant` (0), `fully compliant` (0),
`certified` (0), `audited` (0), `DPC` (0), `solicitor-approved` (0), `legally
approved` (0), `bank-grade` (0), `military-grade` (0), `100% secure` (0),
`never leaves Ireland` (0), `EU only` (0), `end-to-end encrypted` (0).

## 7. Suppression, stated as the rule and not as the implementation

The page states D-011 point 3's floors — three for behavioural counts, five for
percentages — and adds D-032 R12's asymmetry: access counts are the contract
record and are exact at any cohort size.

**This is deliberately a statement about the rule, and the page says so** ("When
they arrive, this is the rule they arrive under"). R-027 records that
`suppression.ts:33–41` tests only `eligibleWorkspaces < 3` and publishes the
value unconditionally once the population clears the floor, so
`presentBehavioural(1, 40)` returns a value of 1. R-028 records that
`presentRate()` has no production caller at all.

**Nothing untrue is published**, because the figures those functions govern do
not exist yet: every behavioural metric on the live snapshot is `unavailable`.
But the page must not be read as evidence that the implementation was verified.
It was not, and WP-07 owns both fixes.

One claim was checked before it was written: "Three and five are constants in
the code that produces the figures. They are not per-account settings."
`BEHAVIOURAL_MIN_WORKSPACES = 3` and `RATE_MIN_WORKSPACES = 5` are module-level
constants with no override path anywhere in `src`. True as written.

## 8. Forbidden wording

### 8.0 The sweep was broken first, and the fix matters more than the result

The first run of this sweep reported **zero hits for every pattern**, including
patterns that were provably present in the file. The cause: on this Git Bash
build, `grep -i -F` used together **aborts** and returns empty output, which a
`| wc -l` turns into a silent `0`. Combined with `-o` it fails without printing
anything.

Demonstrated rather than asserted:

```
$ grep -n -i "insur" src/app/venues/questions/page.tsx

267:                Whether Signal Studio carries insurance, and where each supplier

$ grep -o -i -F "insurance" src/app/venues/questions/page.tsx | wc -l
0
$ grep -c -i -F "insurance" src/app/venues/questions/page.tsx
/usr/bin/bash: line 1: 12139 Aborted
$ grep -o -i "insurance" src/app/venues/questions/page.tsx | wc -l
2
```

**A clean report from a broken check is worse than no check**, and this
programme has already paid for that once (E09.11 §12.5, the citation heuristic
that suppressed two real defects on the live venues page). It is recorded here
so nobody reinvents it, and `-F` is used nowhere in the re-run.

## 11. The overlap that needs a founder answer

A concurrent package built **`/venues/what-you-see`** under E12.06, titled "What
comes back to you", covering what a venue sees, what it never sees, suppression
and renewal. That is roughly sixty per cent of this page.

Two public pages describing the same trust boundary in different words is
exactly the competing-source failure E09.10 §0 exists to prevent, and the first
paraphrase divergence between them becomes a venue reading two different
scopes.

**Recommendation, for the founder to approve or push back on:** keep both routes
and split them cleanly. E12.06 owns the *mechanism* — how the record arrives,
what Signal Studio administers, what happens at renewal. E12.07 owns the
*boundary* — the three things, the negative list, the suppression rule, sharing
and publishing, the name, and the refusals. The reusable §5.1 block appears once,
here, and E12.06 links to it rather than restating it. Neither page was edited to
achieve that, because the other belongs to a concurrent package.
