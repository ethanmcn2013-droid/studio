## 1. Criterion-by-criterion

### C1 — a new invitation code carries at least 48 bits, computed not asserted

`studio/src/lib/invitation-code.ts`, `app/src/lib/comp-code.ts`.

31-symbol alphabet, 10-character body. `codeEntropyBits()` returns
10 × log2(31) = **49.54 bits**. The tests assert the floor *and* spell out the
keyspace, `31^10 = 819,628,286,980,801`, so the number in the module
documentation is checkable rather than decorative.

Proof: `src/lib/invitation-code.test.ts` → "carries at least the stated entropy
floor, computed not asserted"; `src/server/invitation-code-security.test.ts` →
"clears the stated entropy floor, computed rather than asserted".

### C2 — one generator per repository

Three generators existed. All three are gone:

| Was | Entropy | Now |
|---|---|---|
| `studio/scripts/issue-codes.ts` `generateCode(prefix, 5)` | 31^5 ≈ **2^24.8** | `generateInvitationCode` |
| `studio/src/app/hq/entitlements/actions.ts` `genLicenseCode()` | 31^8 ≈ 2^39.6 | `generateInvitationCode` |
| `app/src/server/actions/comp.ts` `newCode()` | 16^7 = **2^28** | `generateCompCode` |

Proof: `invitation-code.test.ts` → "source contract: one generator, no local
re-implementations" asserts `generateCode(` and `genLicenseCode(` are gone, not
merely unused.

### C3 — uniform draws, with a control that proves the test can detect the defect

All three old generators drew `randomBytes[i] % 31`. 256 = 8×31 + 8, so A–H came
up 9/256 against 8/256: **12.5% more often**.

The test that proves this is fixed carries its own control. In
`app/src/server/invitation-code-security.test.ts` the same run executes the old
biased draw and asserts it **exceeds** the bound the new draw must sit under.
Without that, a bound too loose to detect anything would look like a green test.

The bound was also mutation-proven standalone before being committed. Five
independent trials, 620,000 draws each:

```
trial 1: OLD worst A-H = 22034 (bound 20900) -> TRIPS (test catches it)
         NEW worst A-H = 20140 (bound 20900) -> passes
trial 2: OLD 21880 TRIPS / NEW 20228 passes
trial 3: OLD 21959 TRIPS / NEW 20176 passes
trial 4: OLD 22055 TRIPS / NEW 20367 passes
trial 5: OLD 21958 TRIPS / NEW 20260 passes
```

An earlier draft of this test used 62,000 draws and a 9% bound. That bound sat
almost exactly on the biased mean, so it would have caught the defect roughly
half the time. It was found and corrected by running the control, which is the
reason the control is now permanently in the suite.

### C4–C7 — the share-link store

`app/drizzle/0027_share_link_token_hash.sql`, `app/src/server/share-token.ts`,
`app/src/server/db/share-link-resolver.ts`.

- **C4** `share_links.token_hash` is sha256 hex under `uq_share_links_token_hash`.
  The test mints a link, dumps the entire table and asserts the secret string
  does not appear in it. The database used is built by applying the checked-in
  migration SQL, split on `--> statement-breakpoint` exactly as the runner does,
  so if 0027 stops creating the index the test fails.
- **C5** The hash itself and the public row id are each proven to resolve to
  `null`.
- **C6** A pre-0027 plaintext row still resolves; a backfilled row is proven not
  to open via its public id through the legacy branch, because that branch is
  fenced behind `token_scheme = 'plaintext'`.
- **C7** Both branches of the dual-read resolver are asserted to carry
  `innerJoin(workspaces)` and `isNull(workspaces.archivedAt)` — counted, so
  adding a third unguarded branch fails.

The migration itself was verified through the ledger gate rather than by
inspection: `pnpm db:contract` builds a fresh database, applies the baseline
plus all forwards, and re-runs as a no-op. Index count moves 31 → 32, which is
the unique index. **The comment-before-first-breakpoint trap was avoided** — the
first segment of 0027 contains the header comment *and* the first `ALTER`, so
all three statements run.

### C8 — the budget is spent before the lookup

`app/src/server/actions/comp.ts`. `redeemCompCodeImpl` resolves identity and
calls `redeemWithinAttemptLimits` **before** it touches `comp_codes`. A
source-contract test compares the two string offsets and fails if the order
inverts, because looking up first leaves an unmetered "does this code exist"
oracle, which is the primitive a guessing attack actually needs.

### C9 — everything runs

Registered in `app/package.json`: `share-token-security.test.ts`,
`invitation-code-security.test.ts`. Registered in `studio/package.json`:
`invitation-code.test.ts`.

### C10 — the failure mode is in the source

`comp.ts` states, in the file: the limiter **fails open**, Upstash is **not
provisioned**, so on 2026-08-03 it enforces nothing in production, and entropy
is the control that actually holds. A test asserts that text is present, so
deleting the caveat fails the build.

## 2. The finding that matters more than R-033

**There are two live redemption writers, in two databases, with two security
postures, and couples use the weaker one.**

- `studio/src/lib/entitlements-db/codes.ts` `redeemLicenseCode` has IP-hash
  velocity limiting, a recipient-email lock, a single-use conditional flip, a
  revoked state, per-user idempotency and an audit ledger. It is good.
- `app/src/server/actions/comp.ts` `redeemCompCodeAction` has expiry, an atomic
  quantity claim and per-user idempotency. It has **no recipient lock and no
  revoked state**.

`studio/scripts/issue-codes.ts` writes both, and its own inline comments name
which is which: studio's `license_codes` row is *"sponsor audit / who-issued-
what"*; the Tasks `comp_codes` row is *"runtime redemption surface"*. The path
carrying every guard is the audit copy. The path a couple's browser reaches is
the other one.

The arithmetic that made this urgent, for the code as it shipped:

- prefix = the venue slug, which is public — a Founding 25 venue is named on the
  map and in the film — so it contributes nothing;
- 5 characters over 31 symbols = 28,629,151 candidates;
- a venue with 40 live codes has 40 targets, so ~716,000 expected guesses;
- at 50 requests a second, **about four hours**.

The reward is not a free tier. It is an account bound to a named venue's
sponsorship, consuming a code a real couple was handed, appearing in that
venue's adoption evidence.

R-033 by comparison requires the attacker to already hold a database read.

**What is fixed:** entropy on all three generators, uniform draws, and an
attempt budget spent before the lookup.
**What is not:** the two writers are not merged, there is no recipient lock and
no revocation on the live path, and codes already issued keep 2^24.8. All four
are founder questions in `tasks/E08.06.md`, deliberately not decided here.
