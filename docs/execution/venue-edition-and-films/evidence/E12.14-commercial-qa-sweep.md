## 3. Conversion — two pages had no next step, and both now have one

The rule applied: what is a venue meant to do next on this page, and can it?

| Route | Primary action, after this task | Before |
|---|---|---|
| `/venues` | Join the venue waitlist | unchanged |
| `/venues/demo` | Join the venue waitlist | unchanged |
| `/venues/couple-preview` | Ask me a question → `/contact` | unchanged |
| `/venues/what-you-see` | Ask me a question → `/contact` | unchanged |
| `/v/<token>` proposal | Return the order form to hello@signalstudio.ie | unchanged, one action, per E13.16 §3.1 |
| `/v/<token>` invitation | one action | unchanged |
| **`/venues/privacy`** | **Ask me a question → `/contact`** | **none: two links, both navigation** |
| **`/venues/questions`** | **Ask me a question → `/contact`** | **none: two links, both navigation** |

**Why these two were defects and not merely thin.** Each closes by inviting an
action it did not provide.

`/venues/privacy` closes on the heading *"If something here is not clear, ask."*
and then offered "Read the questions venues ask" and "The Founding 25". Both are
navigation to another Venue Edition page. There was no way to ask.

`/venues/questions` is worse, because it carries E09.10 §6's governing rule
twice — *"Ask, and you get the current answer rather than a comfortable one"*
and *"I do not know, and I would rather find out and tell you than guess"* — and
offered only "The Founding 25" and "What your venue sees". The FAQ is precisely
the surface a venue reaches when it has a question the page did not answer,
which is the exact case that rule exists to handle, so it is the one page where
the ask has to be reachable.

**The fix** adds the same primary action the two sibling preview pages already
use, with the same destination and the same `subject`, so the four secondary
commercial pages hand a venue one next step rather than three different ones.
The previous links are kept as secondary. Verified in the served HTML:

```
/venues/privacy    <a ... href="/contact?subject=venue-edition&...&artifact=venue_privacy_ask">Ask me a question</a>
/venues/questions  <a ... href="/contact?subject=venue-edition&...&artifact=venue_questions_ask">Ask me a question</a>
```

Neither file is a registered experience, so this fix adds no gate failure (§6).

**One conversion gap that is not fixable here.** The `/v/<token>` proposal state
and the E12.09 proposal both end on "complete the order form and send it back".
**There is no order form.** It is `E11.11` §4's deliverable. A venue that says
yes today has nothing to complete.

### 4.1 Two defects found and fixed

**(a) `scrollable-region-focusable`, serious, `/v/<token>` proposal state, 375px.**
The commercial-summary table is `min-w-[420px]` inside an `overflow-x-auto`
container. At mobile width that container scrolls, and a scrolling container
with no focusable content inside it cannot be reached by keyboard at all. WCAG
2.1 SC 2.1.1. A venue reading the proposal on a phone could not see the columns
past the fold without a mouse.

Fixed with `tabIndex={0}`, plus `role="region"` and
`aria-label="Venue Edition commercial summary"`, because a focusable container
with no accessible name is announced as an unnamed group. Re-measured on a fresh
build: `axe_serious=0`, and `tab_stops` rose from 2 to 3, which is the region
becoming reachable.

**(b) Two `h1` elements on `/hq/venue-proposal`.** Fixed under E12.09; see
`E12.09-one-page-proposal.md` §7. Re-measured: `h1=1, skips=0`.

### 4.2 The one remaining violation, and it is systemic

Every one of the twelve remaining serious violations across the six public pages
and the HQ tool is the **same rule and the same colour pair**:

```
color-contrast (serious)
  foreground #71717a  (--ink-quiet)
  background #f4f4f5  (--bg-deep)
  ratio 4.39:1        WCAG AA floor for small text: 4.5:1
```

Node counts per route, at desktop: `/venues` 21 · `/venues/privacy` 5 ·
`/venues/what-you-see` 5 · `/hq/venue-proposal` 12 · `/venues/demo` 1 ·
`/venues/questions` 1 · `/venues/couple-preview` 1.

It hits the small uppercase eyebrow labels, the tabular step numbers and the
form hints — the pattern every new page inherited from `/venues`, which is
E12.04, already approved and already live.

**It misses AA by 0.11.** It is real, it is not dramatic, and **it is not this
task's to change**, because `--ink-quiet` and `--bg-deep` are design-system
tokens used across all 40-plus studio routes. Changing either is a
design-system decision with a blast radius far outside E12, and it would touch
every registered experience surface at once.

**Recommendation:** darken `--ink-quiet` from `#71717a` to approximately
`#6b6b73` on `--bg-deep` backgrounds, or lift `--bg-deep`. Either clears AA
across the whole site in one change. This needs the founder and probably a DS
pass, and is raised in the packet.

```
src/app/venues/couple-preview/page.tsx:251  p7-bare-term  "eighteen months"
src/lib/venue-invitation/copy.ts:39         p7-bare-term  "eighteen months"
```

`copy.ts:39` is a doc comment reading *"Never a bare eighteen months."* — naming
the rule, not breaking it. It needs a citation entry, not an edit.

`couple-preview:251` is the interesting one. **The copy is correct.** It reads:

> Each couple keeps it for eighteen months from the day they open
> it, or three months past the wedding, whichever is later.

The grace rule travels with the term exactly as D-022 requires. It is flagged
because **P7's grace window is line-scoped**: `bareTermHits` slices
`graceWithin: 200` characters out of a **single line**, and JSX wrapped the
sentence so "eighteen months" landed on line 251 and "whichever is later" on
line 253.

**Why this matters more than one false hit.** The pin mechanism only earns its
keep if a count can ratchet toward zero. A false positive pinned at 1 becomes
permanent noise, and a permanent 1 is indistinguishable from a real defect that
appeared later. Any JSX page that wraps that sentence gets the same hit.
**Recommendation:** run the P7 grace window over a joined-line window rather
than a single line. Owner: WP-06.

`check-venue-edition-contract.mjs`, which sweeps for the *retired price

which sweeps for *prohibited claims*. **Recommendation:** WP-06 adds all ten,

## 9. Two things about how this run was done, because both nearly produced a false green

**The build lock.** Three work packages share this worktree. `pnpm build` failed
with *"Another next build process is already running"* because a sibling was
mid-build. Killing it would have corrupted their run. The correct move was to
wait for the lock to go stale and retry, which is what happened.

**A stale server silently invalidated a whole verification run.** After the
fixes, `next start` was restarted and the harness re-run. The harness reported
`/v` still failing and `/hq/venue-proposal` rendering an error page. Both were
wrong. The **old** server still held port 3462, the new one had died with
`EADDRINUSE` into a log nobody was reading, and the rebuild had overwritten the
old server's chunks underneath it. The harness had measured a stale build and a
broken page.

Had the numbers happened to look good, that run would have been recorded as
proof of fixes that had not landed. The port was cleared by PID, the server
restarted, readiness confirmed by an HTTP 200, and every number in §4 comes from
that run. **The lesson is cheap and worth writing down: a verification harness
that does not assert what build it is talking to can report anything.**
