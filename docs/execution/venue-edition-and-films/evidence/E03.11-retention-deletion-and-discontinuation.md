**What this is.** A first draft of the Signal Studio retention, deletion and
service-discontinuation position, written by an AI agent under decision D-016.

**What it is not.** Not legal advice. Not a reviewed instrument. Not a compliance

## 0. The rule this document was written under

> **A retention period that nothing enforces is a false statement.**

So this document is in two halves and they are kept apart on purpose.

- **§1 to §2 report what the code actually does today**, verified by file on
  2026-08-04. Nothing in those sections is aspirational.
- **§3 to §6 draft the policy**, and every rule carries one of three marks:
  **ENFORCED** (code does it today), **BUILT BUT NOT RUNNING** (the code exists
  and nothing calls it on a schedule), or **NOT BUILT** (it is a policy intention
  and no code exists).

A rule marked **NOT BUILT** may not appear on a privacy page, in an agreement, or
in a sales answer as though it were a control.

## 1. What the code actually does today

### 1.1 The retention sweep exists, and it does not run

| Fact | Verified at |
|---|---|
| `PII_RETENTION_MS` is 24 months (30-day months), and `retentionSweep()` shreds identifying hashes for any person whose access ended before the cutoff and who holds no active row | `studio/src/lib/entitlements-db/gdpr.ts` |
| The sweep is invoked from exactly one place | `studio/src/app/api/cron/access-reconcile/route.ts` |
| That route's own header says: *"The endpoint is ready now; enabling the schedule (`vercel.json` crons) is the operator step"* | same file |
| **`studio/vercel.json` schedules one cron, `/api/cron/sponsored-use`. `access-reconcile` is not in it.** | `studio/vercel.json` |
| `app/vercel.json` schedules one cron, `/api/cron/digest`. There is no retention or purge cron in the app at all | `app/vercel.json` |

> **Conclusion, stated plainly: the 24-month purge is implemented and has never
> been scheduled. No personal data is being purged by time anywhere in this
> system today.**

### 1.2 What crypto-shredding actually removes, and what it leaves

`shredPersonPII()` nulls `entitlements.email_hash`, `redemptions.ip_hash`,
`redemptions.user_agent` and `license_codes.recipient_email_hash`, marks the Clerk
id dead, and appends a `shred` event to the hash-chained audit ledger carrying
non-personal counts only.

It leaves the anonymised skeleton: tier, dates, amounts, and the pseudonymous
Clerk id as a join key.

**Two limits that matter and are recorded rather than smoothed over.**

1. **It reaches the entitlements store only.** It does not touch a couple's
   workspace content, and role map §10.3 makes the point precisely: crypto-shredding
   a hashed identifier does not erase free text. A guest's name and health
   information typed into a task title is plaintext in the workspace body and is
   untouched by shredding an email hash.
2. **It is triggered by a Clerk `user.deleted` webhook** at
   `studio/src/app/api/webhooks/clerk/route.ts`, which requires
   `CLERK_WEBHOOK_SECRET`. `studio/docs/INFRASTRUCTURE.md` records that this
   variable *"was unset in prod before the reset; must be set for the shredder to
   be live"*. **Whether it is set today has not been verified in this programme.**

### 1.3 Account deletion, which is real and is immediate

| Fact | Verified at |
|---|---|
| `POST /api/account/delete` is authenticated, deletes only the caller's own account, purges first and calls Clerk admin delete last | `app/src/app/api/account/delete/route.ts` |
| Erasure is unified across Tasks, Notes, Timeline and Signal, running the three module erasures in parallel then the host database, with per-module failures logged and never aborting the others | `app/src/server/account-unified-erasure.ts` |
| Google OAuth refresh tokens collected during the Notes erasure are revoked at `https://oauth2.googleapis.com/revoke`, best-effort | same, line 29 |
| Row-level erasure is hand-rolled and thorough: tasks, comments, activities, attachments rows, share links and their visits, pending invites, notifications, preferences, entitlements, memberships, board metadata, and the workspaces the user owns | `app/src/server/account-erasure.ts` |
| It is **immediate and irreversible.** There is no grace period and no undo | `app/src/app/api/account/delete/route.ts` header |

### 1.4 A verified defect: attachment bytes survive account deletion in production

This is the most consequential finding in this document and it was found by
reading the code rather than the policy.

`account-erasure.ts` collects `attachments.stored_path` for every attachment it
deletes, then removes the bytes with:

```
await unlink(path.resolve(process.cwd(), storedPath));
```

That is a **local filesystem** unlink, and the failure is caught and ignored by
design.

In production, `stored_path` is a **Vercel Blob URL** beginning `https://`, because
`chooseBackend()` in `app/src/server/storage.ts` selects Blob whenever
`BLOB_READ_WRITE_TOKEN` is set, which it is. `path.resolve` on an https URL never
names a real file, so every unlink fails, every failure is swallowed, and **the
attachment bytes stay in Vercel Blob after the account is deleted.**

The correct seam already exists and is already used elsewhere: `deleteBytes()` in
`app/src/server/storage.ts` handles both shapes and calls `del()` from
`@vercel/blob`. It is called from `actions/attachments.ts` and `actions/resources.ts`
and **not** from `account-erasure.ts`.

Verified on both `app` `main` and `claude/integrate-app`.

> **Consequence for this document:** Signal Studio cannot state that deletion is
> complete. Until this is fixed, a couple's uploaded photographs and documents
> outlive their deleted account. This is a build item, not a drafting one.

### 1.5 Backups

- **Nothing takes a backup on a schedule.**
- The Turso account is Free tier, so point-in-time recovery is unavailable, and
  the budget is zero (D-015 Q5).
- The only backup of production is `db-archive/2026-07-31/`: one manual copy, on
  one laptop, of the **previous generation** of databases, never restored.
- A restore has been rehearsed against a local file with the production schema and
  recorded numbers.

Source: `evidence/E08.08-E08.09-observability-and-continuity.md`, `studio/docs/RECOVERY.md`.

> **Consequence: no statement about backup retention windows is true today**,
> because there is no backup regime for a window to describe.

### 1.6 Export

- `GET /api/account/export` is authenticated, resolves the user from the session
  and never from the client, returns a complete machine-readable copy across
  Tasks, Notes, Timeline and Signal, and degrades a module to
  `{ available: false }` rather than failing the whole export. It is shaped for
  Article 20 portability and it is real.
- The **Keepsake** export is a different thing: a self-contained artifact that
  opens with no network, carries the venue's name only on one line in the footer,
  and makes no promise about storage and no claim about the law. It exists as
  `src/lib/keepsake/export.ts` and `src/lib/keepsake/lifecycle.ts` on
  `claude/integrate-app`.
- **Keepsake has no wiring.** `evidence/E06.11-keepsake.md` states it in its own
  words: no route, no download button, and no call site that enforces read-only.
  A couple cannot reach the Keepsake export today.

## 2. The five conflicting retention statements

Role map §10.2 records four. There are five, and at most one can survive.

| # | Statement | Where it is stated | Enforced by code? |
|---|---|---|---|
| 1 | Content "stays until you delete the workspace", plus encrypted backups rolling off on a 30-day window | `app/src/app/privacy/page.tsx` (live) | **No.** No backup regime exists |
| 2 | After termination "you can export your data for sixty days" | `app/src/app/terms/page.tsx` (live) | **No.** Deletion is immediate and irreversible; there is no 60-day window |
| 3 | On account closure "we delete it within sixty days. Backups age out inside ninety days" | `studio/src/app/privacy/page.tsx` (live) | **No.** Deletion is immediate, not within sixty days, and there is no backup regime |
| 4 | Identifying hashes purged 24 months after the entitlement ends; anonymised audit skeleton and financial records kept 6 years | `studio/content/hq/decisions/gdpr-data-lifecycle-policy.md` item 3 | **Built and not running** (§1.1). No 6-year purge exists at all |
| 5 | Keepsake is free, read-only and indefinite while the service exists | D-010 point 3 | **Not built** (§1.6) |

**Statements 1, 2 and 3 also contradict each other**, before any question of
enforcement. Statement 2 promises a sixty-day export window after termination that
statement 1's product behaviour makes impossible.

Role map §12 item 8 records the choice as unresolved and founder decision 8.
**This document does not add a sixth version.** §3 proposes one rule set and marks
the conflict as open until the founder picks.

## 3. The proposed retention rules

Each rule carries its enforcement state. **PROPOSED** means it needs a founder
decision before it may appear anywhere.

### 3.1 The one rule that is settled on the build regardless of the legal answer

Role map §12 item 3 records the Keepsake lawful basis as unresolved, and then
records what is settled anyway:

> **Special-category data, guest contact details and children's data are purged at
> the end of the access term, whichever lawful basis wins.**

That is the firmest thing in this document and it is drafted firmly.

| Rule | State |
|---|---|
| Special-category free text is purged at the end of the access term and never enters Keepsake | **NOT BUILT.** No mechanism exists to identify it, and role map §4 explains why: it is free text in an unstructured store, not a field |
| Guest contact details are purged at the end of the access term and never enter Keepsake | **NOT BUILT** |
| Children's data is purged at the end of the access term and never enters Keepsake | **NOT BUILT** |
| No child data in any venue-facing evidence, and no identifiable child on any published surface | **PARTLY.** No published surface renders photographs or attachments, verified. Titles and tags publish, and nothing filters them |

**The honest position, and it is uncomfortable.** Three of these four are policy
intentions with no code behind them, and the reason is structural rather than
neglect: there is no way to identify special-category free text inside an
unstructured store without reading it, and §5 of the role map records that reading
it collides with the "we do not read your workspace" promise. Role map Scenario 1
sets out the two exits, and both are builds. This is recorded as an accepted
exposure with a required end date, not as a control.

### 3.2 Financial and audit records

| Rule | State |
|---|---|
| Financial and transaction records retained six years for Irish Revenue record-keeping, then purged | **PARTLY.** The retention happens by omission, because nothing deletes them. **No six-year purge exists**, so "then purged" is currently untrue |
| The anonymised audit skeleton is retained alongside them, with the hash chain computed over non-personal fields so shredding never breaks tamper-evidence | **ENFORCED.** `studio/src/lib/entitlements-db/gdpr.ts`, `audit.ts`, with append-only database triggers |

### 3.3 Identifying data in the entitlements store

| Rule | State |
|---|---|
| Identifying hashes purged 24 months after a person's access ends, or immediately on an erasure request, whichever is first | **BUILT BUT NOT RUNNING.** §1.1. The fix is one entry in `studio/vercel.json` |

**PROPOSED, and it is the cheapest item in this document:** schedule
`/api/cron/access-reconcile` in `studio/vercel.json`. Until that happens, the
24-month rule may not be stated anywhere as a control.

### 3.4 Couple workspace content

| Rule | State |
|---|---|
| Workspace content is retained while the account exists and the access term or Keepsake runs | **ENFORCED**, in the sense that nothing deletes it |
| Content is deleted when the couple deletes the workspace or the account | **ENFORCED for rows. NOT ENFORCED for attachment bytes** (§1.4) |
| A stated finite period for Keepsake | **NOT DECIDED.** Role map founder decision 8. D-010 point 3 says indefinite while the service exists, and Article 5(1)(e) wants a stated period either way. This is the sharpest open conflict in the document |

### 3.5 Backups

| Rule | State |
|---|---|
| Any stated backup retention window | **NOT BUILT.** There is no backup regime |

**PROPOSED:** state nothing about backups on any public surface until a backup
regime exists, and remove the two live sentences that describe one. The current
statements are not merely unenforced, they describe a thing that does not exist.

### 3.6 Operational and security logs

| Rule | State |
|---|---|
| Operational logs are retained by the platform and governed by the platform | **Accurate as a description.** `app/src/server/operational-log.ts` defines the distinction and a test fails if the definition is removed |
| No server-scope log line carries content or a credential | **ENFORCED**, proven on seven shapes in `app/src/server/operational-log-contract.test.mjs` |
| A stated retention period for platform logs | **NOT VERIFIED.** Vercel's own retention has not been checked in this programme, and P15 forbids stating it |

## 4. Deletion

### 4.1 What a couple can do today, accurately described

- **Export:** `GET /api/account/export`, immediate, complete, machine-readable.
- **Delete:** `POST /api/account/delete`, immediate, irreversible, unified across
  four products, with Google token revocation.

Both are real and both are credited. Neither may be described as more than it is.

### 4.2 Three qualifications that must appear wherever deletion is described

1. **Attachment bytes are not removed in production** (§1.4). Until fixed, the
   product deletes the record of a file and leaves the file.
2. **Deleting an account destroys workspaces that account owns, including shared
   ones.** R-023, and D-027 point 1 decided it is fixed before Cohort 1 rather
   than at release. Today, one partner deleting their account can destroy the
   couple's shared workspace. No document may describe deletion as safe for a
   shared workspace until that is resolved, and it is answered together with the
   couple-separation question in E03.10.
3. **A removal route for a person who is not an account holder does not exist on
   any surface.** Role map founder decision 1. A guest named in a couple's
   workspace has no route to ask for removal, because there is no contact address,
   no controller name and no removal link on any published page.

### 4.3 Third-party requests

The handling shape is role map Scenario 1, and it is not restated here:
restriction under Article 18 on receipt, unilateral action on any published
surface regardless of the couple, a deadline to the couple for private content,
Signal Studio executing the erasure itself if the deadline passes, a suppression
record so the same data cannot be silently re-added, and confirmation to the
requester.

**PROPOSED, and it needs both a decision and a build:** the deadline to the
couple. Fourteen days is the safer reading, because Article 12(3) allows one month
overall and fourteen days leaves Signal Studio time to act itself. Named rather
than chosen quietly.

## 5. Service discontinuation

The Keepsake promise (D-010 point 3) is free, read-only, indefinite access **while
the service exists**, with a one-click export the couple owns, no storage
guarantee, and never the word "forever". The export is what makes the promise
honest, so what happens if the service ends turns entirely on the export existing.

### 5.1 The proposed commitment

**PROPOSED.** If Signal Studio discontinues the service:

1. Every account holder is told in writing, to the address on the account, **at
   least 90 days before** the service is withdrawn.
2. The export stays available for the whole of that period, and the notice
   contains a direct link to it.
3. The export is self-contained: it opens with no network connection and does not
   depend on Signal Studio existing. That property is already built and tested in
   `src/lib/keepsake/export.ts`.
4. On withdrawal, all personal data is deleted rather than sold, transferred or
   left running. **A commitment not to transfer personal data as part of a
   business sale is deliberately not made here**, because it is the kind of
   promise a founder should make with advice rather than by default. See §7.
5. Published surfaces are taken down rather than left to decay.

### 5.2 What blocks it today

- **Keepsake has no route and no download button.** A commitment whose whole
  substance is "the export is one click" cannot be made while the click does not
  exist.
- The account export at `/api/account/export` does exist and would serve as the
  fallback, but it is a JSON file named after a user id. `evidence/E06.11-keepsake.md`
  is blunt about it: real portability, and not the Keepsake promise.

**PROPOSED:** the 90-day commitment is made only once the Keepsake export has a
route a couple can reach. Until then, the honest venue-facing and couple-facing
sentence is that there is a complete export available today at any time, and that
the discontinuation commitment is being written.

## 6. Opt-outs and suppression

### 6.1 Outreach to venues

The legitimate-interests assessment for venue outreach is LIA-3 in
`evidence/E03.11-legitimate-interests-assessments.md`. The requirements that
belong here are the operational ones.

| Requirement | State |
|---|---|
| Every outreach message carries a plain opt-out in the founder's own words rather than a footer | **BUILT as copy.** `evidence/E11.05-07-outreach-email.md` records the line and its source, D-013 point 4 |
| A "no" or "stop" puts the address on the suppression list immediately, and nothing further is sent from any cohort | **POLICY ONLY** |
| The suppression list is checked before every send | **POLICY ONLY** |
| Outreach carries no open pixel and no link tracking | **BUILT as policy and asserted in the copy record.** `studio/docs/email-system/email-inventory.md` |
| Stopping rule at four touches, and an explicit no stops at one | **POLICY ONLY** |

> **The suppression list is manual and has no store.** A repository-wide search
> for a suppression list, table, file or module returns documentation describing
> one and no implementation. `studio/docs/email-system/sender-architecture.md`
> says so in its own words: *"Founder outreach suppression is manual and
> permanent."* `evidence/E11.05-07-outreach-email.md` carries an unchecked box
> reading "Suppression list live and checked against the cohort (E11.04)".

**PROPOSED:** a suppression list may be a text file, and for 25 venues that is
proportionate. What it may not be is a memory. Requirements: one file, in the
repository or in the operator's own store, appended before the next send, checked
against every cohort, never pruned, and carrying the date and the exact words the
person used. Recorded here so that "manual" means "written down" rather than
"remembered".

### 6.2 Couple-facing and guest-facing opt-outs

| Requirement | State |
|---|---|
| An Article 21 objection route for a supplier or guest named in a workspace | **NOT BUILT.** No contact route on any published surface (role map founder decision 1) |
| A couple's ability to stop venue-facing activation reporting about themselves | **NOT DECIDED.** It follows the lawful basis in role map §12 item 2. If Article 6(1)(f) is the basis, an Article 21 objection applies and there is no route |
| Marketing consent from couples | **Not applicable, and it is a deliberate position.** D-010 point 1: couples are asked for nothing by default, and any case-study use is a separate specific opt-in |

## 7. Decision points. None of these is chosen quietly.

1. **Which retention statement survives?** §2. Five live or recorded statements,
   at most one can be true. Role map founder decision 8. Until this is answered,
   the live pages contradict each other and the product.
2. **Is there a stated finite period for Keepsake, or a dormancy rule?** Role map
   founder decision 8 calls an open-ended read-only archive containing guests'
   health information the least defensible state in the system. D-010 point 3 says
   indefinite while the service exists. **This draft does not invent a period.**
   The safer reading would be a dormancy rule: an archive untouched for a stated
   number of years is deleted after notice to the last known address. It is
   proposed, not adopted.
3. **Schedule the retention cron?** §3.3. One line in `studio/vercel.json`. It is
   the cheapest thing in this document and it converts a written rule into a
   control.
4. **Fix attachment-byte deletion?** §1.4. A verified erasure defect with the
   correct seam already written. Small, and it is the difference between deletion
   being real and being partial.
5. **Correct or remove the three live retention sentences?** §2, statements 1 to
   3. All are on live public pages. This document does not change a live page.
6. **Make the 90-day discontinuation commitment, and does it survive a business
   sale?** §5. The second half is the part that needs advice.
7. **Set the deadline given to a couple on a third-party erasure request.** §4.3.
   Fourteen days proposed.
8. **Approve the suppression-list requirements in §6.1**, and name where the file
   lives.

## 8. Points a solicitor must settle

1. Which of the five retention statements in §2 is the one that should survive,
   and does correcting three live public pages require anything more than editing
   them?
2. Is an open-ended Keepsake archive compatible with Article 5(1)(e) storage
   limitation, and if a finite period is required, does a dormancy rule with
   notice satisfy it?
3. Does the six-year retention of financial records need a stated basis beyond
   Irish Revenue record-keeping, and does that basis reach the anonymised audit
   skeleton attached to it?
4. Is erasure that removes the database rows but leaves the stored file in object
   storage a breach of Article 17, and if so is it notifiable while it is being
   fixed?
5. Where an account holder's deletion request destroys a shared workspace that
   another data subject also contributed to, whose rights prevail, and may Signal
   Studio refuse or defer the deletion to protect the second person (R-023,
   E03.10)?
6. What is the minimum lawful commitment on service discontinuation, and can a
   controller promise that personal data will not transfer as part of a business
   sale without that promise becoming unenforceable against a purchaser?
7. Is a manual suppression list adequate for direct marketing to businesses under
   S.I. 336 of 2011 as amended, and does a business email address at a named
   individual attract the same treatment as a personal one?
8. Does Article 17(2), erasure of data made public, require Signal Studio to
   notify search engines and cached copies when a published wedding page is taken
   down on a third-party request?
