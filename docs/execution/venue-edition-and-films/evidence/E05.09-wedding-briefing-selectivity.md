# E05.09 — is the briefing selective, and has it anything to be selective about?

Evidence for E05.09. Written 2026-08-03 by WP-08 in worktree `_wt-wp08` (app,
branch `claude/wp08-couple`). Criteria written before assessment.

**The E05-E06 audit did not reach Signal.** Nothing here contradicts it; it
extends into ground the audit left unexamined.

---

## The answer, before the detail

**The engine is genuinely selective and it is good.** Six triggers, a hard cap of
three per block, a per-task deduplication so one item cannot be reported three
times, a stated denominator so "surfaced 3" always arrives with "read 41", and a
count taken before the cap so work held back is never described as clear. That
is a real product claim honestly implemented, and it is now pinned by five
tests.

**And on the day a sponsored couple redeems, it has nothing to select.** Not one
task in their workspace carries a date, so the date-driven half of the engine is
dark. The only thing the briefing can say to them is a synthetic observation
about the template the product itself just installed.

The two facts are not in tension. The engine is not the problem; the missing
input is.

---

## Criterion-by-criterion

### 1. A quiet workspace produces an empty briefing, not a list — **MET**

Thirty untouched items produce `isEmpty: true`, `needsAttention: []`,
`readCount: 30`, `triggeredCount: 0`. The empty copy states the denominator:
`readCountSentence` in `src/modules/signal/lib/briefing/voice.ts`, threaded
through `getBriefingEmptyCopy` (`lib/onboarding/personalization.ts`), which
refuses to say nothing crossed on a day when something did.

### 2. Thirty items, three deadlines, three surfaced — **MET**

Test `thirty items with three real deadlines surface three, and say so`.
`readCount` is 30 and the surfaced ids are exactly the three dated ones.

### 3. The cap holds, and held-back work is not called clear — **MET**

Forty overdue items produce three in `needsAttention`, and `triggeredCount`
(counted before `BUCKET_CAP` at `build.ts:196`) is strictly greater. The comment
at `build.ts:186-195` explains why synthetic rows are excluded from that count;
the test asserts the arithmetic rather than trusting the comment.

### 4. One task, several rules, one row — **MET**

An item that is overdue, idle nine days and blocked would be claimed by
`due-soon`, `stuck-work` and `blocked-too-long`. `bestByTask`
(`build.ts:80-93`) keeps the strongest. Asserted across all three blocks.

### 5. A dismissal does not shrink the denominator — **MET**

`suppressed: new Set(["due-soon:dismissed"])` empties the read and `readCount`
stays 1. The keying is `${trigger}:${taskId}`, so a dismissal sticks for the
reason it was given and the same task can return under a different rule.

### 6. The briefing reads the couple's membership, not just the owner — **MET**

**This corrects the recon map supplied to this package**, which recorded Signal
as per-user and concluded that an invited spouse would get "a briefing built
only from their own scope". That is true of the *preference* row
(`analytics_users.clerkId`, `signal-build-for-user.ts:208`) and false of the
data:

- `src/modules/signal/lib/planning-periods/scope.ts:105-111` joins
  `workspace_members` and marks the row `owner` or `member`.
- `src/modules/signal/lib/briefing/tasks-db-source.ts:126-128` filters
  `t.workspace_id IN (SELECT workspace_id FROM workspace_members WHERE user_id = ?)`.

So an invited spouse's briefing does cover the shared wedding workspace. The
recon's practical conclusion survives for Notes and Timeline (see the E05.10
matrix), but not for Signal.

The wedding segment is also already wired: `signal-build-for-user.ts:255` maps
`contextType === "wedding"` to the wedding empty-state voice, and
`planning_periods.context_type` admits `wedding_season`
(`src/server/db/schema.ts:247`).

### 7. What a sponsored couple's briefing actually contains on day one — **MEASURED**

Measured, not asserted. The wedding template as it stands in this worktree,
2026-08-03T07:13:31Z:

```
$ node --import tsx --import ./src/test/register-server-only.mjs ./probe.tmp.ts
tasks 18
dueOffsetDays declared 0
milestones declared 0
lanes {"done":2,"doing":4,"review":3,"todo":9}
```

Fed through the real engine exactly as `applyTemplateToWorkspace` writes it for
a workspace whose `primary_date` is null:

- `readCount` 18.
- Zero `due-soon` items. Zero `crowded-week`. **No wedding task can reach the
  couple's first briefing, because no wedding task has a date.**
- One row does appear: `synthetic:overload`, "Seven items open at once",
  because the template seeds four `doing` and three `review` items and the
  overload rule fires above five (`triggers.ts:236`).

So the first thing Signal says to a couple who has just been given a workspace
by their venue is an observation about the workspace they were just given. It is
not wrong, and it is not what "what needs your attention today" is for.

### 8. No date on the workspace means nothing can be surfaced by date — **MET, and durable**

`resolveTemplateDueAt` (`src/lib/template-anchor.ts:50-58`) returns null when
either the offset or the anchor is absent, and its header states the refusal
deliberately: *a fabricated deadline is worse than an absent one*. That refusal
is right and is recorded here as correct behaviour, not as a defect.

The consequence is the chain:

```
redemption (comp.ts:259) → applyTemplateToWorkspace(templateId, ws)
  → reads workspaces.primary_date  → NULL, because redemption never captures it
  → resolveTemplateDueAt(null, offset) → null for every task
  → tasks.due_at all null, tasks.is_milestone all 0
  → Signal: no due-soon, no crowded-week.  Timeline: no milestones.
```

The test asserts this as a property that holds however E05.03 rewrites the
template: with no wedding date, nothing seeded can be dated, so anything that
reaches the first briefing must be synthetic.

**The same missing input has three separate consequences**, which is why it is
worth naming once: the couple's access term (D-022, `max(redemption + 548d,
wedding + 90d)` cannot be computed without it), the Timeline anchor (E05.08),
and this. Capturing the wedding date at redemption closes all three.

---

## Deliberately not asserted

The template's current counts are **not** pinned as equalities. E05.03 owns the
template and is rewriting it in this same worktree under another package;
asserting `dueOffsetDays === 0` today would booby-trap that work. The numbers
live in this document with the command that produced them; the test asserts only
what stays true either way.
