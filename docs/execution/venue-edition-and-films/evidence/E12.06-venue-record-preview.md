## 1. The premise in the task title had to be re-read, and this is the whole finding

E12.06 is titled "Add the Venue Portal trust-and-renewal preview" and depends on
E07.18, "the portal preview follows the portal being complete." Both E07.16 and
E07.18 read `status: done`, founder-approved 2026-08-03.

**Read only that far, the correct build is a preview of a portal. It would have
been a false statement to a venue about to pay €1,000.**

What the record actually says, in the order it was found:

| Source | What it says |
|---|---|
| `project-control.mjs task E07.16` | `status: done`. First acceptance criterion: "A venue user can authenticate as themselves: a venue-scoped identity exists and the account surface is reachable by it, not by a single shared operator secret." |
| The same record's `evidence` array | Nine entries, and **every one of them records a failure**: `hq/auth.ts:15-25` one shared password for all operators; `project-venue-access.ts:326` `members: []` returned unconditionally; `account-panel.tsx` hardcoded support history and invite-as-a-notice-string; `actions.ts:22-27` any slug accepted with no per-venue authorisation. |
| `evidence/E07.16-venue-identity-lab.md`, which is E07.16's `specPath` | Header: "**options for founder decision. Nothing here is built. Nothing here is approved.**" Audit score: **3 of 13 criteria satisfied, 2 partial, 8 not satisfied.** |
| `RAID.md` R-043, status open | "The Venue Portal has no venue. There is no venue-authenticated route anywhere." |
| E07.16's approval note | "Approved. All of Wave 2 — the E07 audit and the invitation-administration build…" |

Both readings are right. **"Done" here means the audit is done and the
invitation-administration build is done.** It does not mean a venue portal
exists. The approval note says so in its own words.

**D-032 point 1, approved 2026-08-03, then answered the open question:**

> Venue identity at launch is **Option C**. Signal HQ administers invitations on
> the venue's behalf and the venue receives evidence rather than a login. No
> venue-authenticated route is built before 1 September. **A′** is held as a
> two-day follow-on to be decided after the first three venue conversations.
> **B** is not started before the 2026-08-20 UI freeze. R-043 is answered rather
> than left open.

So the task is buildable, and what is buildable is a preview of **what a venue
receives**, not of a portal it reaches. That is what was built.

**This is worth recording once, plainly, because it will recur.** A `done`
status on a task whose title names a thing is not evidence that the thing
exists. On this programme it can equally mean the audit that discovered it does
not exist has been approved. The `specPath` document is the tiebreaker, and it
should be read before any dependent task is built.

## 5. The one thing that must gate publication, stated plainly

**This page describes suppression behaviour the shipped code does not yet
implement.**

- R-027, severity critical, open: `suppression.ts:33-41` tests the population
  only. A behavioural count of 1 in a cohort of 40 is published as `1`.
- R-028, severity high, open: `presentRate()` has no production caller; the only
  rate formatter, `format.ts:44-71`, divides two exact values with no threshold.

The page says a count is withheld below three and a rate below five. That is the
ratified rule (D-011 point 3, D-032 R12) and the brief for this task directed it
to be written that way. It is not yet what the code does, and WP-07 owns closing
the gap.

**Recommendation: this page does not go live until R-027 and R-028 are closed.**
A venue reading a suppression promise, then receiving a report that discloses a
single identifiable couple, is a worse outcome than a venue that read nothing.
The wording does not need to change; the ordering does.
