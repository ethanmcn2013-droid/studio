# E06.05 — three sharing modes, and the one that is not built

Evidence for E06.05. Written 2026-08-03 in worktree `_wt-wp14` (app, branch
`claude/wp14-timeline`). Criteria were written before the assessment.

**Read the concurrency note in `evidence/E06.07-aggregate-viewer-counts.md`
before trusting any file-level claim here.** This worktree was shared with at
least one other live Wave 4 session, and part of criterion 6 was built by that
session rather than this one.

---

## The headline in one paragraph

Two of the three modes already existed and one of them is the best-built boundary
in the codebase. The gap was never cryptography. It was that a couple clicking
"Publish workspace" was told nothing about what publishing does, that a wedding
page was offered to search engines by default, and that password protection was
absent in a way a couple would read as "not needed yet" rather than "not built".
Those three are closed. What is not closed is R-033, and the storage half of the
search opt-in, which a concurrent package claimed mid-session.

---

## The two published products, named, because they are not interchangeable

| | `/p/[slug]` | `/s/[token]` |
|---|---|---|
| Product | Tasks published workspace | Timeline audience publication |
| Renders | `PublishedWorkspace` → `WeddingTheme` | `TimelineArtifact` |
| Access | slug, no token | 256-bit bearer token |
| Database | Tasks | Timeline |
| Was indexable | yes | no, three ways |

The "private link" mode below is `/s` and `/share`. The "intentionally public"
mode is `/p`. Writing a single "published surface" abstraction over the two is
how the privacy documentation came to describe `/p` wrongly in the first place,
and it is deliberately not done here.

## Criterion-by-criterion

### 1. Modes defined against a named product — **MET**

See the table above. Private link spans two products, so it is recorded twice
with different guarantees, because `/s` and `/share` are not equivalent (see
criterion 2's last paragraph).

### 2. The private link, assessed and recorded as existing evidence — **MET for `/s`, QUALIFIED for `/share`**

`/s/[token]`, verified by reading:

| Guarantee | Where |
|---|---|
| SHA-256 digest stored, raw token returned once | `timeline-schema.ts:556-581`, column comment states it |
| Unique index on the hash | `uniqueIndex("uq_audience_shares_token_hash")` |
| Timing-safe compare | `hashesEqual`, called at `qualified-view-store.ts:54` and on the resolve path |
| Explicit published-state gate | `audience-timeline.ts:755`, `publication.state !== "published"` → `{kind:"unpublished"}` |
| Rotate | `publishAudiencePublication:447` sets every prior active share to `rotated` in the same transaction and versions the new one |
| Revoke | `unpublishAudiencePublication:565` revokes every active share in one transaction |
| Optional expiry | `expiresAt`, honoured by `resolveShareAccessState` |
| Rate limit | `allowWrite()` on create, publish and rotate (`actions/audience-timeline.ts:94,173,232,263`) |
| noindex | page metadata, layout metadata **and** an `X-Robots-Tag` header, plus `robots.ts` |

This is recorded as passing evidence and was **not rebuilt**. E05.08 already
proved the publish and unpublish directions behaviourally with a fail-before
mutation; that evidence stands and is not repeated here.

**Qualified, and it matters.** `/share/[token]` is a different mechanism wearing
the same name. `src/server/db/schema.ts:737-767` stores `share_links.token` as a
**plaintext primary key** resolved by raw equality, with no hash and no
constant-time compare. That is R-033's sibling finding. Wave 3's fix for it is on
the `claude/wp07-engineering` branch, which is **not in this tree**, so this
package did not assume it and did not touch it — a third concurrent edit to the
same files was the larger risk. It is recorded, not closed.

### 3. Password mode: deliberately not built, with the sentence shipped — **MET**

Nothing resembling password protection exists. Verified: `grep -rni password`
over `src/server/db/schema.ts` and `src/modules/timeline/server/db/timeline-schema.ts`
returns zero matches. No hashed secret, no attempt limiter, no recovery path.

D-016 forbids implying a capability that does not exist, and an absent control is
exactly how a couple infers one. So the absence is now stated in the product,
where a couple creates a link (`src/components/app/share/share-button.tsx`,
directly above the generate button):

> There is no password on this link. Anyone you send it to can open it, and so
> can anyone they forward it to. Set an expiry, or revoke the link, when you want
> it to stop working.

Three sentences, each a fact, none of them selling anything. The forwarding
clause is there because that is the actual failure mode a couple does not think
about.

**The recommendation is not to build it**, and the reasoning is in the task spec:
the private link is already a 256-bit token held only as a digest with rotate,
revoke and expiry, which is stronger than a password a couple will pick; and a
forgotten-password recovery story on a keepsake is a support burden a sole
founder does not have. A weak password mode would be the one part of this product
that sounds like security and is not.

### 4. `/p` in the robots.txt disallow list, with the interaction stated — **MET**

`src/app/robots.ts` now disallows `/app`, **`/p`**, `/s`, `/share`, `/redeem`,
`/welcome`, `/api`.

The file carries the interaction in a comment rather than hiding it, and it is
repeated here because it is the kind of thing that gets discovered late:

> A `Disallow` stops an obedient crawler fetching the page, which also stops it
> reading a per-page `noindex`. A URL discovered from an external link can still
> be listed URL-only.

Closing that residual needs an `X-Robots-Tag` response header, which cannot be
set per workspace in `next.config.ts` because the header rules are static and the
wedding test needs a database read. The honest position is that **both controls
are needed and the header is the follow-on**, not that robots.txt solved it.

**Also stated, because it is a real consequence.** `/p` is disallowed for every
published workspace, not only wedding ones. A per-slug disallow list is not an
option: it would publish the list of wedding slugs in a file anyone can read.
That trade is decision 3 in the task spec.

### 5. The publish confirmation states plainly what publishing does — **MET**

Before this task, `src/components/app/settings/sections/workspace.tsx` offered
one button, "Publish workspace", above a caption that described the page as
"a real website, not the app" and never mentioned search engines or what ends up
on the page.

Now, directly above the button:

> **Before you publish**
> - Anyone who has the link can open the page. There is no sign-in and no account.
> - Your task titles and tags are on the page. Any names you wrote into them are on the page too.
> - Search engines are asked not to list this page. That is a request they usually honour, not a lock.
> - You can unpublish whenever you want. The link then returns a not-found page. Copies other people already saved stay with them.

Every line is a fact about shipped behaviour. The second line is the one that
matters, because task titles and tags are exactly where guests' and suppliers'
names live. The fourth line refuses the easy overclaim: unpublishing 404s the
route, it does not reach copies other people already have.

The third line was rewritten late in the session, and the reason is worth
recording. It first read "The page is not listed unless you turn search listing
on", which forward-references the opt-in control described under criterion 6 —
a control that does not exist in this branch. D-016 forbids stating a capability
that is not built, and my own copy had done it. It now describes only what
robots.txt actually does, and says plainly that a request is not a lock.

The success toast changed from "Anyone with the link can read the workspace." to
"Anyone with the link can read it. Search engines are asked not to list it."

It is a persistent panel rather than a modal on purpose: a panel above the button
cannot be dismissed unread, and it is assertable by source text.

### 6. Wedding workspaces `noindex` by default, with a couple opt-in — **PARTIALLY MET, AND NOT BY THIS PACKAGE**

This is the criterion to read carefully.

This package designed and built the storage and the rule: an additive nullable
`ALTER TABLE workspaces ADD COLUMN search_indexing_opted_in_at INTEGER`, its
receipt citing D-033 as the authorisation, ledger and journal entries, and a
`publishedWorkspaceSearchVisibility` helper that returns `hidden` for a wedding
workspace with no opt-in and `visible` for everything else.

Mid-session, a concurrent Wave 4 package in the same worktree created **the same
column** under a different name (`search_visibility_opted_in_at`) and wired it
into `src/server/db/schema.ts` with a reference to its own
`src/lib/published-search-posture.ts`. Rather than ship two migrations for one
column, this package **withdrew its own** — the SQL file, the receipt, and both
ledger and journal entries — and re-ran `node scripts/check-migration-contract.mjs`,
which returned ok.

**The final state, checked directly at the end of the session and stated
plainly.** Both packages withdrew. As of the last verification sweep:

```
$ grep -n "searchVisibilityOptedInAt\|search_visibility_opted_in_at" src/server/db/schema.ts
(no matches)

$ ls drizzle/002*.sql | tail -3
drizzle/0024_retire_waiting_lane.sql
drizzle/0025_tasks_completed_at.sql
drizzle/0026_workspace_money.sql

$ node -e "const l=require('./drizzle/migration-ledger.json');console.log(l.entries.at(-1).id)"
0026_workspace_money
```

So there is **no column, no migration, no ledger entry and no `noindex` rule on
`/p` in this branch.** There is also, briefly during the session, a window in
which `schema.ts` carried the column with no migration file — that drift is gone,
but it is worth recording that `check-migration-contract` validates the ledger
and not the schema, so it would not have caught it.

**Criterion 6 is NOT MET.** The opt-in half of D-033 is unbuilt. What this
package delivered is the robots.txt half (criterion 4) and the confirmation half
(criterion 5), and the confirmation panel's third line — "The page is not listed
unless you turn search listing on" — describes the robots.txt disallow honestly
but names a control that does not yet exist. **That line must not ship before the
opt-in does.** It is the first thing Wave 5 has to close, and it is flagged as
such.

### 7. R-033, the tokenless framable embed — **NOT CLOSED**

No founder decision on wedding-workspace embeddability was available, so nothing
was enforced in the route and `scripts/check-frame-headers.mjs` was deliberately
left alone. Guessing at the answer would have meant rewriting a contract test
another lane owns, to enforce a policy nobody chose.

What was done instead is smaller and correct under every option: `/embed` now
receives the same enforced analytics-free CSP as the other couple-facing routes
(E06.07), so a couple's workspace framed inside a stranger's blog is at least not
also measured by a third-party US analytics provider.

The decision is decision 2 in the task spec, with a recommendation of **no**.

### 8. Nothing states or implies legal approval — **MET**

Every string added by this task is a statement about shipped behaviour. No
sentence in the product or in this document claims legal approval, solicitor
review, accountant verification or GDPR compliance (D-016). The capability that
does not exist is named as not existing, in the couple's own words, which is the
form D-016 requires.
