## 1. The one thing this test is for

The access term. Everything else in this walkthrough is ordinary product. The
term is the thing D-022 ratified, R-015 flagged as unimplementable, and a fix
landed for on 2026-08-03. **This test must read `expires_at` out of the database.
It must not read the term off the screen.** The screen has been right and the
database wrong before; that is what R-015 was.

## 3. The state the test starts from, verified 2026-08-04

**The rule is implemented and tested in the app integration branch
(`_wt-integrate` @ `a78f3c3`), and it is not deployed.**

- The arithmetic is `src/lib/venue-access-term.ts`. The database side is
  `src/server/db/couple-access-term.ts`.
- The wedding date is **not** a new field. `weddingDateMsForWorkspace` reads
  `workspaces.primary_date`, and only on a workspace whose `contextType` is
  `wedding` or whose `activeDomain` is `wedding`. An exam date on a student
  workspace can never reach the term calculation.
- The recompute is wired into the paths that write a wedding date, in
  `src/server/actions/planning.ts`, and it fails soft: a failure is reported to
  Sentry and swallowed, so the couple keeps the floor they already had rather
  than losing an onboarding.

**Verified by running `pnpm test` in `_wt-integrate`. Exit 0, 1,263 tests, 0
failures.** The named results that carry this task:

```
✔ with no wedding date, runs exactly 548 days from redemption
✔ treats an unparseable wedding date as no wedding date, never as shorter
✔ never returns less than 548 days, whatever the wedding date says
✔ gives three months past the wedding when that is later
✔ falls back to 548 days when the wedding date is unknown, never shorter
✔ reads primary_date on a wedding workspace
✔ ignores primary_date on a workspace that is not a wedding
✔ recomputes the couple's term wherever a wedding date is written
✔ a sponsored wedding workspace has no member cap, so no seat count exists
```

**Two findings recorded rather than hidden.**

1. The production entitlements database has an `entitlements.wedding_date`
   column, applied 2026-08-03. The shipped code does not use it.
   `grep -n "weddingDate\|wedding_date" _wt-integrate/src/server/db/schema.ts`
   returns nothing. Anyone reading that column expecting the couple's wedding
   date will read null forever.
2. The dirty `app` working tree holds a **second, untracked** implementation of
   the same rule (`src/lib/venue-edition-term.ts`,
   `src/server/db/sponsored-access-term.ts`). Two implementations of D-022 exist
   in the workspace. Whichever is integrated, the other has to go.

## 4. The script

### Step 1 — The rule must be green before a code is minted

- **Run:**
  ```bash
  cd _wt-integrate && pnpm test
  ```
- **Expect:** exit 0, and the nine named results above present.
- **Fail:** STOP. Do not mint a code against a rule that does not pass.
- **Result 2026-08-04:** **PASS.** Exit 0, 1,263 tests, 0 failures.

### Step 2 — Production must not be publishing wedding pages to search engines

- **Run:**
  ```bash
  curl -s https://app.signalstudio.ie/robots.txt
  ```
- **Expect:** a line reading `Disallow: /p`.
- **Pass:** the line is present.
- **Fail:** **STOP. Do not run this walkthrough with a real couple.**
- **Result 2026-08-04:** **FAIL.** Production returns `Disallow` for `/app`,
  `/s`, `/share`, `/redeem`, `/welcome` and `/api`. **`/p` is not among them.**
  The R-031 fix is in `_wt-integrate` and undeployed. Four tests cover it there
  and none of them is running in production.

### Step 3 — Mint an invitation code for a rehearsal venue

**Not run. Needs the entitlements database.**

- **Run:**

  ```bash
  cd studio
  pnpm tsx scripts/issue-codes.ts <rehearsal-venue-slug> ...
  ```
- **Expect:** a code minted by `generateInvitationCode`, which is now the only

- **Pass:** one code, tied to the rehearsal venue.
- **Fail:** if the script mints from anything other than
  `src/lib/invitation-code.ts`, STOP.

### Step 4 — Case A: redeem with no wedding date

**Only a human can do this. It needs a real account.**

- **Do:** open `/redeem/<code>` in a private window, create the account, and
  stop before onboarding. Do not enter a wedding date.
- **Then read the database:**
  ```sql
  SELECT id, workspace_id, started_at, expires_at, notes
  FROM entitlements
  WHERE notes = 'comp:<code>';
  ```
- **Expect:** `expires_at` = `started_at` + 548 days, exactly.
- **Pass:** the difference is 548 days to the millisecond of the day boundary.
- **Fail:** any other value. A shorter one is a critical stop. A longer one
  means a date leaked in from somewhere and must be traced.

### Step 5 — Case B: the long-lead wedding, which is the whole point

**Only a human can do this.**

- **Do:** complete wedding onboarding on the same account with a wedding date
  **more than 458 days after today**. A March 2027 booking for a September 2028
  wedding is the canonical case from R-015.
- **Then re-read the same entitlement row.**
- **Expect:** `expires_at` has moved to wedding date + 90 days.
- **Pass:** the new value is later than the old one and equals wedding + 90.
- **Fail:** if `expires_at` is unchanged, the recompute did not fire. **STOP.**
  This is R-015 still live and it is the failure that lands on the couple in
  public. Check that the workspace's `context_type` is `wedding` or its
  `active_domain` is `wedding`; `weddingDateMsForWorkspace` returns null for
  anything else, by design.

### Step 6 — Case C: the short-lead wedding

**Only a human can do this.**

- **Do:** a second rehearsal account, wedding date 200 days out.
- **Expect:** `expires_at` stays on redemption + 548 days.
- **Fail:** if it moved to wedding + 90, the term went **earlier**, which D-022
  point 3 forbids absolutely. Critical stop.

### Step 7 — The postponement case

**Only a human can do this.**

- **Do:** on the Case B account, move the wedding date twelve months later.
  Then move it one month earlier.
- **Expect:** the first change extends `expires_at`. The second changes nothing.
- **Fail:** any earlier movement is a critical stop.

### Step 8 — The venue's name, and only the name

- **Do:** open the couple's workspace and read the attribution.
- **Expect:** the venue's name in one quiet line. Today that is
  "Compliments of <venue>".
- **Pass:** name only. **No logo. No venue-written welcome message. No badge, no
  "powered by" in the viewport** (D-027 point 3, D-011 point 2).
- **Fail:** anything more is a copy-freeze problem, not a design preference. It
  binds E11, E12.12, E12.13, E13.09 and E14.12: no sales asset may imply a venue
  logo or a venue's own words appear in the couple's workspace.

### Step 9 — OpenGraph carries the venue name only

- **Run:**
  ```bash
  curl -s https://app.signalstudio.ie/p/<slug> | grep -i "og:description\|og:title"
  ```
- **Expect:** the venue name, nothing else about the venue (R-024).
- **Fail:** any marketing phrasing in the unfurl is a stop.

### Step 10 — The first production attachment

**Only a human can do this, and it has never been done.**

- **Do:** upload one file to the rehearsal couple's workspace in production.
- **Expect:** the upload succeeds and the file loads back.
- **Pass:** both.
- **Fail:** if the response is the configured-storage error from
  `src/server/storage.ts` (*"Storage not configured: set BLOB_READ_WRITE_TOKEN
  in Vercel project settings"*), the EU Blob store is provisioned but the token
  is not on the app project. That is a five-minute fix and a total failure if it
  is discovered by a couple instead.

### Step 11 — Clean up, deliberately

**Only a human can do this.**

- **Do:** record what the rehearsal left behind: a Clerk account, a workspace, a
  redeemed code, an entitlement row, and possibly a Blob object. Decide what is
  removed and what is kept as evidence, and write it down.
- **Note:** permanent deletion is not something this session performs.

## 6. What I would tell the founder

The term arithmetic is right, it is tested against the exact case that would
have hurt, and the wedding date reaches it through the field the couple already
fills in rather than a second one nobody would keep in step. That work is good.

**It is not deployed, and neither is the noindex fix that goes with it.** Both
travel in the same app integration branch. Until that branch ships, running this
walkthrough against production tests the old flat 548-day term and publishes the
rehearsal couple's page to search engines while doing it.

The order I would take it in: deploy the branch, run steps 4 to 7 against a
rehearsal couple, then run step 10, then contact a venue.
