# CR-005 — E08.04 requires database row-level security, which the platform does not have

**Raised:** 2026-08-03 by Claude Code (Wave 3, WP-07)
**Status:** open — **awaiting founder decision. The baseline is unchanged.**
**Affects:** E08.04, and the release-gate evidence that cites it

---

## Why this needs change control

E08.04 is titled *"Complete multi-tenant data isolation and database row-level security for
venues and couple workspaces."* It is p1, release-blocking and on the critical path.

**Turso/libSQL does not support row-level security.** There is no RLS anywhere in either
repository, and the source says so itself. This is not work that was skipped. It is work
the platform cannot accept, so the task cannot be satisfied as written by any amount of
effort.

Changing what a release-blocking task requires is a scope change (WORKFLOWS §5), so it
stops here for your decision rather than being quietly reinterpreted. Recording it as
"done, near enough" would be exactly the kind of silent reconciliation this project
forbids.

## What was built instead

WP-07 delivered the strongest isolation the platform does support, and verified it:

1. **Application-level tenant scoping**, with the scoping rules extracted into
   `src/server/tenant-scope-rules.mjs` so they are data rather than a habit.
2. **A CI gate** that fails the build on an unscoped query, so "every query remembers to
   filter" stops being a discipline and becomes a check.
3. **A behavioural negative suite** — `cross-tenant-negative.test.ts`,
   `cross-tenant-isolation.test.mjs`, `tenant-scope.test.mjs` — that asserts one tenant
   cannot read another's rows, rather than asserting that the code looks right.

The verifier's finding is worth repeating plainly: this is **not** equivalent to RLS. RLS
fails closed at the database, below the application. What exists fails closed at the
application layer and depends on the gate staying green. It is materially better than
unenforced convention and materially weaker than the title claims.

## The options

**A. Amend the task to what the platform can deliver.** Retitle E08.04 to "Complete
multi-tenant data isolation for venues and couple workspaces, enforced by application-level
scoping, a CI gate and a behavioural negative suite." Acceptance criteria follow. The
release-gate evidence then describes a control that exists.

**B. Keep the title and accept the task can never pass.** E08.04 stays permanently
unsatisfiable and blocks its release gate forever. Not recommended, but it is a legitimate
way of recording that the platform choice has a cost you are not willing to paper over.

**C. Change the platform.** Move the entitlements and workspace data to a database with
real RLS. This is not a 29-day change and is not recommended before 1 September, but it is
the only option that satisfies the title as written, and it should be recorded as the
long-term answer if isolation-at-the-database is something you want.

## Recommendation

**Option A**, with C recorded as a post-launch consideration rather than dropped.

The reason is that B and C both leave the release gate citing a control that does not
exist between now and 1 September, which is the same class of problem as R-028: a control
named in a document and absent from the running system. A is the only option where the
gate evidence and the code agree.

**Whichever you choose, the honest sentence for any venue-facing or legal-facing document
is that isolation is enforced in the application and verified by tests, not enforced by the
database.** Nothing should say or imply otherwise (D-016).

## Impact if Option A is approved

- **Schedule:** none. The work is already built and verified.
- **Scope:** E08.04's title and acceptance criteria change. No other task changes.
- **Release gate:** the gate can then be evidenced honestly. Today it cannot be.
- **Risk:** a new RAID entry recording that isolation is application-enforced, so any
  future direct-database access path (an analytics reader, an ops script, a BI tool) is
  outside the control and must be assessed separately. **This is the real residual risk and
  it should be written down whichever option is chosen.**
