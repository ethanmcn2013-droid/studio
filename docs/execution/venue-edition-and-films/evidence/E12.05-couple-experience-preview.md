## 3. The finding that changed the page: a bar that does not exist

`src/app/venues/page.tsx:180-189` renders, inside the hero workspace mock, a
persistent identity bar reading **"Sponsored by Glenmara Estate"** across the
top of the couple's workspace, with a source comment describing it as the venue
identity line. The page's prose says the couple "see your venue's name at the
top."

`grep -rn "Sponsored by" app/src` returns **nothing**. There is no persistent
venue bar in the product. What exists is a dismissible card anchored to the
**bottom** of the Tasks board (`fixed inset-x-0 bottom-6`), shown once, which
the couple can close permanently.

This preview therefore does not depict a persistent bar, and says explicitly
that the card "is not a banner that follows them around."

**Returned as a boundary request to E12.04.** The `/venues` hero mock and the
sentence "they see your venue's name at the top" describe a surface that is not
built. It is either a product decision to build (a persistent name line) or a
copy correction. It is E12.04's, not this task's, and E12.04 is Done and
approved, so it is raised rather than edited.

## 8. The experience registry, and how it was not broken

A new route is a newly discovered experience, so
`experience:validate --product=studio` reported
`studio.page.venues-couple-preview: discovered experience is not registered`.

`experience:discover --write` was **not** run. I-014 records what it does: it
rebuilds the whole registry, silently registers the two unresolved
`__design-lab/delight` routes that are awaiting a founder call, and resets
`lastReviewedAt` on seven entries, destroying the 2026-08-03 human re-baseline.

Instead, `discoverRegistry` was called in a throwaway script to compute the
entry and its materiality hash, and the entry alone was merged into
`registry.json`. Three invariants were asserted before the write and the script
refused to write unless all three held:

1. `writeStableJson(JSON.parse(original))`, normalised to CRLF, is
   **byte-identical** to the file on disk. Proved true, so the serialiser
   reproduces this file exactly and cannot silently reformat it.
2. Every pre-existing entry is byte-identical after the merge.
3. Pre-existing entry order is unchanged.

Result: `1 file changed, 88 insertions(+)`. No deletions. Final hash
`d812165a05a8a0b3`, coverage `none/none/none`, which validates because the
registered hash **matches** the discovered hash. The coverage rule at
`scripts/experience/lib.mjs:573-579` only demands complete coverage when a
registered hash **differs** from the fresh one, which is the unsatisfiable case
I-014 describes. A new entry registered at its true hash does not enter it.

**One correction, recorded because it is exactly the trap.** The entry was first
written at hash `ccd80a247db7c11e`, then the file was edited once more to make
the E09.11 §6.3 collaboration line verbatim rather than paraphrased. Validate
immediately reported `changed experience lacks complete fixture, screenshot, and
accessibility coverage` — the unsatisfiable failure I-014 describes, produced by
a two-line copy edit. The single field was corrected to `d812165a05a8a0b3` by
the same three-invariant script. The lesson worth keeping: **register the route
last, after the copy is final**, because on this repository every subsequent
edit to a registered surface costs a hand re-baseline.

## 9a. A worktree hazard worth recording, because it produced two false reds

Several WP-13 tasks ran concurrently in the one worktree, `_wt-wp13`. Three
observable consequences, all transient, none a defect:

1. **`pnpm build` failed twice with errors that were not in this code.** Once
   with `The export NO_THIRD_PARTY_HEADER was not found in module .../venue-invitation/paths.ts`,
   which was a sibling mid-refactor between renaming an export and updating its
   two importers. Once with
   `ENOENT: .next/static/<hash>/_clientMiddlewareManifest.js`, which is two
   `next build` processes writing one `.next` directory. Both cleared on retry,
   and the build passed exit 0 four separate times either side of them.
2. **`next start` served a stale build**, because a server started before a
   rebuild keeps the old output in memory and `pkill` does not reach a
   Windows-spawned node process. Verification was redone on a fresh port after a
   fresh build, and the assertions in §7 are from that run.
3. **`ds-check` went from green to red** during the session on a file this task
   never opened.

**The rule this implies:** a gate result from a shared worktree is only evidence
if it is reproduced after the concurrent lanes settle. Every green in §7 was
confirmed on a final run at the end of the session, not on its first observation.
