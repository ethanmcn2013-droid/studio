The 2026-08-03 checkpoint's R-033 work moved the share-link credential check out

### 2.1 The one that could not have run

`share-token-security.test.ts` is a good test file. It applies the checked-in
migration `0027` SQL to a real SQLite database, splitting on
`--> statement-breakpoint` exactly as the runner does, then exercises the real
resolver against it. It proves the guest secret never appears anywhere in
`share_links`, that the stored hash is not itself a credential, and that the
UNIQUE index refuses a duplicate at the database level rather than in
arithmetic.

It also imported `resolveShareLinkRowWith` from `@/server/db/queries`, which
begins `import "server-only"` — a specifier the Node test runner cannot resolve,
and which the resolver module's own docstring correctly identifies as the reason
it was extracted in the first place:

```
Error: Cannot find module 'server-only'
Require stack:
- src\server\db\queries.ts
- src\server\share-token-security.test.ts
✖ fail 1
```

Its "source contract" block additionally sliced `queries.ts` from a function
that does not live there, producing an empty string that every assertion in the
block would have matched against. The file has since been corrected by its
owning group and now runs.

The lesson generalises, and it is why section 4 exists: **a test file's
existence says nothing about whether it runs.**

## 4. The journey, mapped, and the map kept honest by CI

The sponsored journey runs: a venue is invited, pays, receives a founding
number, issues an invitation; a couple redeems it, plans, publishes; the venue
is shown a number. It crosses both repositories, so each carries a manifest for
its own segments at `contracts/sponsored-journey-coverage.v1.json`.

`pnpm journey:coverage` expands `pnpm test` — following `pretest` and any
`pnpm <script>` it chains to — into the set of files CI actually runs, then
fails when a file named as covering a segment is missing **or is not in that
set**. An orphaned test file is a hard failure. That is the defect from section
2, turned into something that cannot happen quietly again.

Every segment is either covered or declared uncovered with a reason and an
owner. There is no third state, and a segment that is neither fails the check.

The checker's own rules are proven by `--self-test`, which runs in CI:

```
check-journey-coverage --self-test
  ok    the entry script's own files are seen
  ok    a chained `pnpm test:extra` is followed
  ok    pretest is followed
  ok    an unreferenced script is not counted as run
  ok    a wired, existing covering test passes
  ok    an ORPHANED covering test fails — the defect this check exists for
  ok    a covering test that does not exist fails
  ok    a segment with neither coverage nor a declaration fails
  ok    a declared gap with a reason and an owner passes
  ok    a declared gap with no owner fails
  ok    a segment cannot be both covered and uncovered
```

## 5. The gaps, stated plainly

### No browser, responsive or device coverage exists. The task title asks for it.

Nothing anywhere drives redeem → plan → publish through a browser. Playwright is
installed in the app repository and runs under `pnpm experience:test`, but that
suite covers experience-quality fixtures, not the venue-to-couple path, and it
is not part of `pnpm test`. No breakpoint test, no device profile, no throttled
connection. Every segment above is proven at the module and query level only.

I-014 also establishes that the studio capture plan cannot reach `complete`
coverage for **any** surface, piloted or not — a structural gap in the
Experience Quality OS, not a chore someone skipped.

Building a browser suite before the 2026-08-20 UI freeze is a scope decision.
It is raised as a founder question rather than started.

### Attribution is deliberately untested, because testing it would pin a bug

R-029 is open: every adoption definition counts **workspaces**, the attribution
join runs on a **subject**, and the Tasks call site passes a different subject
id from the other three products. A test written against today's behaviour would
lock the wrong unit in place. Declared uncovered with R-029 as the owner.

### Renewal and lapse have nothing to test

No invoice is generated. No renewal notice is sent — the `renewal-upcoming` and
`payment-failed` templates are written, registered and exercised by the render
test, but studio has no sender at all. No dunning or grace transition exists for
a venue. The one part that *is* covered is the part that matters most: that a
lapsed licence stops new issuance only and never shortens a redeemed couple's
access.

### One venue-facing read has no suppression floor, and that is now pinned

`src/app/api/internal/partner-stats/route.ts` returns a behavioural count
(`reachedBoard`) with no D-011 floor. It is not a disclosure today because its
only consumer is the founder-only `/hq/marketing` roll-up. It becomes R-027 on a
new surface the moment D-027 point 4's per-venue adoption evidence is turned on.
The boundary test that pins this — and proves the route projects four aggregate
numbers and can reach no couple content — was orphaned. It now runs.
