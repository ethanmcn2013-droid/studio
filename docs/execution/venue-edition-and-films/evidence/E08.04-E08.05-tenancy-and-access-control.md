## 0. The headline, before any detail

Two things a reader should take away before anything else.

**One.** The task title E08.04 asks for "database row-level security".
**There is none, and there will be none by 1 September.** Both databases
run on libSQL/SQLite over Turso, which has no row-level security and no
per-row policy engine. This is not a setting that was left switched off —
the capability does not exist on the provider. The control that actually
exists is application-level scoping plus a static CI gate, and that is a
materially weaker thing: it detects a forgotten predicate, it does not
prevent one. Nothing beneath it fails closed. E08.04 cannot be completed
as titled and a change request is recommended (see §6).

**Two.** E08.05 asks for role-based authorisation "across venue owners,
managers, viewers and couples". **No venue-authenticated route exists
anywhere in the product** (R-043). The three-role capability matrix in
`studio/src/lib/account/roles.ts` governs four founder-facing review
panels and nothing else. E08.05 is honestly **documented-only** for the
venue half, and partially built for the app half.

## 1. What the audit found, including in its own predecessor's work

An interrupted earlier run of this task left a committed checkpoint
(`_wt-wp07` `a5324b3`, `_wt-wp07s` `7cb50d5`) that was explicitly
unverified. It was audited adversarially rather than accepted. Four
findings, all verified by mutation rather than by reading:

### 1.1 The tenant gate had a verified false negative — FIXED

The static gate accepted any token from its list appearing **anywhere**
after `.from(`, and `.id` was on that list. So this read:

```ts
db.select({ title: tasks.title })
  .from(tasks)
  .innerJoin(users, eq(users.id, tasks.createdBy));
```

has no tenant predicate of any kind and **passed the gate green**,
because the join's ON clause contains `users.id`. Verified by writing
exactly that file into `src/server` on 2026-08-03 and running the gate:
green.

A join is a relationship, not a restriction. Fixed by splitting the token
list by strength in `app/src/server/tenant-scope-rules.mjs`: strong tokens
(which name a tenant column — `workspaceId`, `userId`, `sponsorId`,
`workspaceSlug`) count anywhere after `.from(`; weak bare-column tokens
(`.id`, `.token`, `.slug`, `.code`, `.email`) count only inside `.where(`.

**The tightening cost nothing.** Measured across all four data surfaces:
247 governed reads, 8 waived, and **zero** new violations under the
stricter rule. No legitimate read was relying on the loophole.

### 1.2 The gate's own sensitivity was never proven — FIXED

`tenant-scope.test.mjs` could only ever show that the detector finds
nothing in a repository that currently passes, which is exactly the
evidence a silently broken detector also produces. The rules are now a
separate module with `app/src/server/tenant-scope-rules.test.mjs` running
them over 22 synthetic statements whose correct answers are known —
including the false negative above, pinned as a permanent regression test.

### 1.3 The venue capability guard did not guard — FIXED

`studio/src/lib/account/role-matrix.test.ts` was written by the
checkpoint, and `roles.ts` cited it in its own header as the enforcement
of "no venue role may ever hold a capability reaching couple content".
Two independent defects:

- **It was never wired into `pnpm test`.** It had never run in CI once.
- **Even when run, it could not detect the thing it existed to detect.**
  It iterated its own hand-written copy of the capability list, because
  `AccountCapability` was a bare union type and a type cannot be
  enumerated at runtime.

Proven by mutation: a capability literally named `view_couple_notes` was
added to `roles.ts` and granted to the owner role. The test
"declares no capability that names couple content" **passed green**.

Fixed by making the capability list a runtime value with the type derived
from it (`ACCOUNT_CAPABILITIES`), exporting `ACCOUNT_ROLES`, and having
the test read the production lists. Re-run against the same mutation:
**4 tests fail**, including the couple-content test. Green before, red
after — that is the whole difference between a guard and a decoration.

### 1.4 Every isolation test was a source inspection — FIXED

`cross-tenant-isolation.test.mjs`, `tasks-security-regression.test.mjs`,
`planning-security-contract.test.mjs` and `tenant-scope.test.mjs` all read
source files and assert about their text. **Not one of them executed a
query.** So the honest answer to "prove an id from workspace A is
invisible in workspace B" was that nothing proved it.

Added `app/src/server/cross-tenant-negative.test.ts`: a real in-memory
libSQL database, two workspaces owned by two people, one row per tenant in
nine sensitive tables, and a per-object assertion that a scoped read
returns the caller's row and returns **nothing** when handed the other
tenant's primary key. It carries a **control case** asserting that the
unscoped read really does return both tenants' rows, so the negative
assertions cannot pass vacuously against an empty table.

### 1.5 Kept, because it is correct

The checkpoint's Signal HQ session-token rewrite (v1 → v2) is good work
and was kept unchanged. The v1 cookie was `sha256("signal-hq-session:v1:"
+ password)` — derivable offline by anyone holding the password, an
offline oracle for the password itself, and carrying no server-side
expiry. v2 is `v2.<issuedAt>.<HMAC>` over a PBKDF2-derived key. Its tests
in `studio/src/lib/hq/auth.test.ts` are written to fail against v1 and do.

### The four data surfaces

Until 2026-08-03 the gate scanned `src/server` only — the Tasks data layer
and nothing else. Signal, Notes and Timeline each carry their own database,
schema module and tenant key, and none was scanned.

| Surface | Schema | Tenant key |
|---|---|---|
| tasks | `src/server/db/schema.ts` | `workspace_id` |
| signal | `src/modules/signal/server/tasks-db/signal-tasks-db-schema.ts` | `workspace_id` |
| notes | `src/modules/notes/server/db/notes-schema.ts` | `user_id` |
| timeline | `src/modules/timeline/server/db/timeline-schema.ts` | `workspace_slug` |

### Known limitations of the control, recorded rather than hidden

1. **It is a detector, not a boundary.** A read that is scoped to the
   wrong workspace id passes it. Only the runtime guard and the auth choke
   points constrain which id is used.
2. **Tokens are matched as substrings**, so a local variable named
   `taskId` counts as evidence even though it is not a column reference.
   Accepted, and pinned as an explicit test so it is a recorded property
   rather than a surprise. Parsing TypeScript is a far larger mechanism
   than the risk warrants.
3. **`isolation-ok:` waivers are honoured on trust.** Eight exist. The
   gate checks that a human wrote a reason, not that the reason is good.
4. **404-versus-403 is proven at the data layer only.** The data layer
   returns empty, which is what lets a route render 404. Only
   `api/attachments/[id]` and `api/calendar/[workspaceId]` were confirmed
   to do so. A route-level sweep is not done.

## 3. E08.05 — the role and permission matrix

### 3.1 Venue-side roles

**Status: specification, not a running control.** No venue holds any of
these roles because no venue-authenticated route exists (R-043). The
matrix governs four `/hq/account-review` panels, which are a founder-facing
review fixture. Do not cite it as evidence that venue authorisation is
implemented.

| Capability | Owner | Manager | Viewer | Enforced by |
|---|---|---|---|---|
| `view_usage` | yes | yes | yes | `roleCan()`, `usage-panel.tsx` |
| `view_reports` | yes | yes | yes | `roleCan()`, `reports-panel.tsx` |
| `download_reports` | yes | yes | **no** | `roleCan()`, `reports-panel.tsx` |
| `edit_reporting_preferences` | yes | yes | **no** | `roleCan()`, `account-panel.tsx` |
| `request_access` | yes | yes | **no** | `roleCan()`, `access-panel.tsx` |
| `manage_members` | yes | **no** | **no** | `roleCan()`, `account-panel.tsx` |

Every cell is asserted in `role-matrix.test.ts`, and the recorded matrix
is now cross-checked against the shipped module in both directions.

**A discrepancy that should not be smoothed over.** R-043 and
`studio/docs/venue-portal/ROLES_AND_PERMISSIONS.md` describe **four**
roles (adding a Signal operator) and a **thirteen-row** matrix, with a
`sponsor_members` lifecycle table. `roles.ts` implements three roles and
six capabilities, and `sponsor_members` does not exist — grep across
`studio/src`, `studio/scripts` and `studio/drizzle-entitlements` returns
nothing. The document describes a design; the code is a different, smaller
thing. Neither has been reconciled and this evidence does not reconcile
them.

### 3.2 What no venue role may ever hold

The venue sees aggregate access evidence and nothing else — not Notes, not
Tasks, not an unpublished Timeline, not a briefing, not a comment, not an
attachment, not a collaborator (D-011, D-027 point 4).

Three mechanisms hold that boundary, in depth:

| Layer | Mechanism | File |
|---|---|---|
| Capability naming | No capability may name couple content or couple identity | `studio/src/lib/account/role-matrix.test.ts` |
| Module reachability | No venue-facing module may reach the app database (`TASKS_DATABASE_URL`); the venue projector may not fetch at all | `studio/src/lib/hq/hq-authorization.test.mjs` |
| Projection | The sponsor-scoped DTO may not carry a workspace handle or any content field | `app/src/server/tenant-scope.test.mjs` invariant 3 |

The third is the load-bearing one. The `workspace_sponsorships` row **does**
hold the workspace id in the database — that is unavoidable, it is the
join. The boundary is therefore a **projection rule, not a storage rule**,
and that is stated in `cross-tenant-negative.test.ts` so no future reader
mistakes the data model for the control.

### 3.3 Couple and collaborator roles (the app)

The product database has **two** workspace roles, not four:
`role text $type<'owner' | 'member'>` in `app/src/server/db/schema.ts`.
There is no viewer, no manager and no guest role in the app. Any document
describing a richer app-side role set is describing a design.

| Actor | Where the role lives | Enforced by |
|---|---|---|
| Couple (workspace owner) | `workspace_members.role = 'owner'` | `getActiveWorkspace()` validates cookie membership before honouring it; `requireWorkspaceOwnerWith()` re-authorises at the data boundary |
| Collaborator (workspace member) | `workspace_members.role = 'member'` | same choke points; membership checked before every mutating action |
| Guest (share link holder) | no row at all — a token, not a role | `resolveShareLinkRowWith()`, hashed lookup, inner join to a non-archived workspace |
| Venue | **no identity exists** | nothing. See R-043 |
| Signal HQ operator | shared password, not a person | `verifyHqToken()` |

**Every role check runs server-side.** `getCurrentUser()` fails closed in
production with no dev-user fallback, asserted in
`cross-tenant-isolation.test.mjs`. Capability is never enforced only by
hiding a control in the UI: `roleCan()` gates render, and the data-layer
choke points gate access independently.

### 3.4 Signal HQ session security

| Property | v1 (until 2026-08-03) | v2 | Test |
|---|---|---|---|
| Derivable from the password offline | **yes** | no | "the token is not derivable from the password alone" |
| Leaked cookie discloses the password | yes, one unsalted SHA-256 | no, PBKDF2 150k | same |
| Server-side expiry | **none** | 12 h, inside the signed token | "expiry is carried inside the token" |
| Forgeable by editing the issue time | n/a | no | "the signature cannot be forged by editing the issue time" |
| Survives password rotation | yes | no | "a token minted under one password does not verify under another" |

All twelve malformed-input cases fail closed. Verified: `tsx --test
src/lib/hq/auth.test.ts` green, and `hq-authorization.test.mjs` pins that
`proxy.ts` verifies rather than recomputing, that every `/hq` surface is
gated or waived in writing, and that only `auth.ts` may mint a token.

**What this still is not, stated plainly.** It is a shared password. There
is no per-person identity, no revocation of one holder without rotating
for everyone, and no audit trail attributable to a named person. **A venue
must never be given this password** — it opens every HQ room, not a
venue's own view.

## 6. What is not done, and what needs a founder decision

1. **E08.04 cannot be completed as titled.** "Database row-level security"
   is not available on Turso/libSQL. Recommend a change request recording
   that the control is application-level scoping plus a CI gate plus a
   behavioural negative suite, and that no evidence record may call it
   row-level security. **Founder question 1.**

2. **E08.05's venue half is documented-only.** There is no venue-
   authenticated route, `sponsor_members` does not exist, and building a
   real venue account before the 2026-08-20 UI freeze is not credible.
   R-043 recommends Option C for 1 September: Signal HQ administers and the
   venue receives evidence rather than a login. **Founder question 2.**

3. **The role documentation and the code disagree** — four roles and
   thirteen rows in `ROLES_AND_PERMISSIONS.md`, three roles and six
   capabilities in `roles.ts`. Recorded, not reconciled. Reconciling it is
   a decision about what a venue may do, not a code cleanup.

4. **A route-level 404-versus-403 sweep is not done.** Two routes were
   confirmed. The data layer is proven; the routes above it are not.

5. **Studio `npm test` is flaky.** Run 1 exited 1 with
   `src/lib/entitlements-db/founding-numbers.test.ts` failing at file
   level while all 39 of its subtests passed; run 2 exited 0 with 421 + 38
   passing. In isolation it passes. This is another group's file (E08.02)
   and is recorded here because an intermittent red in a security-adjacent
   suite will otherwise be explained away by whoever meets it next.

6. **The HQ session is still one shared password.** v2 fixed derivability,
   password disclosure and expiry. It did not create identity. Every
   action in Signal HQ remains unattributable to a person.
