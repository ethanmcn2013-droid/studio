## Objective

Make an uploaded file be what it says it is, keep it private to the workspace
that uploaded it, and state plainly which parts of this task's title are not
built.

## Business reason

A couple's workspace will hold photographs, supplier quotes and signed
paperwork, and those documents name people who never agreed to anything. A file
that can lie about its type is a route to serving script from a Signal Studio
origin. A file that is stored where anyone holding a URL can read it is a
disclosure with no attacker required.

## Intended outcome

1. An upload is accepted only when its declared type is on an allowlist AND its
   own leading bytes agree with that type.
2. The MIME type recorded in the database — which the download route later
   serves as `Content-Type` — is the validated one, never the client's string.
3. Blob-backed downloads stream through the authorized route rather than
   redirecting to a URL the browser cannot authenticate.
4. The absence of malware scanning is written down with its cost, rather than
   implied to exist by the task title.

## Deliverables

- [x] `src/lib/upload-validation.ts` — an allowlist with byte signatures.
- [x] The denylist deleted from `uploadAttachmentAction`, not merely bypassed.
- [x] The download route streaming private blobs instead of 302-ing to them.
- [x] `src/server/attachment-upload-security.test.ts`, registered in `pnpm test`.
- [x] An honest report of the production storage backend.

## Scope

The Tasks attachment path: `uploadAttachmentAction`, `src/server/storage.ts`,
and `GET /api/attachments/[id]`.

## Non-goals

- **Malware scanning is not built.** There is no scanning service in this stack
  and the budget is zero (D-015 Q5). Priced in the evidence, deferred with a
  named trigger. Nothing produced by this task claims a file has been scanned.
- **Quota and size limits are not changed.** They already exist in
  `src/lib/storage-config.ts` and are tier-driven; duplicating them in the
  validator would give two answers to one question.
- **Client-direct multipart upload is not built.** The 50 MB server-action
  ceiling stands.
- **The blob store is not provisioned.** That is a founder action on the HQ
  operator ledger.

## Implementation approach

Audit what exists before designing anything. Replace the denylist with an
allowlist checked on bytes. Fix the private-blob serving defect. Report the rest
rather than building it.

## Acceptance criteria

1. An upload is refused unless its declared type is on an allowlist; types
   nobody enumerated are refused by absence, proven for ten types including
   SVG, HTML, XML and executables.
2. A file whose bytes disagree with its declared type is refused, proven by the
   exact bypass the previous denylist had: HTML content declared `image/png`.
3. The MIME type written to `attachments.mime_type` is the validated type, never
   the raw client string, proven by a source-contract test.
4. Validation runs before the metadata row is claimed, so a refused file never
   reaches the database.
5. Formats with no dependable magic number are marked as unverified rather than
   reported as checked.
6. The download route does not redirect to a blob URL. Private blobs are
   streamed through the route, after the workspace check, proven by a source
   contract; `put` and `get` are proven to agree on `access: "private"`.
7. The security headers (`nosniff`, sandbox CSP, `private, no-store`) apply to
   every backend, with exactly one header block so a future branch cannot skip
   them.
8. A cross-tenant attachment id still returns 404, never 403.
9. The production storage backend is reported as it actually is, and the absence
   of malware scanning is stated with its cost and its trigger.

## Risks

- **Attachment upload is broken in production today, and not by this task.**
  `chooseBackend()` returns `vercel-no-token` when `BLOB_READ_WRITE_TOKEN` is
  absent, and `putBytes` throws. The operator todo is open. Every attachment
  upload on `app.signalstudio.ie` currently fails.
- **The private-blob streaming fix is verified statically only.** No blob store
  is provisioned, so it has not been exercised against a live one.
- **No malware scanning exists.** A couple can upload an infected document and a
  collaborator can download it.
- **The ZIP-container formats share one signature.** A `.docx` and an `.xlsx`
  are indistinguishable by leading bytes; both are accepted as ZIP archives.

## Decisions required

1. Provision the Vercel Blob store, or accept that attachments do not work.
2. Should malware scanning be bought before 1 September, or deferred with the
   exposure recorded?
3. Should `image/heic` stay on the allowlist? iPhone photographs are HEIC by
   default, and nothing in the product renders it.
