# E01.07 — Build the complete dependency map and identify the product, legal, capture, film and outreach critical paths.

**Task ID:** E01.07 · **Epic:** E01 · **Status:** in_progress

---

## Objective

A dependency graph that can answer what blocks what, and the five named critical
paths traced through it with an honest verdict on each.

## Business reason

Twenty edges across four tasks in a 211-task programme is not a dependency map.
It cannot answer the question a dependency map exists for, which is what happens
to everything else when one thing slips. With 29 days and R-001 live, that is the
question.

## Intended outcome

Every genuine precondition is recorded with a written basis; the five paths are
named with their weakest link; and the graph cannot deadlock the programme.

## Deliverables

- [x] The graph in `PROJECT_STATE.json`, every edge carrying a basis
- [x] A `depend` command that refuses an unsourced edge and refuses a cycle
- [x] Dependency satisfaction redefined so approval batching cannot deadlock
- [x] `DEPENDENCY_MAP.md` — the five paths, the conflicts, the gaps
- [x] Tests asserting the edge count and that no edge is unsourced

## Scope

Task-level dependencies across all fifteen epics, and the five critical paths the
title names.

## Non-goals

- Not scheduling. No estimates exist by decision (D-015 Q3) and none are invented here.
- Not resolving I-003. The E04 start conflict is localised, not reconciled.
- Not modelling E15.01 as task edges. Gate state already does that job.
- Not fine-grained ordering inside E07's seventeen non-lock tasks. Recorded as a gap.

## Implementation approach

Propose every edge with a named source, then flag each as controlling or
advisory. Advisory edges stay out of state because the schema has no advisory
flag and inventing one would make guidance look like a rule.

The material problem found while building it: **a dependency was satisfied only
at Done, Done requires founder approval, and D-024 batches approval to the end of
a package.** Wiring the real graph under those semantics would have idled every
parallel package behind one person's queue. Satisfaction therefore moves to
Founder Review, where a task has criteria, evidence and passed verification and
only the signature is outstanding. The cost is that a rejection can cause rework
downstream, so `task <ID>` prints satisfied-but-unapproved predecessors and
starting against one writes a note naming them.

## Acceptance criteria

1. Every task-level dependency that can be traced to a named source is recorded in `PROJECT_STATE.json`, not in a document.
2. Every edge carries a written basis, and a test fails if any task has dependencies with no basis.
3. The graph is acyclic, asserted by `validate` and by a test.
4. The five named paths (product, legal, capture, film, outreach) are each traced with their ordered chain, terminal deliverable, weakest link, and a stated verdict on achievability against the D-008 freeze dates.
5. No achievability verdict claims calendar precision, because no task carries an effort estimate.
6. Conflicts between the proposed graph and existing sources are recorded and not reconciled by guesswork.
7. Wiring the graph does not block any package that could previously proceed, and the semantics that make that true are written down rather than assumed.
8. What could not be determined is listed explicitly.

## Validation plan

## Evidence required

## Risks

An over-large graph is worse than a small one: it stops work for reasons nobody
can defend. The mandatory basis and the advisory/controlling split are the
guards. R-001 is what this task makes legible; it does not reduce it.

## Decisions required

`DEPENDENCY_MAP.md` trades a rework risk for the ability to run packages in
parallel. Push back if you would rather successors waited for your signature.
