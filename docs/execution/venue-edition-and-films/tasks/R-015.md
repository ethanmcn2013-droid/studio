## Objective

Make the shipped redemption path apply the ratified couple access term
`max(redemption + 548 days, wedding date + 90 days)`, and make it impossible for
that term to ever move earlier.

## Business reason

Twenty-five founding venues are about to be told that every couple who books
with them gets Signal Studio for eighteen months or three months past the
wedding, whichever is later. Until this change, the code that runs when a real
couple redeems a real code computed a flat term and nothing else. Irish venues
book twelve to twenty-four months out, so this was not an edge case: a couple
signing in March 2027 for a September 2028 wedding lost the product sixteen days
before the wedding it was bought for, in public, at the venue that gifted it.
That is the single worst outcome this product can produce, and it was live.

## Intended outcome

- The app's redemption path computes the D-022 term.
- The term has a floor of 548 days and no ceiling.
- A wedding date arriving after redemption extends the term. Nothing shortens it.
- The three couple-facing strings that described the term as a flat year say
  what the term actually is.
- The rule exists once in this repository and is held identical to the studio
  implementation by a test that executes both.

## Implementation approach

**Port, not share, and the reason is written into the module.** `app` and
`studio` are separate repositories with separate Vercel projects and separate
build roots. Nothing under `studio/` exists on disk when `app` builds, so an
import is not available. The only working sharing mechanism between them today
is a published npm package (`ds-foundation` is the single precedent), and
standing up a package for one arithmetic rule twenty-nine days before release
buys a release-blocking dependency instead of a fix.

The drift a port invites is answered rather than hoped away. When a studio
checkout sits beside the app checkout, the test imports
`studio/src/lib/venue-edition.ts` and runs both implementations over the same
matrix (**792 differential cases** on this run), asserting identical answers.
When it does not, the test says so out loud and the explicit behaviour vectors
still run, so CI is not silently weaker than a workstation.

**One decision point.** `compRedemptionExpiresAtMs` in
`src/server/db/couple-access-term.ts` is the only place a comp redemption's
expiry is decided. `comp.ts` calls it. A source-contract test fails if that
stops being true or if any flat duration multiply reappears on the redeem path.

**The wedding date, stated plainly.** See "What happens when the date is
absent" below.

## What happens when the date is absent, stated plainly

The rule needs a wedding date. The product does not supply one on the sponsored
path at all. There are **three** separate reasons, and the first survey of this
found only one of them. All three are verified in source.

1. **The capture is flag-gated off in production.** The date has a column and a
   capture UI: `workspaces.primary_date` (`src/server/db/schema.ts:308`),
   captured by the wedding branch of contextual onboarding
   (`contextual-onboarding.tsx:383`, `required` on the wedding path). That path
   is gated behind the `contextualOnboarding` flag, whose default is
   `NODE_ENV !== "production"` (`src/lib/planning/flags.ts:33`).

2. **Even with the flag on, a sponsored couple never reaches the capture.**
   Venue Edition redemption deliberately skips onboarding.
   `redeemCompCodeImpl` applies the wedding template inline and the result card
   deep-links straight to the board: `redeem-result-card.tsx:64-66` sends the
   couple to `/app/tasks?welcome=venue&v=<slug>`, and the comment above it says
   so outright, "deep-link past /welcome direct to the board". Only a
   non-sponsored redemption falls through to `/welcome`. So the one screen that
   asks for the wedding date is the one screen the sponsored couple is routed
   around. **This is the real blocker, and it is bigger than the flag.**

3. **There is no postponement path to recompute from.** `workspaces.primaryDate`
   is written at workspace creation only, in `bulkCreateWorkspacesAction` and
   `completeContextualOnboardingAction` (and copied unchanged by workspace
   duplication at `planning.ts:1097`). A search of `src` finds no action that
   updates it afterwards. D-022 point 3's postponement case is implemented and
   tested at the rule and database levels, but the product has no UI that can
   trigger it today.

**So the honest statement of what ships.** Every sponsored couple who redeems
today gets exactly `redemption + max(548, mintedDurationDays)` days. That is
identical to what shipped before this change, so no couple is worse off and no
term is ever shorter than the ratified one. What changed is that the machinery
is now correct, reachable and pinned: the moment a wedding date exists for a
couple, the grace half of D-022 applies with no further code change. What did
**not** change is that no wedding date exists for them yet.

**R-015 is therefore reduced, not closed.** The half of the risk that said "the
code computes the wrong term" is fixed and proven. The half that said "and no
wedding date is stored on the entitlement" is answered structurally — the date
has a home and a writer — but the product does not yet put a date in it for the
couples who need it. Reasons 2 and 3 are product-flow work, not term work, and
they are founder decisions rather than edits inside this task.

This is written into the module header of `src/server/db/couple-access-term.ts`
so the next reader cannot miss it.

## Risks

- **R-015 is reduced, not closed.** The rule is correct and reachable; the input
  it needs is not supplied on the sponsored path at all. Closing R-015 needs the
  three decisions below, not just the flag.
- **The postponement case is implemented but unreachable.** Nothing in the
  product can change a wedding date once a workspace exists, so D-022 point 3 is
  proven by test and cannot be exercised by a couple. If a couple postpones
  today, their term does not move. It also does not shorten.
- **The port can drift** if someone edits the studio rule and this repository is
  built without a studio checkout beside it. Mitigated by the differential test
  plus explicit vectors; not eliminated. A single shared package would eliminate
  it and is the right answer once there is time for it.
- **The extend path is fire-and-forget.** If
  `extendCoupleAccessForWeddingDate` throws, the failure is captured to Sentry
  and onboarding continues. The couple keeps the 548-day floor. Failing a
  couple's onboarding to fix an extension would be the worse trade, but it does
  mean a silent under-extension is possible and only visible in Sentry.
- **`studio/scripts/issue-codes.ts` still refuses non-548 durations.** A venue
  that already knows a long-lead date cannot have a longer code minted for it.
  The redeem path handles this correctly anyway, so the exposure is a missing
  optimisation rather than a broken term.

## Decisions required

1. **How the sponsored couple's wedding date gets captured at all.** Three
   things block it and they need one answer, not three. (a)
   `SIGNAL_CONTEXTUAL_ONBOARDING_ENABLED` is off in production. (b) Venue
   Edition redemption deep-links past `/welcome`, so even with the flag on the
   couple never sees the date question. (c) Nothing can change the date
   afterwards. **Recommended: ask for the wedding date on the redemption screen
   itself**, which is where the couple already is, where they certainly know the
   answer, and where D-022 point 1 said it belonged ("capture the wedding date
   at redemption"). That is a small, contained UI addition on a surface this
   task already touched, and it is the change that makes D-022 real for a
   long-lead couple. It was not built here because adding a question to the
   sponsored redemption flow is a product decision seventeen days before
   UI-freeze (2026-08-20), not an engineering detail. The alternative is to
   accept the 548-day floor for Cohort 1 and record that acceptance rather than
   leave it implied.
2. **`studio/scripts/issue-codes.ts:121-129`, D-022 point 4.** The guard reads:

   ```ts
   if (durationDays !== VENUE_EDITION_COUPLE_ACCESS_DAYS) {
     fail(
       `venue_edition codes must last ${VENUE_EDITION_COUPLE_ACCESS_DAYS} days (18 months)`,
     );
   }
   ```

   D-022 point 4 ratified: accept a computed duration, refuse anything shorter
   than 548 days. The exact replacement, using the helper that already exists at
   `studio/src/lib/venue-edition.ts:180`:

   ```ts
   const refusal = venueEditionDurationRefusal(durationDays);
   if (refusal) fail(refusal);
   ```

   plus adding `venueEditionDurationRefusal` to the existing
   `@/lib/venue-edition` import in that file. This is a **studio** change and
   this work package must not edit `studio`, so it is recorded here rather than
   made.
3. **Whether the port becomes a shared package.** Recommended after 1 September,
   not before.
4. **The redemption card metadata fix.** Approve or push back on the one item
   this task added to its own scope: `app/src/lib/comp-notes.ts` and the two
   call sites in `comp.ts`. It is separable from everything else here.
