# E08.06 — Secure invitation tokens against guessing, reuse, unintended forwarding, replay and duplicate redemption.

**Task ID:** E08.06
**Epic:** E08 — Engineering, security and reliability
**Status:** Founder Review
**Executor:** claude_code
**Approver:** Ethan McNamara
**Spec written:** 2026-08-03

---

## Objective

Make every bearer token that opens a Signal Studio surface — the couple's
invitation code and the Tasks share link — infeasible to guess, impossible to
reuse as another person, and stored in a form that a database read does not
turn into access.

## Business reason

A venue hands a couple a code. If a stranger can guess that code, they receive
a sponsored wedding workspace, they consume a code a real couple was given,
and they appear inside the adoption evidence the venue is shown. The failure is
attributable to a named Founding 25 venue, in public, at the moment the
programme is trying to establish that the product is safe to put in front of
its customers.

## Intended outcome

Three things are true that were not true on 2026-08-03:

1. A newly issued invitation code carries ~2^49.5 of guessing surface rather
   than ~2^24.8, and the number is asserted by a test rather than described in
   a comment.
2. `share_links` no longer stores a value that grants access. The secret exists
   in the URL and nowhere else; the row holds a sha256 under a unique index.
3. The redemption path spends an attempt budget before it will answer whether a
   code exists.

## Deliverables

- [x] One invitation-code generator per repository, with a stated entropy floor
      and a test that fails if the floor is lowered.
- [x] Rejection sampling in place of `byte % 31`, with a test carrying its own
      control that proves it detects the old bias.
- [x] Migration 0027 plus the dual-read resolver, the backfill script, and a
      security suite that runs against a real SQLite file built from the
      checked-in migration SQL.
- [x] Attempt limiting on the redeem path, checked before the lookup, with the
      failure mode stated in the source.
- [x] The share-link security suite registered in `pnpm test` and passing.

## Scope

The couple invitation code (`comp_codes` in the app, `license_codes` in
studio), the Tasks share link, and the redemption path that consumes them.

## Non-goals

- **Recipient locking is not implemented.** `license_codes.recipient_email_hash`
  exists and is enforced on the studio path; the app path that couples actually
  use has no equivalent. Whether a code should be bound to an email address is
  a product decision about how a venue hands a code over, not an engineering
  one. Decision required, below.
- **Revocation on the live redemption path is not implemented.** The studio path
  has `status = 'revoked'`; `comp_codes` has no revoked state.
- **The two redemption writers are not merged.** Recorded as a finding.
- **Codes already issued are not re-minted.** They keep their original entropy.
- Malware, uploads and storage are E08.07.

## Implementation approach

Audit the checkpoint adversarially first, then close the entropy gap, then
register everything so it actually runs. Entropy is chosen as the load-bearing
control because the rate limiter cannot be, and that choice is stated rather
than implied.

## Acceptance criteria

1. A newly minted couple invitation code carries at least 48 bits of entropy,
   with the arithmetic computed in a test rather than asserted in prose, and the
   test fails if the length or alphabet is reduced.
2. Exactly one invitation-code generator exists per repository; a source-
   contract test fails if a local re-implementation reappears.
3. Code characters are drawn uniformly. The test proving it carries a control
   that runs the previous biased draw and must fail the same bound, so a bound
   too loose to detect the defect cannot pass as a green test.
4. `share_links` stores sha256 under a UNIQUE index and never the secret; proven
   by dumping the whole table after a mint and asserting the secret is absent,
   against a database built from the checked-in migration 0027 SQL.
5. Neither the stored hash nor the public row id opens a share link; both are
   proven to resolve to null.
6. Every share link minted before migration 0027 still resolves, and a
   backfilled row cannot be opened by its public id through the legacy branch.
7. Share-link resolution never crosses a tenant boundary and never revives an
   archived workspace, proven on both branches of the dual-read resolver.
8. The redemption path consults its attempt budget before it looks the code up,
   proven by a source-contract test on statement order, so no unmetered
   "does this code exist" oracle exists.
9. Every test above runs in `pnpm test`. A security test that is not registered
   is not a control.
10. The limiter's failure mode (open, and unenforced until Upstash is
    provisioned) is stated in the source file, not only in a document.

## Risks

- **R-033** — addressed for new rows; the plaintext exposure is *reduced, not
  closed*, until `scripts/db/backfill-share-link-token-hashes.mjs --apply`
  reports zero plaintext rows against production.
- **Codes already in circulation keep 2^24.8.** The fix is forward-only.
- **The limiter fails open and Upstash is unprovisioned**, so entropy is the
  only control that is actually running today.
- **New:** a share link's URL can no longer be recovered after minting. "Copy
  this link again" is gone from the manage popover. That is what storing a hash
  costs.

## Decisions required

1. Should a venue invitation code be locked to the couple's email address? It
   closes unintended forwarding and it changes how a venue hands a code over.
2. Should `comp_codes` gain a revoked state, so a code handed to the wrong
   couple can be withdrawn?
3. Should the ~2^24.8 codes already issued be re-minted before Cohort 1?
4. Should the two redemption writers be merged onto the studio path that already
   carries recipient locking, revocation and an audit ledger?
