## Objective

Walk one invitation end to end, from a code minted for a venue to a couple with
a working wedding workspace, and verify the access term that is **actually
written to the database**, not the one the copy promises.

## Business reason

This is the product a venue is buying. If any step of it fails in front of a
real couple, it fails in public, at the venue that gifted it, which is the worst
outcome this product can produce (R-015's own framing). Every venue-facing
promise about the access term is a promise the database has to keep.

## Intended outcome

A recorded walkthrough exists showing a code minted, a redemption page loaded, an
account created, a workspace provisioned with the venue's name on it, and an
entitlement row whose `expires_at` matches
`max(redemption + 548 days, wedding date + 90 days)` for the wedding date the
couple actually entered.

## Deliverables

- [ ] A rehearsal walkthrough against a rehearsal venue and a rehearsal account.
- [ ] The `expires_at` value read back out of the database, in both the
      no-wedding-date case and the long-lead case.
- [ ] A screenshot or recorded text of the branded workspace showing the venue's
      **name only**.
- [ ] A statement of what a couple sees if they never enter a wedding date.

## Scope

`scripts/issue-codes.ts`, `/v/<venue>` invitation paths, `/redeem/[code]`,
account creation, contextual onboarding, `couple-access-term.ts`,
`workspaces.primary_date`, and the venue attribution line in the workspace.

## Non-goals

- Venue logos or venue-written welcome messages. D-027 point 3 fixes launch
  branding at the venue's **name only**. Do not build or test what is not the
  position.
- Keepsake. It has no product surface (E15.05).
- A second wedding-date field. The date is `workspaces.primary_date` and asking
  the couple twice is a defect, not a feature.

## Implementation approach

Rehearse against a rehearsal venue and a throwaway account, in three cases: no
wedding date, a short-lead wedding, and a long-lead wedding. The long-lead case
is the one R-015 exists for and it is the only one that proves the fix.

## Acceptance criteria

1. A code minted through `scripts/issue-codes.ts` for a rehearsal venue is
   redeemable exactly once, and a second redemption of the same code is refused.
2. Redeeming with **no wedding date recorded** writes an entitlement whose
   `expires_at` is exactly redemption + 548 days. The couple is not told a
   longer term than that anywhere on the redemption confirmation.
3. Completing wedding onboarding with a wedding date **more than 458 days out**
   moves the same entitlement's `expires_at` to wedding date + 90 days, and the
   new value is read back from the database rather than inferred from the UI.
4. Completing onboarding with a **short-lead** wedding date leaves `expires_at`
   on the 548-day floor. The term never moves earlier.
5. Changing the wedding date to a later one moves `expires_at` later. Changing
   it to an earlier one does not move it at all.
6. The provisioned workspace shows the venue's **name only**. No logo, no
   venue-written message, no "powered by" in the viewport. The attribution is
   one line.
7. The workspace's OpenGraph description carries the venue name only (R-024).
8. A published wedding workspace is `noindex` and `/p` is disallowed in the
   deployed `robots.txt`. **This currently fails in production** and is a
   release-blocking precondition for running this test with a real couple.
9. One attachment is uploaded successfully in production, because the Blob store
   has never been exercised there.
10. The redemption confirmation copy states the term in the couple's own terms
    without using "forever", "for life", or any permanence claim.

  workspace is offered to crawlers in production.
- The Blob store has never taken a production write. Attachment upload is on the
  couple's first-run path.
- **R-033** — `/embed/<slug>` renders a published workspace with no token, on
  any third-party site. Not fixed. A couple has no signal it happened.

## Decisions required

1. Does the rehearsal run against production, or against a preview deployment?
   Production is the only honest answer for a release test, and it means a real
   Clerk account and a real workspace that then has to be cleaned up.
2. R-033: are sponsored wedding workspaces embeddable at all? The simple answer
   is no and it costs nothing the couple asked for.
