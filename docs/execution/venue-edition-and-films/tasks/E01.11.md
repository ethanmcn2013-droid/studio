# E01.11 — Set the offer-freeze, UI-freeze, copy-freeze, capture-freeze, film-lock and release-candidate dates.

**Task ID:** E01.11 · **Epic:** E01 · **Status:** in_progress
**Executor:** claude_code · **Approver:** Ethan McNamara · **Spec written:** 2026-08-03

---

## Objective

Make the six ratified freeze dates operative: recorded in state, reported, and
attached to the tasks they gate.

## Business reason

D-008 set the six dates on 2026-08-02. They then existed in one note on one task
and in the decision log, and appeared in no report. A freeze date nobody can see
is a date nobody meets.

## Intended outcome

The six dates are first-class records, every generated status report shows them
with days remaining, the weekly review flags the ones landing inside seven days,
and the tasks each freeze gates carry that date as a target.

## Deliverables

- [x] A `freezes` block in `PROJECT_STATE.json`, seeded from D-008, each entry naming its source and what stops changing
- [x] A Freeze dates section in generated `STATUS.md` with days remaining
- [x] Freezes landing inside seven days flagged in the weekly review
- [x] Target dates attached to the eleven tasks the freezes gate
- [x] A `freeze` command that reports and refuses to move a date
- [x] A test asserting the six dates are exactly D-008's

## Scope

The six dates, their representation, their reporting, and their attachment to
tasks.

## Non-goals

- **Not changing any date.** D-008 ratified them. Moving one is change control.
- Not setting target dates on tasks the freezes do not name. Eleven were unambiguous; the rest are for the packages that own them.
- Not enforcing a freeze. Enforcement is a gate criterion (commercial 12), not a database constraint.

## Dependencies

None recorded.

## Inputs

- `DECISIONS.md` D-008 clause 3 — the six dates, controlling
- `PROJECT_STATE.json` — where they were not
- `DEPENDENCY_MAP.md` §3 — which tasks each freeze actually gates
- `REPORTING.md` §8 — why a target date must be stated and never computed

## Implementation approach

Seed the six from D-008 with their source recorded on each, and write what each
freeze means in one sentence, because "UI freeze" tells a future session the date
and not the obligation. Render them. Then attach them as target dates only to
tasks the freeze demonstrably gates: E05.12 *is* UI freeze, E09.12 *is* copy
freeze, E14.15 *is* capture freeze. Guessing beyond that would be fabricated
precision.

The `freeze` command deliberately reports and refuses to move a date. The guard
against a session quietly rescheduling a freeze is that there is no command to do
it.

## Acceptance criteria

1. All six dates are recorded in canonical state exactly as D-008 ratified them: offer 2026-08-15, UI 2026-08-20, copy 2026-08-21, capture 2026-08-22, film lock 2026-08-28, release candidate 2026-08-30.
2. Each carries the decision that set it and a sentence saying what stops changing on that date.
3. They appear in the generated status report with days remaining, and a passed freeze is marked as passed rather than shown as a negative number.
4. The weekly operating review names any freeze landing inside its seven-day window and the next one after it.
5. The tasks each freeze gates carry it as a target date with a recorded basis.
6. No command can move a freeze date. Moving one requires a change request.
7. A test asserts the six dates match D-008 exactly, so drift fails rather than passes.

## Validation plan

- `freeze` — expect the six dates with days remaining
- `node --test tools/project-control.test.mjs` — the freeze-date assertion and the render assertion
- The generated `STATUS.md` Freeze dates section
- `status weekly` §6 — the freeze horizon
- Attempt to move a freeze and confirm refusal

## Evidence required

- The `freeze` command output
- The `STATUS.md` section
- The test run
- The eleven target dates set, with their bases

## Risks

The dates are aggressive. `DEPENDENCY_MAP.md` §3 judges capture freeze on
2026-08-22 the tightest date in the programme, because it needs E04 to E09
substantially built and approved in nineteen days, and `BASELINE_REVIEW.md` §9
found no candidate implementation for E05 or E06. If a freeze moves, D-008 says
the release *definition* moves through a change record, not the work.
