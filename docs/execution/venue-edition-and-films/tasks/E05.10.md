## Objective

Write the access matrix the four named relationships need, check it against what
ships, close the defects that are closable inside this package, and prove by
test that a sponsoring venue can never become a member of a couple's workspace.

## Business reason

The couple's workspace is the thing the venue bought and the thing the venue
must never be inside. Everyone else the couple names is a person they chose. The
programme's central promise lives or dies on that distinction being enforced by
code rather than by convention.

## Intended outcome

1. The venue exclusion is a test that fails if anyone widens the invitation path.
2. The four-relationship matrix exists and is checked, so the roles gap is a
   founder decision with a shape rather than an open-ended worry.
3. The one ratified-constraint violation on the invitation path is fixed.

## Implementation approach

Audit first. The invitation machinery is genuinely well built and was not
touched: token entropy, email match, seven-day expiry, resend cooldown, server
clamp on both write and accept, audit rows. One user-facing string violated a
ratified decision and was replaced. Everything else is evidence and a test.

## Acceptance criteria

1. The four relationships the title names have a written access matrix stating
   what each should see and do.
2. That matrix is checked against shipped code, and every row is marked met,
   partly met, or not met with a file and line.
3. A sponsorship row confers no membership, and no membership confers a
   sponsorship.
4. Any role value other than `owner` reaching the accept path is clamped to
   `member`, including venue-shaped values.
5. A sponsor identifier or reference is not a usable invitation token.
6. No sponsor-facing read path can reach a membership row, a task, a note, a
   comment, an attachment or a share link.
7. No surface on the invitation path states a price, a plan or a seat count
   (D-020, "the couple never sees a price").
8. A sponsored wedding workspace has no member cap, and unlimited is represented
   as an absent cap rather than a large number.
9. The invitation surface tells the invitee truthfully what accepting grants,
   given that only one collaborator role exists.

## Risks

- Criterion 4's clamp is code, not a SQL constraint. `workspace_members.role`
  has no check constraint, so a direct write or a future migration could seat an
  arbitrary role. Recorded; adding the constraint is a migration and is offered
  as an option rather than taken unilaterally.
- `member` is full read-write on everything. A florist invited to see one task
  can read the honeymoon budget. This is stated on the invitation page now so it
  is at least not a surprise, but it is the gap, not the fix.

`workspace_members.role` gains a database-level constraint. Options in the
packet.
