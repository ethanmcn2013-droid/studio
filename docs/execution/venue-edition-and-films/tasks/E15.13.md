## Objective

Run the founder access promised in D-009 point 5 and the founding-request intake
promised in D-014 point 2, so that both are bounded, recorded, and never turn
into per-venue development.

## Business reason

Twenty-five unbounded relationships become a full-time job, which is exactly what
D-009 point 5 bounded and what R-006 measures. The request intake is the
mechanism that lets a venue be heard without anything being built for it.

## Intended outcome

Founder access is delivered as promised and no more. Every founding request is
logged, categorised and answered, and the boundary is a documented benefit rather
than a refusal produced later.

## Deliverables

- [ ] The founder-access commitment written where a venue can read it.
- [ ] The request intake, with a state per request.
- [ ] A monthly rollup of what was asked for.
- [ ] The standing answer for a request that will not be built.

## Scope

One 30-minute call per venue per year plus a named email route (D-009 point 5),
and the `sponsor_requests` intake in the entitlements database.

## Non-goals

- Standing access. D-009 point 5 is explicit that it is not standing access.
- Building anything for one venue. D-014 point 2, stated explicitly in the
  Benefits Charter so the boundary is a benefit and not a later refusal.

## Acceptance criteria

1. The founder-access commitment appears in the Benefits Charter in the exact
   ratified shape: one 30-minute call per venue per year, plus a named email
   route, and not standing access.
2. Every founding request is written to `sponsor_requests` with a sponsor, a
   state and a created date. Nothing lives only in an inbox.
3. Every request reaches a terminal state with an answer the venue receives.
   Silence is not a state.
4. The standing answer for a request that will not be built is written once and
   reused: requests are logged and shape the roadmap, nothing is built for one
   venue.
5. A monthly rollup names what was asked for and how many venues asked, and it
   feeds the roadmap rather than the backlog directly.
6. No request results in venue-specific code, configuration or copy.
7. The call is offered and its use is recorded, so the commitment can be
   evidenced at renewal.

## Risks

- **R-006** — founder capacity. Twenty-five calls a year is manageable; twenty-
  five open-ended relationships is not, and the difference is entirely in how
  this task is operated.
- The intake table exists and has no operating procedure. A table with no
  procedure becomes an inbox with extra steps.

## Decisions required

1. Who triages a request, and within what time? A request with no stated response
   time defaults to whenever the founder gets to it, which is how the boundary
   erodes.
