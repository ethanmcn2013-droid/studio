## Objective

Create the couple access lifecycle as an executable state machine, derived from the entitlement row rather than stored.

## Business reason

Every downstream surface asks the same question in a different way: what can this couple do right now. One answer, in one place, is the difference between a coherent product and five drifting opinions.

## Intended outcome

The lifecycle is code, under test, and the wedding day is deliberately not a state transition.

## Deliverables

- [ ] studio/src/lib/venue-lifecycle.ts COUPLE_ACCESS_STATES, nextCoupleAccessState, deriveCoupleAccessState
- [ ] studio/src/lib/venue-lifecycle.test.ts transition and derivation coverage including the expiry boundary
- [ ] studio/docs/architecture/ADR-008-venue-edition-lifecycle.md section 7

## Scope

The access state vocabulary, transitions, and derivation from redemption, expiry and erasure timestamps.

## Non-goals

Building Keepsake mode. Building the export. Building the deletion flow. Those are E06 and E03.

## Dependencies

| Dependency | State | Waived? |
|---|---|---|
| R-015 access-term fix | shipped in this package | no |

## Inputs

D-010 points 2 and 3, D-022, studio/src/lib/venue-edition.ts, studio/src/lib/entitlements-db/pure.ts resolveTier.

## Implementation approach

Derive rather than store, so there is no second source of truth to drift. Fold the wedding day into the term instead of making it an event, so nothing can fire on a couple's wedding day.

## Acceptance criteria

1. The four access states are defined with their legal transitions.
2. State is derived from redemption, expiry and erasure, never stored separately.
3. The expiry boundary matches the access gate exactly: expiresAt equal to now reads as ended.
4. Keepsake never expires on a clock.
5. Erasure is reachable from every live state and is terminal.
6. There is no post-wedding state, and the reason is recorded.
