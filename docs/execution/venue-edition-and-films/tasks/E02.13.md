## Objective

Give the Founding Venue number a real home: a stored field with a unique
constraint, assigned when the first payment clears.

## Business reason

D-009 point 6 and E02.10 both promise every founding venue a number, `01/25` to
`25/25`, assigned on cleared payment. Until now the only occurrence of `01/25`
in the codebase was marketing copy on the public venues page. Nothing computed
or stored which number a venue held, so two venues both being told they are
`07/25` was a matter of luck. That mistake is unrecoverable with exactly the
people whose reference value is the reason they were recruited.

## Intended outcome

The number is a fact on a row rather than a sentence on a page, and the database
makes a duplicate impossible rather than unlikely.

## Deliverables

- [x] `studio/src/lib/venue-founding-number.ts` — the pure rules
- [x] `sponsors.founding_number` and `founding_number_assigned_at`
- [x] A partial UNIQUE index on `founding_number` where not null
- [x] `studio/src/lib/entitlements-db/founding-numbers.ts` — assign, withdraw, programme status
- [x] Migration extended, with a fail-closed duplicate guard before the index
- [x] 15 unit tests and 16 writer tests against a real SQLite engine

## Scope

Storage, the unique guarantee, assignment on cleared payment, withdrawal on
payment reversal, and honest remaining-places reporting for scarcity claims.

## Non-goals

The HQ console control that calls it. The certificate render (E12.11). The
public founding page counter (E12.04). Payment-clearing detection itself, which
is E08. This task makes the number storable and correct; surfacing it is other
epics' work.

## Implementation approach

The rules live in a pure, client-safe module so they can be tested without a
database and reused by any surface. The writer holds the guarantee in the
database, not in application arithmetic: the read-compute-write is a race, and a
partial UNIQUE index is what makes losing that race harmless rather than silent.
The claim and its audit-ledger line commit in one transaction, per audit.ts.

## Acceptance criteria

1. The number is stored on the sponsor row and rendered as `NN/25` everywhere.
2. A partial UNIQUE index makes two venues holding the same number impossible at the database level, proved by test.
3. A number is assigned only when payment has cleared — never at signature, never on invoice.
4. Assignment is idempotent: a venue that already holds a number gets it back, never a second one.
5. A number held by a lapsed venue is never reissued.
6. Withdrawal exists only for a reversed payment, requires a reason, and records both in the audit ledger.
7. Remaining places are computed from the taken set, so a scarcity claim is true when it is sent.
8. Assignment order follows cleared payment, then earlier signature, and refuses to invent a winner when neither separates two claims.

## Risks

The migration was already applied to production before this field existed, so it
must be run once more to add `founding_number`. It is additive and idempotent.

Assignment has no caller yet: nothing detects a cleared payment automatically,
so the first numbers will be assigned by an operator action that does not exist
until E08. Recorded rather than hidden.

None. The policy was ratified in E02.10 and D-009 point 6; this implements it.
