## Objective

State, and then keep true, which segments of the venue-to-couple journey are
covered by tests that actually run — and which are not.

## Business reason

The sponsored journey is the product being sold to 25 venues: the venue pays,
issues an invitation, a couple redeems it, plans a wedding in it, publishes
something their family sees, and the venue is shown a number about it. Every
step crosses a privacy or commercial boundary that cannot be walked back once a
real couple is on the other side of it. Coverage that exists only on paper is
worse than no coverage, because it stops anyone looking.

## Intended outcome

Before: the app test suite was **red** and truncated. Seven test files across
the two repositories — roughly 2,200 lines of security, privacy, billing and
backup tests — existed on disk and were executed by nothing. One of them could
not run at all: it imported a `server-only` module the test runner cannot
resolve, and died on its first line.

After: the suite is green, every one of those files runs, and both repositories
carry a manifest that maps each journey segment to the test files that cover it
and **fails CI when a named covering test stops being run**. Segments with no
coverage are declared, with a reason and an owner. There is no third state.

## Scope

Establishing the real pass/fail state of both suites by running them; mapping
the sponsored journey to the tests that cover it; repairing what the 2026-08-03
checkpoint broke; and adding the mechanism that stops coverage silently rotting.

## Non-goals

- **Rewriting other groups' tests.** The billing, tenancy, token and backup
  tests belong to Groups A, B and C. This task establishes whether they run and
  whether they pass, not whether they are the tests those groups would write.
- **A browser or device suite.** Declared uncovered with a reason and an owner.
  Building one before the 2026-08-20 UI freeze is a founder call, not a gap an
  agent closes unasked.
- **Volume.** Three tests that pin a privacy boundary beat fifty shallow ones.

## Implementation approach

The check expands `pnpm test` — following `pretest` and any `pnpm <script>` it
chains to — into the set of files CI actually executes, then asserts that every
file named as covering a journey segment is in that set. An orphaned test file
is a hard failure, not a silent gap. This is the exact defect found on
2026-08-03, so the check is written to fail on it.

## Acceptance criteria

1. The real current pass/fail state of both suites is established by running
   them, with actual counts recorded — not inferred, and not reported as
   passing without a run.
2. Every segment of the sponsored journey is enumerated: venue invited, venue
   pays, founding number assigned, venue issues an invitation, couple redeems,
   couple plans, couple publishes, couple leaves, venue reads metrics.
3. Every segment is either mapped to named test files or declared uncovered
   with a reason and a named owner. A segment that is neither fails the check.
4. A named covering test file that exists but is not executed by `pnpm test`
   fails the check. Proven by the check's own self-test, not asserted.
5. Both suites pass end to end with the exact commands from `package.json`, and
   the recorded output is the real output.
6. The privacy boundary of the venue axis is pinned by a test that runs: the
   only venue-directed read in the app repository projects four aggregate
   numbers and can reach no couple content.
7. The check and its self-test run in CI in both repositories.
8. What is not covered is stated as not covered. No segment is described as
   tested because a test file exists.

## Risks

- **The suite was red and nobody knew.** The checkpoint's R-033 refactor moved
  the workspace guard out of `queries.ts`, and an existing contract test that
  asserts on that file's text failed. Because `pnpm test` chains with `&&`,
  every group after the failure never ran. A green report that is actually red
  has already cost this programme a cycle; this is the second instance.
- **Two studio script tests failed once under concurrent load and passed twice
  when re-run.** Recorded as an observed flake, not diagnosed. A flaky security
  test is a test that will be re-run until it passes.
- No browser, responsive or device coverage exists for the sponsored journey.
  The task title asks for it. It is not built.
