## Objective

Give every venue-sponsored surface a numeric performance budget that something
actually measures, and make a regression fail the build rather than a document.

## Business reason

A couple opens their workspace on a phone, in a venue, on venue wi-fi, often
while the venue is watching. The founding venue is the referrer. A slow first
load is the venue's embarrassment, not only Signal Studio's. Budgets are the
cheap way to stop that degrading between now and 1 September, when there is no
performance monitoring in production and nobody watching a dashboard.

## Intended outcome

Before: `contracts/launch-budgets.v1.json` had carried numeric budgets since
June 2026 and nothing measured them. Its only consumer read a measurements file
containing four nulls and the string `"pending browser/provider measurement"`,
and was in no CI workflow. `pnpm performance:measure` walked five sibling
repositories, four of which had been merged into `app` on 2026-07-31, printed
`"built": false, "gzipBytes": 0` for each, and exited 0.

After: every budget carries a measured number and a population, both
repositories fail CI when a measured value exceeds its ceiling, and every budget
that is NOT measured is named in the contract with the reason it cannot be.

## Implementation approach

Two numbers per budget. `budget` is the target. `ceiling` is a ratchet set at
today's measured value, and the ceiling is what fails the build. That lets the
check run in CI from day one on a codebase already over target, instead of
being switched off until someone has time to fix the bundle. A ceiling may only
be lowered; raising one is a founder decision, not an edit.

Every measured number carries the **population** it was computed over, and a
population of zero is never a pass. This is the specific failure that made the
superseded script worthless, and it recurred in miniature in the checkpoint: the
app repository's `repo_images` budget reported `0 KB · ok` because
`app/public` holds five SVGs and no raster image at all.

## Acceptance criteria

1. Every budget in the contract carries a measured value, the population that
   value was computed over, the date it was measured, and the basis of both its
   target and its ceiling. No budget is a bare number.
2. A measured value above its ceiling fails the run with a non-zero exit code,
   proven by deliberately breaching a ceiling and observing the failure — not by
   reading the code.
3. A budget whose population is zero never reports `ok`. It either fails with
   exit 3, or, where the emptiness is a known fact, reports `no data (declared)`
   against a reason recorded in the contract.
4. A missing production build, a missing `imageRoot`, a build manifest whose
   shape has changed, or a contract naming a budget the script cannot produce
   each fail with exit 3 rather than reporting a measurement of zero.
5. The check runs in CI in both repositories, after `pnpm build`, on every pull
   request and every push to `main`.
6. The checker's own rules are exercised by `--self-test`, which runs in CI and
   needs no build, so the enforcement logic is proven and not merely present.
7. Every budget the check does NOT measure — LCP, INP, CLS, server p75,
   per-route first-load JS, uploaded-image delivery, queries per page — is named
   in the contract with the reason it cannot be measured today and the
   instrument that would be needed. None is reported as passing.
8. No surface produced by this task claims a web-vitals, device or throttled
   -connection measurement has been taken. None has.

## Risks

- **The E08.10 gate criterion cannot be satisfied as written.** It requires
  measurement "on a mid-range mobile over a throttled connection" and names
  `pnpm budgets:check` and `pnpm performance:measure` as the commands that
  produce the numbers. There is no device lab, no Lighthouse CI job and no RUM
  provider, and both named commands are broken. This needs a change request or
  an accepted narrowing. Raised as a founder question.
- **`pnpm performance:measure` is still live and still exits 0 measuring
  nothing.** This session rewrote it to refuse to run and point at the
  replacement; the change was reverted by a concurrent lane working in the same
  worktree. The trap is unchanged as of this writing. It is a four-line fix and
  the orchestrator should re-apply it.
- The app's shared runtime is 45% over its target. Recorded, not hidden, and
  not fixed here.

## Decisions required

1. Accept `total_client_js` and `largest_chunk` targets set equal to today's
   measurement, or set real targets? No prior target existed for either.
2. Is a Lighthouse CI job or Vercel Speed Insights in scope before 1 September,
   or are web vitals accepted as unmeasured at launch?
3. `studio/public/brand/collateral/venue/venue-deck-preview.png` is 656 KB and
   is venue-facing. Compress it, or accept the ceiling where it is?
