# E06.05 — Implement private-link, password-protected and intentionally public sharing modes.

## Objective

Give the couple three sharing modes with genuinely different guarantees, and say
in the couple's own words what each one does and does not protect against.

## Business reason

"Who can see this" is the first question a couple asks and the first question a
venue asks on the couple's behalf. Three modes with vague boundaries is worse
than two modes with sharp ones, and a mode that sounds like security but is not
would be the single most damaging thing this product could ship into a trust
sale.

## Intended outcome

- The three modes are named against the product each belongs to, because there
  are two published products and they are not interchangeable.
- The private link's guarantees are recorded as evidence rather than rebuilt.
- Password protection is recorded as deliberately not built, with the exact
  sentence a couple reads in its place shipped in the product.
- The intentionally-public mode defaults to off for wedding workspaces, `/p` is
  in the robots.txt disallow list, and the publish confirmation states plainly
  what publishing does.

## Implementation approach

Audit first. Two of the three modes already have a data layer and one of them is
strong; the work is to assess them against written criteria, record what passes,
and build only the gap. The gap turned out to be copy and posture, not
cryptography: what was missing was any sentence telling a couple what publishing
does, and any default that protects a wedding page from search.

## Acceptance criteria

1. The three modes are defined against a named product. Where a mode spans two
   products, the criteria say which control belongs to which.
2. Private link is assessed and recorded as existing evidence: SHA-256 token
   hash, a unique index on the hash, a timing-safe compare, an explicit
   published-state gate, optional expiry, rotate and revoke, share versioning
   and a rate limit.
3. Password mode is recorded as deliberately not built, and the exact sentence a
   couple is shown in its place ships in the product rather than being implied
   by an absent control.
4. `/p` is in the robots.txt disallow list, and the known interaction between a
   `Disallow` and a per-page `noindex` is written down rather than papered over.
5. The publish confirmation states plainly what publishing does, including that
   task titles and tags are on the page and that search engines are not invited.
   Before this task it was one button whose caption never mentioned either.
6. Wedding workspaces are `noindex` on `/p` by default, and search visibility is
   an explicit couple opt-in.
7. R-033 is answered: a decision is recorded on whether wedding workspaces are
   embeddable at all, and if the answer is no, the exclusion is enforced in the
   route and `scripts/check-frame-headers.mjs` is updated in the same change.
8. Nothing in the shipped copy states or implies legal approval, solicitor
   review or GDPR compliance (D-016).

## Risks

- **Criterion 6 is not delivered at all, and this is the headline risk.** Two
  Wave 4 packages sharing the worktree built the same storage column within
  minutes of each other. This package withdrew its migration on finding the
  collision; the other package then withdrew theirs. Final state, verified:
  no column in `src/server/db/schema.ts`, no `0027` SQL file, ledger tail
  `0026_workspace_money`. **The publish confirmation shipped by this task says
  "The page is not listed unless you turn search listing on", and that control
  does not exist yet.** The line is true about the default and forward-references
  a control. It must not reach a couple before the opt-in ships.
- **`check-migration-contract` validates the ledger, not the schema.** During the
  session `schema.ts` carried a column with no migration file and the gate stayed
  green. That drift class is currently uncaught.
- **R-033 is not closed.** No decision on wedding-workspace embeddability was
  available, so nothing was enforced in the `/embed` route. What was done is
  smaller and correct under every option: `/embed` now carries the same
  analytics-free CSP as the other couple-facing routes (E06.07).
- **`share_links.token` is still a plaintext primary key resolved by raw
  equality.** Wave 3's fix is on the WP-07 branch, which is not in this tree.
  Not touched here to avoid a third collision.

## Decisions required

1. **Ship password-protected sharing, or record it as deliberately not built?**
   Recommendation: do not build it. The private link is already a 256-bit token
   stored only as a SHA-256 digest, with rotate, revoke and expiry, which is
   stronger than a password a couple will choose. A forgotten-password recovery
   story on a keepsake is a support burden a sole founder does not have, and a
   weak password mode would be the one part of this product that sounds like
   security and is not. The refusal sentence is already shipped.
2. **Are sponsored wedding workspaces embeddable on third-party sites at all?**
   Today anyone holding a slug can frame a couple's page inside a site the couple
   has never seen, with no signal and no way to stop it short of unpublishing
   (R-033). Recommendation: no for wedding workspaces. It costs nothing the
   couple asked for.
3. **`/p` in robots.txt disallow changes behaviour for every published
   workspace, not only wedding ones.** A per-slug disallow list is not an option,
   because it would publish the list of wedding slugs. Recorded as accepted under
   D-033; say the word if general Tasks projects should stay crawlable and the
   control should be the per-page `noindex` alone.
