## Objective

Give a couple a safe path from a photograph on their phone to a photograph on
their public artifact, where "safe" means the file's own metadata cannot
publish a location the couple deliberately concealed.

## Business reason

A Timeline made of titles and dates is a rail. The photographs are what make it
a keepsake worth a venue's EUR 1,000, and they are the single largest reason a
couple will send the link to their family. They are also the largest new
privacy surface in the epic: a phone photograph carries the coordinates of the
place it was taken and the second it was taken, so shipping photographs without
stripping metadata would quietly undo E06.06 for every couple who used it.

## Intended outcome

A photograph published on a couple's artifact carries no EXIF, no GPS, no
capture time and no free-text comment; it appears the right way up; it has an
alt attribute that is either the couple's own words or deliberately empty; and
the numbers governing its size are written down rather than buried in a resize
call.

## Scope

The byte path and its rules: what may be published, what is removed before it
is, what the photograph's alt attribute becomes, and what the numbers are.

## Non-goals

- **Re-encoding pixels.** No image is resized or re-compressed server-side.
  There is no image-processing library in this repository and adding one is a
  dependency decision, not a line of code. `stripImageMetadata` removes
  metadata segments and copies the compressed image data untouched, which is
  why it cannot lose quality and needs no native binary.
- **Rotating pixels.** Orientation is read and handed back as a value so the
  caller can persist it and apply it at render. Discarding it without recording
  it is how a portrait phone photograph ends up sideways on a public page.
- **Face detection, auto-tagging and face grouping.** A standing no, ratified
  in D-033. A "smart crop" is a face detector, so smart crop is out too.
- **Changing the upload action.** That file is E08.07's, on another branch.

## Implementation approach

Build the half that is safe to build alone and that everything else waits on,
and leave the half that would collide.

The metadata boundary is a pure function over bytes. It parses JPEG segments
and PNG chunks, reads the TIFF stream that carries orientation, GPS and capture
time, and then rebuilds the file without any segment that describes it. Format
support is an allowlist of two: JPEG and PNG, the formats it can prove it has
cleaned. WebP, HEIC and anything else are refused rather than passed through
unexamined, which is the same refusal-by-absence rule E08.07 applied to MIME
types.

## Acceptance criteria

1. A photograph carrying GPS coordinates, a capture time and an orientation is
   read for all three, and then published with none of the three present. The
   proof is a round trip on real bytes, not a call to a library, and it asserts
   the literal ASCII of the removed data is absent from the output.
2. The EXIF orientation is returned to the caller as a value after the segment
   carrying it has been removed, together with the CSS transform and the
   axis-swap flag needed to put a portrait photograph the right way up.
3. Format support is an allowlist, and a format outside it is refused rather
   than passed through. A truncated or malformed file is refused, not
   half-parsed.
4. Stripping never touches a pixel: the intrinsic dimensions and the
   entropy-coded image data are byte-identical before and after.
5. The maximum long edge, the minimum long edge, the target byte size and the
   refusal ceiling exist as exported values with numbers, not as comments.
6. Alt text has exactly three outcomes — described, decorative, refused — and
   never falls back to a filename. A decorative photograph gets `alt=""`, never
   a missing alt attribute.
7. A caller that forgets to strip is refused publication: bytes still carrying
   metadata return `metadata-present` rather than being published.
8. No face detection, no auto-tagging, no face grouping and no smart crop
   appears anywhere in the module, asserted by reading the source.
9. Every criterion above is covered by a test **registered in `package.json`'s
   `test` script**, so it runs in CI rather than only on the author's machine.
10. What is not built is stated as not built, in this spec and in the evidence:
    the upload wiring, the public image path, crop, and re-compression.

## Risks

- **R-031 / D-033.** A public image path on `/p` is a second indexable asset
  carrying a couple's wedding. The decision below has to be taken before any
  byte becomes publicly readable.
- **No image-processing library.** Without one there is no server-side resize,
  so the long-edge and byte ceilings are enforced by refusal rather than by
  correction. A couple uploading a 12-megapixel photograph is told no rather
  than being helped. That is a worse experience and a better privacy posture,
  and it is a deliberate trade recorded here rather than hidden.
- **The Timeline database has no receipt-backed migration runner.** Storing
  orientation, alt text and display dimensions needs columns, and there is no
  agreed path to add them.

## Decisions required

1. **Public blob URL or token-bound image route?** A public blob URL is
   unguessable but permanently readable by anyone who ever had it, and it
   survives unpublishing unless explicitly deleted. A token-bound route is
   revocable and costs a serverless read per image. This is the exposure
   decision and it is not reversible once couples have shared links.
2. **Does an image-processing dependency get added?** Server-side resize and
   re-compression need one. It costs no money and it is a real supply-chain and
   build-size decision on a serverless platform.
3. **Do photographs ship for 1 September at all**, given they need a column on
   a database with no production migration path?
