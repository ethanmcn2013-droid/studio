# E04.12 — Build deterministic migration fixtures and test data for every lifecycle state.

## Objective

Build one deterministic fixture per lifecycle state, on a pinned clock, so every state can be loaded and reviewed without waiting for it to occur.

## Business reason

Nobody can review a Keepsake screen, or a released-sponsorship screen, that takes eighteen months to reach naturally. The freeze dates in D-008 leave no room to wait.

## Intended outcome

Every state on all three axes has a fixture, coverage is asserted by test, and each fixture says what it proves.

## Deliverables

- [ ] studio/src/lib/venue-lifecycle.ts LIFECYCLE_FIXTURES and LIFECYCLE_FIXTURE_NOW_MS
- [ ] studio/src/lib/venue-lifecycle.test.ts coverage assertions across all three axes

## Scope

Fixtures for every invitation, access and sponsorship state, with the R-015 long-lead case and both survival cases represented.

## Non-goals

Rendering the fixtures into screens, which is E09 and E12. Seeding a database, which follows once the entities exist.

## Dependencies

| Dependency | State | Waived? |
|---|---|---|
| E04.07 | in this package | no |
| E04.03 | in this package | no |

## Inputs

The state machine, D-010, D-020, D-022, R-015.

## Implementation approach

Pin the clock. Derive each fixture's declared state from its own data and assert the two agree, so a fixture cannot quietly describe a state it does not represent.

## Acceptance criteria

1. Every state on all three axes has at least one fixture, asserted by test.
2. The clock is pinned, so no fixture means something different tomorrow.
3. Each fixture's declared access state is derived from its own dates and matches.
4. Each fixture states what it proves.
5. The R-015 long-lead fixture demonstrably outlasts its own wedding, and the flat 548-day term demonstrably would not have.
6. Fixtures exist for a lapsed licence and for a released sponsorship, both with access unmoved.
