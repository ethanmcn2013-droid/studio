## Objective

A security review with real findings and their true current state, a
production-readiness verdict that is allowed to be negative, and three
operational documents a single founder can execute alone at 03:00.

## Business reason

On 1 September, 25 venues are contacted and couples start arriving. There is
one operator, no on-call rota, no paid tooling and no second pair of hands. The
difference between a bad night and a bad outcome is whether the steps were
written down before they were needed. And a review that only reassures is worse
than none, because it converts an unexamined risk into an examined one that was
waved through.

## Intended outcome

Before: no security review, no production-readiness verdict, no release
checklist, no rollback procedure and no incident runbook exist for this
programme. The `data` release gate is `not_started`.

After: all five exist, specific to this stack, with real commands. The open
privacy findings appear in the production-readiness picture with their true
state, including the ones that are still open, and the verdict names what must
happen before a venue is contacted rather than declaring readiness.

## Implementation approach

Every finding is verified in the code as it stands today, by file and line, and
given a state of **closed**, **reduced**, or **open** — with the specific
condition that would close it. A finding whose fix is written but not deployed
is `reduced`, never `closed`: production is what a couple touches.

The three operational documents are written for one person with no help, so
each step is a command that can be pasted, and each decision point states what
to do when the answer is not obvious.

## Acceptance criteria

1. The review contains findings, each verified against current code by file and
   line, with a severity, an exploitation path in concrete terms, and a state of
   closed, reduced or open. A finding with no failure scenario is not a finding.
2. R-027, R-028, R-031, R-032 and R-033 each appear with their true current
   state, including the ones still open, and no fix is described as landed in
   production when it has only landed in a branch.
3. The production-readiness verdict is allowed to be, and is, negative where the
   evidence is negative, and names the specific conditions that must be met
   before the first venue is contacted.
4. The release checklist is executable by one person: every step is a command or
   an observation with a stated pass condition, and every step that requires a
   founder decision says so rather than assuming it.
5. The rollback procedure covers code, configuration and schema separately,
   states plainly which migrations cannot be rolled back and what is done
   instead, and gives a time budget per step.
6. The incident runbook names a person, a channel and a clock for each of the
   five scenarios the `data` gate lists, records the 72-hour Article 33
   notification clock and where the Data Protection Commission is contacted, and
   records the absence of paid on-call as an accepted limitation of the zero
   budget.
7. Nothing in any of the four documents states or implies legal approval,
   solicitor review, accountant verification or unqualified GDPR compliance.
8. Every command in every document is real, runnable in this stack, and taken
   from `package.json`, `DEPLOY.md` or the Vercel and Turso CLIs — not invented.

## Risks

- **The gate requires two things this session cannot do:** a tabletop
  walkthrough of the runbook, and a rollback executed once against a staging
  deploy. Both need the founder. Until both happen, the `data` gate cannot pass
  on E08.12's account, whatever the documents say.
- **The runbook names a person for every scenario, and the person is Ethan for
  all of them.** Written down, that is a single point of failure rather than a
  rota. Recording it does not fix it.
- A review by the agent that also wrote much of the code under review is not an
  independent review, and is not described as one.
