# E01.05 — Create the project board with fields for epic, task ID, priority, status, owner, dependency, acceptance evidence and target date.

**Task ID:** E01.05 · **Epic:** E01 · **Status:** in_progress
**Executor:** claude_code · **Approver:** Ethan McNamara · **Spec written:** 2026-08-03

---

## Objective

A project board carrying all eight named fields, generated from canonical state
so it cannot drift from the truth by being edited.

## Business reason

Eight fields are named in the title and each is named because someone needs to
answer a question with it. Six existed. Two did not, and one of the two missing
ones was acceptance evidence, which is the field the whole founder sign-off rule
turns on.

## Intended outcome

Every field in the title is a real field, populated or explicitly null, visible
on the generated board.

## Deliverables

- [x] `targetDate` and `targetBasis` on every task, with a `target` command
- [x] An `Evidence` column and a `Target` column on the generated board
- [x] Validation refusing a target date with no recorded basis
- [x] Tests asserting all eight fields are present

## Scope

The board's fields and their generation. The board is `BACKLOG.md`, rendered from
`PROJECT_STATE.json`.

## Non-goals

- Not a new tool. The board already existed; two fields did not.
- Not per-task forecasting. `REPORTING.md` §8 refuses computed completion dates and this must not create one.
- Not estimation. That is D-015 Q3 and stays progressive.

## Dependencies

None recorded.

## Inputs

- `BACKLOG.md` as generated before this task — ten columns, no target, no evidence
- `PROJECT_STATE.json` task records — 29 keys, none a target date
- `REPORTING.md` §8 — the standing refusal of forecast dates
- `DECISIONS.md` D-008 clause 3 — the six freeze dates, the only dates in the project that are ratified

## Implementation approach

The tension in this task is real and worth stating: the title requires a target
date, and `REPORTING.md` §8 forbids reporting forecast completion dates per task.
Both survive if the field is **stated, never computed**. A date arrives only when
someone sets it and gives a reason; nothing derives one. `validate` refuses a
target date whose basis is empty, so a date cannot appear without a reason
attached to it.

The first real target dates are the six freeze dates from D-008, attached to the
tasks those freezes actually gate. That connects this task to E01.11 instead of
leaving two governance tasks each half-done.

## Acceptance criteria

1. All eight named fields exist: epic, task ID, priority, status, owner, dependency, acceptance evidence, target date.
2. Acceptance evidence appears on the generated board as a column, not only in the underlying data.
3. A target date exists as a per-task field, is nullable, and is never computed from anything.
4. `validate` refuses a target date with no recorded basis.
5. A test asserts every one of the eight fields is present on the board, so a future render cannot drop one silently.
6. The board is generated from canonical state and `render --check` fails if it is hand-edited.
7. The tension with `REPORTING.md` §8 is resolved in writing rather than ignored.

## Validation plan

- `node --test tools/project-control.test.mjs` — the board-fields test and the target-date validation tests
- Inspect the generated `BACKLOG.md` header row and one populated row
- `render --check` — expect a clean pass
- Attempt a target date with no basis and confirm `validate` reports an error

## Evidence required

- The generated board header and a real row carrying a target date
- The test run
- `render --check` output

## Risks

The field could be used to fabricate a schedule. The mandatory basis is the
guard, and it is enforced by the validator rather than by convention.

## Decisions required

None. But note plainly: if you would rather this project carried **no** per-task
target dates at all, the honest route is a change request against the task title,
not a field left empty.
