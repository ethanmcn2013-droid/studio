# E08.05 — Complete role-based authentication and authorisation across venue owners, managers, viewers and couples.

**Epic:** E08 — Engineering, security and operational readiness

## Objective

Write down every role, what each may do, and what enforces it — then make the
one boundary that matters most, that no venue role can reach a couple's private
planning content, a build failure rather than a convention.

## Business reason

D-027 point 4 makes the Venue Portal at launch "invitation administration
only", which implies an administrator. There is none. Before a venue is given
anything that looks like access, the programme has to know exactly what a venue
can and cannot see, and be able to show it.

## Intended outcome

1. The role set is written down once per surface, with no third undocumented
   set, and the difference between what is designed and what is built is
   stated rather than blurred.
2. The rule that no venue role may hold a capability reaching couple content is
   enforced by a test that has been proven to fail when the rule is broken.
3. The Signal HQ session token is no longer derivable from the password.

- [x] Signal HQ session token v2 audited and kept: PBKDF2-derived HMAC key,
      issue time inside the signed token, twelve malformed-input cases failing

- [x] `role-matrix.test.ts` **wired into `pnpm test`** — it had never run
- [x] `ACCOUNT_CAPABILITIES` / `ACCOUNT_ROLES` exported as runtime values so
      the guard reads the shipped module instead of its own copy
- [x] The couple-content rule proven by mutation: green before, red after
- [x] Full role and permission matrix covering venue owner, manager, viewer,
      couple, collaborator, guest and HQ operator, with the enforcing file for

- [x] Evidence document
- [ ] Founder decision on R-043 Option C (see Decisions required)

## Scope

The venue capability matrix in studio, the app's workspace role checks, the
Signal HQ session gate, and the written matrix covering every actor.

## Non-goals

- **Building a venue account.** No venue-authenticated route exists, and
  building one before the 2026-08-20 UI freeze is not credible. R-043 holds the
  options; this task does not choose between them.
- **Implementing `sponsor_members`.** The lifecycle in
  `ROLES_AND_PERMISSIONS.md` has no implementation and this task does not
  create one.
- **Reconciling the four-role design with the three-role code.** That is a
  decision about what a venue may do, not a code cleanup.
- **Replacing the shared HQ password with per-person identity.**

## Implementation approach

Audit the prior run's work adversarially before accepting any of it. For each
claimed control, mutate the thing it claims to protect and confirm the control
turns red. Fix what does not. Where a control genuinely cannot be built before
launch, write it as documented-only in the same words that would be used if it
had been built, so no reader mistakes one for the other.

## Acceptance criteria

1. The role set is enumerated in one place per surface — venue roles in studio,
   workspace roles in the app — with no third undocumented set, and any
   divergence between documentation and code is stated explicitly.
2. Every role check runs server-side; no capability is enforced only by hiding
   a control in the UI.
3. Every cell of the venue capability matrix is asserted against the shipped
   module, not against the test's own copy, and a capability added to the
   module without a recorded decision fails the build.
4. No venue role may hold a capability naming couple content or couple
   identity, proven by a mutation that adds one and turns the suite red.
5. The venue-facing read path cannot reach the app database, and the venue
   projector cannot fetch anything at all.
6. The Signal HQ session token is not derivable from the password, carries a
   server-side expiry, cannot be forged by editing its issue time, and does not
   survive password rotation — each proven by a test written to fail against
   the previous implementation.
7. Every `/hq` surface is gated or waived in writing, and the session token is
   minted in exactly one place.
8. Whatever is not implemented by 1 September is stated as not implemented,
   with the interim operating model named (D-016, R-043).
9. The evidence cites the guard by file for each role check, not a description
   of one.

## Risks

- **R-043 is not closed by this task.** There is still no venue identity. The
  shared HQ password still opens every HQ room, so it must never be given to a
  venue, and that constraint is now written into `auth.ts` itself.
- **The matrix governs a fixture.** Until a venue-authenticated route exists,
  every row is a specification. The evidence says so in its own words.
- The documentation/code role disagreement is recorded and unreconciled.

## Decisions required

   venue receives evidence rather than a login.** Confirm, so E08.05's venue
   half can be evidenced as deliberately documented-only rather than left

2. **Which role set is real** — the four-role, thirteen-row design in
   `ROLES_AND_PERMISSIONS.md`, or the three-role, six-capability code? They
   cannot both be cited as the venue permission model.
