## Objective

Make a backup of every module database takeable and provably restorable by one
command, rehearse a restore for real and record the result, replace a recovery
drill that could not fail, and add data-integrity checks over the couple's
workspace and the commercial record.

## Business reason

Turso is the only supplier in this stack whose failure is permanent rather
than temporary. Two databases carry the things this programme cannot
reconstruct: `tasks-prod` holds the couple's planning content, and
`entitlements-prod` holds who paid, which founding place they hold, and which
couple redeemed which code.

Losing the second means neither the venue's position nor the couple's access
can be re-established from anywhere. Losing the first, in public, at the venue
that gifted the workspace, is the same class of failure as R-015 — the worst
outcome this product can produce.

Before 25 venues are asked for money, "what happens if the database is lost"
needs an answer with a measured number in it.

## Intended outcome

- A backup of every module database can be taken with one command, and each
  one is restored and verified in the same run.
- A restore has actually been performed, with the elapsed time and row counts
  recorded rather than estimated.
- The studio recovery drill exercises the real entitlements schema and can
  fail, including on the one failure that looks like success.
- Data-integrity invariants over both databases run as commands and are held
  by tests that prove each check fires.
- The gap between "we can restore" and "we are backed up" is stated in those
  words, with what remains as a founder decision.

## Deliverables

- [x] `app/scripts/db/restore-verify.mjs` — restores into a throwaway local

- [x] `studio/docs/RECOVERY.md` rewritten against what is true on 2026-08-03.

## Scope

Backup and restore tooling; a real rehearsal; the recovery runbook; integrity
invariants over both databases; deletion of the drill that measured nothing.

## Non-goals

- **A scheduled backup job.** The obvious mechanism is a GitHub Action, which
  would put couple planning data into Actions artifact storage. That is a
  data-handling and residency decision for the founder, not for a script.
- **Turso point-in-time recovery.** A paid-tier feature; the account is Free
  and the budget is zero (D-015 Q5).
- **Running either integrity checker against a production database.** Requires
  credentials and a founder decision about connecting a build agent to live
  commercial data.
- **A schema change of any kind.** Group A owns entitlements migrations this
  wave; nothing here adds a column.

## Implementation approach

1. Audit the checkpoint adversarially before building anything. Two of its
   four test suites were run for the first time in this session; one was red.
2. Keep what was right. The backup format, the sorted content hash, the
   trigger-last restore ordering and the SELECT-only contract are all correct
   and were not rewritten.
3. Fix what was wrong: an order-dependent test that counted accumulated
   fixture damage, a hand-copied table DDL, an uncommitted-to-CI test set, and
   a 300 KB database dump committed into the repository with no gitignore
   entry.
4. Replace the fake drill with one whose final step is the failure that looks
   like success: a restore that replays every row and drops the triggers.
5. Execute the rehearsal and record the real numbers.

## Acceptance criteria

1. A backup of a real database can be taken and then restored into a
   throwaway database, with per-table row counts and content hashes
   recomputed **from the restored database** and compared against the
   manifest — executed at least once, with the elapsed time recorded.
2. The restore path refuses any target that is not a local file, so a
   rehearsal cannot become a production overwrite.
3. A restore that loses rows, alters a value, loses an index, or loses a
   trigger is each detected, proven by a test per failure mode.
4. A recovery drill exercises the real entitlements schema, carries sponsors,
   license codes, redemptions and the audit ledger, and proves append-only
   enforcement on the **restored** copy rather than the source.
5. Every module database can be backed up by one command, and a run that
   covered only some of them exits non-zero.
6. Data-integrity invariants exist over both databases, are SELECT-only by
   contract, and each one is proven to fire by a test that plants exactly one
   violation and requires that check — and only that check — to report it.
7. An integrity check whose table is absent is reported as skipped, never as
   passing.
8. No database dump is committed to a repository, and the backup output
   directory is git-ignored.
9. The runbook states the actual provider, the actual tier, the actual backup
   guarantee, and the data-loss window as a number, and names what is not
   built as not built.

## Risks

- **New, recorded here:** the data-loss window today is "the time since
  someone last ran a dump by hand". On 2026-08-03 that is four days, against
  databases that have since been replaced.
- **New, recorded here:** the measured restore time is a local-file number.
  The real number includes a network restore and a Vercel cutover, neither of
  which has been timed.
- Neither integrity checker has been run against production, so both report
  the health of a schema rather than of the live data.

## Decisions required

1. **Where does a backup live, other than one laptop?** GitHub Actions
   artifacts, Vercel Blob, and a private repository are all viable at zero
   cost, and each puts couple planning data somewhere new. Recommended:
   Actions artifacts with a 30-day retention, because the credentials are
   already there. It needs the founder's yes before it is built.
2. **Is a four-day-old manual dump of the previous generation of databases an
   acceptable position on 1 September?** Recommended no; item 1 is the fix and
   it is roughly a half-day once decided.
