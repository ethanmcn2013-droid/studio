## Objective

A single document that walks the route a sponsored couple actually takes, names
the file and line behind every step, and says plainly where the route breaks.

## Business reason

Twenty-five venues are about to hand this link to real couples. Everything E05
builds, everything the "Before the Day" film shows, and every promise the venue
makes rests on this route working. Nobody had walked it end to end. The map is
how the programme finds out what it is actually selling before a venue is
contacted.

## Intended outcome

The programme can state, with evidence, which steps of the couple journey exist,
which are blocked, and which were never built. The access term is described as
D-022 ratified it rather than as a flat eighteen months.

## Deliverables

- [x] `evidence/E05.01-couple-journey-map.md`, the map, 18 steps with file and line
- [x] Correction of three statements in `evidence/E05-E06-audit.md`, each with evidence
- [x] A handoff table routing every finding to the task that owns it

## Scope

The authenticated and unauthenticated route from the venue's invitation link to
first useful action, and the described state of active planning, wedding day and
Keepsake. What each of the four products gives a redeemed couple. What the venue
can see at each stage.

## Non-goals

- Fixing anything the map finds. The map is a document plus the seams it proves
  are missing.
- The venue-branded welcome surface (E05.02).
- Motion, responsive and polish work (E05.11); design-system review (E05.12).
- Building Keepsake. Its absence is reported, not remedied.

## Implementation approach

Walk the routes in source order rather than reading documentation. For each
step, open the file that implements it and record the line. Where behaviour
cannot be determined without a running service, label it unverified rather than
inferring.

## Acceptance criteria

1. Every route from invitation to first useful action is walked in order, each
   step naming the file and line, marked exists, partial or absent.
2. The access term is stated as `max(redemption + 548 days, wedding date + 90
   days)` per D-022, with the code path named and its reachability stated. No
   flat "eighteen months" claim appears anywhere in the document.
3. Every production break is named as a break, with file and line, and is never
   described as working.
4. For each of the four products, the map states whether a redeemed couple
   reaches it and what they see.
5. The map states what the venue can see of private planning content at each
   stage, with every egress path enumerated, and asserts nothing the code does
   not support.
6. No seat count, allotment or numeric per-couple entitlement is stated as fact
   anywhere in the document (D-020).
7. Keepsake and post-wedding stages are described as not built where they are
   not built, with the grep evidence.
8. Every claim is traceable to a file and line in the repository, or is
   explicitly labelled as needing a live check.

## Validation plan

Re-derive every load-bearing claim against the worktree rather than against the
prior audit. Run the greps and the test suites the document cites and paste the
real output. Where a suite fails, attribute the failure.
