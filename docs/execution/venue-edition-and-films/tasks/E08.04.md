## Objective

Establish, prove and honestly document the boundary that stops one couple's
workspace being readable from another, and stops a venue's view reaching any
couple's private planning content.

## Business reason

Twenty-five venues will each introduce Signal Studio to couples who put their
guest lists, supplier details and family arrangements into it. One cross-tenant
read, once, ends the programme — not because of a fine, but because the venue
that recommended it has to explain it. The product's whole proposition to a
venue is that it is safe to hand to a couple.

## Intended outcome

Three things are true that were not true before:

1. A forgotten tenant predicate fails CI, and the mechanism that detects it has
   itself been proven to detect, by mutation rather than by assertion.
2. A cross-tenant read is proven **empty** against a real database, per
   sensitive object, rather than inferred from the shape of the source.
3. The absence of database row-level security is stated in writing, with the
   compensating control named, everywhere the control is described.

## Scope

The app's four data surfaces (Tasks, Signal, Notes, Timeline), the studio
venue-facing read path, and the documentation of the control's real shape.

## Non-goals

- **Building row-level security.** It is not available on the provider.
- **A route-level 404-versus-403 sweep** across every API route. The data
  layer is proven; the routes above it are not. Recorded as an open gap.
- **Fixing the studio/app documentation disagreement about roles.** That is
  E08.05 and, underneath it, a decision.
- **Any schema change.** This task added no migration and no column.

## Implementation approach

Audit first, adversarially, including over the interrupted prior run's own
work. Prove each existing control by mutation before accepting it as evidence.
Build only what the mutations show to be missing: the gate's self-proof, the
strong/weak token split, and the behavioural negative suite.

## Acceptance criteria

1. Every workspace-scoped read in the app carries a tenant predicate, proven by
   a static gate that fails CI when a scoped table is read without one.
2. The gate is itself proven to detect a violation — a deliberately unscoped
   read turns it red — rather than only ever reporting green.
3. The tenant boundary has a runtime guard that throws rather than degrading to
   an unscoped or empty-string-scoped query.
4. The absence of database row-level security is stated explicitly in the
   evidence with the compensating control named, and no surface implies it
   exists.
5. A cross-tenant negative test exists per sensitive object — tasks, comments,
   attachments, share links, invites, entitlements, notifications, activities,
   sponsorships — proving an id from workspace A returns nothing in workspace
   B, against a real database rather than by source inspection.
6. The negative suite carries a control case proving the unscoped read would
   have leaked, so the assertions cannot pass vacuously.
7. No venue-scoped read can reach Notes, Tasks, Timeline or Signal content,
   enforced at capability, module-reachability and projection layers.
8. Every tenant-keyed table is governed, and the governed list cannot drift
   from the schema in either direction.
9. The evidence names, by file, every place a tenant predicate is enforced, so
   a reviewer can audit the list rather than trust it.

## Validation plan

node --test src/server/tenant-scope-rules.test.mjs src/server/tenant-scope.test.mjs
npx tsx --test src/server/cross-tenant-negative.test.ts
npx tsc --noEmit --incremental false

Plus three mutation runs, each of which must turn a green suite red:
an unscoped read; an unscoped read masked by a join ON clause; a governed
table removed from the schema.

## Risks

- **The control is a detector, not a boundary.** A read scoped to the *wrong*
  workspace id passes it. Nothing beneath it fails closed. This is inherent to
  the provider and is the reason criterion 4 exists.
- **Waivers are honoured on trust.** Eight `isolation-ok:` waivers exist; the
  gate checks that a reason was written, not that it is a good one.
- R-029 — the attribution unit is incoherent, which affects what the venue
  axis counts. Not addressed here.

## Decisions required

1. **The task title asks for "database row-level security", which Turso and
   libSQL do not provide and will not by 1 September.** Record as a change
   request that the control is application-level scoping plus a CI gate plus a
   behavioural negative suite? The alternative — leaving the title and calling
   the built control "row-level security" — is exactly the kind of quiet
   redefinition D-016 forbids.
