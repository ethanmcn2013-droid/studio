## Objective

Make the shipped Notes-to-Tasks flow read like something a couple planning a
wedding would say, without changing a line of its behaviour.

## Business reason

This flow is the moment the product proves its central promise. It is where
words leave a private notebook, and it is the only place in Notes where
anything crosses a boundary at all. The mechanism was built carefully: an
exact-body-bound assertion, an atomic guard against duplicates, a stated
payload. Then it was described to the couple in the vocabulary of the people
who built it. A couple reading "Send approved extract to Tasks" and "Will send:
approved wording, note ID, workspace ID" does not learn that their note is
safe. They learn that this software was not written for them. The behaviour was
already right, so the words are the whole of the work.

## Intended outcome

The same flow, the same guards, the same server actions, described in language
a couple recognises, and held there by a test rather than by good intentions.

## Deliverables

- [x] Every user-visible string in the flow moved into one module
- [x] Engineer vocabulary removed from the shipped surface
- [x] The privacy sentences rewritten and kept in every state they occupied
- [x] A machine-checkable guard, registered in the CI chain
- [x] A fail-before run proving the guard is not tautological
- [ ] Founder approval

## Scope

The hand-to-Tasks flow in `src/modules/notes/app/hybrid/HybridNotebook.tsx`
(the shipped notebook), its strings, and the two genuinely wrong strings in the
legacy `Notebook.tsx` rollback path.

## Non-goals

- **No logic change.** No state, guard, server action, assertion or retry
  behaviour is edited. Wording only.
- The local-recovery and offline subsystem's strings ("Local recovery is
  blocked…", roughly fourteen of them). They are engineer-shaped too, they are
  a different subsystem, and rewriting them here would hide a real behaviour
  question inside a copy task. Named honestly as unmet, not quietly skipped.
- Visual, motion or layout work. E05.11.
- The Timeline preview panel's field labels, which belong to E05.08.

## Implementation approach

The flow's strings were inline across a 2,500-line component, which is why they
drifted. They move to `src/modules/notes/lib/notes-copy.ts` in two registers,
generic and wedding, with a test asserting both registers define every key.
That makes the wording reviewable by someone who did not write it, which is
what the acceptance criteria require, and it gives E05.11 and E05.12 one place
to read from.

## Acceptance criteria

1. Every user-visible string in the hand-to-Tasks flow is defined in one
   module rather than inline in the component.
2. No user-visible string in the flow contains: extract, promote, approved
   wording, approved action, approved send, approved source, workspace ID,
   note ID, note identity, immutable, payload, receipt, destination.
3. The privacy sentence still names exactly what crosses and what does not, in
   words a couple reads, and appears in every state it appeared in before.
4. In the wedding register the boundary sentence states that the venue never
   sees any of it.
5. Every error state in the flow reads as something a couple can act on.
6. A test enforces 2, 3 and 4 and fails if a banned term returns.
7. That test runs inside `pnpm test`, not only when invoked by hand.
8. The guard is demonstrated to fail against the pre-task strings.
9. Behaviour is unchanged: same states, same guards, same server actions.
10. `pnpm typecheck` clean, `pnpm test` green, brand-voice lint zero HARD
    findings in the module.

## Risks

- The internal task id was printed to the couple as "Receipt review_task_…".
  Moved to a `data-task-id` attribute so support and tests keep it without the
  couple reading it. If anything depended on that visible text, it would be a
  test, and no test referenced it.
- The wedding register changes wording only. If a founder decides the couple's
  Tasks product should not be called "your list", the copy module is the single
  place to change it.

## Decisions required

1. **"Add to our list" versus "Send to Tasks" for a couple.** The wedding
   register currently avoids naming the product. Real trade-off, in the packet.
2. **Whether the local-recovery strings get the same pass.** They are the
   largest remaining block of engineer-shaped copy in Notes.
